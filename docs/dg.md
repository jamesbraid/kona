# DG: how the kernel driver reaches the display generator

What the 6.5.30m kernel driver does about video: the cursor, the buffer swap and the retrace wait. Register values and addresses are in [DG.h](../DG.h). Facts are labelled **established** (read from the disassembly, function named), **inferred** (reasoning given) or **unknown**. First configuration only: one IP27 Onyx2, one InfiniteReality2 pipe; genlock, other pipe counts and the option boards are not read.

Sources: `kona_kernel/disasm/kona_video/kona_video.text.s` (all function names below), the Kona kernel driver assembly unit 1, the Kona kernel driver genlock assembly unit, and the 6.5.5 installed header the Kona stack header 6 for the ioctl structures.

Notation: `P` is the driver's per-pipe state. Offsets are the ones the code uses.

## What the driver can reach

**Established.** The kernel never writes a display register directly. Every display access is a write to `HH_VC_ADDRESS` (0x8003c0) followed by one or more writes to `HH_VC_DATA` (0x8003d0), through the 32-bit register window. The only reads are in `kona_attach` (`docs/xg.md`, steps 4 and 7), which writes 0x8800 and 0x0b00 to `HH_VC_ADDRESS` and reads `HH_VC_DATA`. `HH_VC_DATA_INCR` and `HH_VC_FREADY` (HIP.h) are never touched by the driver.

**Inferred.** The pair is an indirect port into the display generator: the address write selects a register, the data write moves its value. The name "VC" comes from the kpm table. The driver has no code for video timing, mode tables, colour lookup, gamma or blanking: the display mode, the video format and the colour tables are loaded by other paths (X server and the microcode, `ucode/dg4/`, `ucode/vof/`) that this driver does not carry. Whether the display generator is the chip on the far side of the port is **unknown**. *Test that would settle it:* take the address values the kernel writes to the port (0x100-0x103, 0xb00 + 0x100n, 0xb02 + 0x100n, 0x8800) and look each one up in the address blocks of the firmware's display-bus table ([ucode/dg_access.tsv](../ucode/dg_access.tsv), written by `retools/tools/kona/dg_access.py` from `arm1.u`). The firmware reaches that bus with `DoDGRqstVCWrite` and `DoDGRqstVCRead` at ARM address 0x00600000 + 4 x A (below); if every kernel address falls in a block the table assigns to the display-generator board, the port and the bus are one space and the unknown closes for those addresses. An address with no block (0x8800 is not among the constants in that table) needs the frame-manager chip's decode table, which is not available, or a bus capture of the data word.

## Cursor

**Established.** Three ioctls feed the cursor, all of which only record state under the lock at `P+3520` and set a "pending" flag:

| Entry | Stores | Flag set | Grade |
|---|---|---|---|
| `kona_select_cursor` (the select cursor Kona driver request) | mode byte at `P+3555`, glyph address word at `P+3560`, hot spot halfwords at `P+3568` and `P+3570` | `P+3552` and `P+3553` | established |
| `KONApositioncursor` | x halfword at `P+3564`, y halfword at `P+3566` | `P+3553` | established |
| `kona_set_channel_rect` (the set channel rectangle Kona driver request) | one entry of the cursor-rectangle table (below) | `P+3552` and `P+3553`; also sets the current cursor channel `P+3556` to 32 (none) | established |

The mode values in the 6.5.5 header are 0 off, 1 crosshair, 2 glyph.

The pending flags are consumed in `kona_video_intr`, which is the handler for the video interrupt (docs/hip.md), under the same lock. So cursor state reaches the hardware once per video interrupt, not at ioctl time.

**Established.** `kona_video_intr` on `P+3552` set: runs `kona_enable_dac_cursor`, then writes address 0x101 and data `P+3560` (the glyph address). If the DAC flag `P+3554` is clear it first writes address 0x103 and data `P+3555` (the mode). On `P+3553` set: runs `kona_determine_cursor_channel`; if the owning channel changed, reruns `kona_enable_dac_cursor`, writes address 0x100 with the new channel number, and writes address 0x103 with the mode (or 0 when no channel owns the cursor); then writes the position, in one of two forms.

- **Not a DAC cursor.** One data write to address 0x102: bits 0-12 are `x - hot_x - x1 + 32`, bits 13-25 are `y - hot_y - y1 + 32` (x1, y1 from the owning channel's rectangle, hot spot from the select call). When the word at `P+1088` has a zero top nibble, bits 0-1 are cleared, so x is a multiple of four. **Established:** `P+1088` is `id.dg.xmap[0]`, the identity word of the first display-generator XMAP chip in the configuration record the caller supplied ([kernel.md](kernel.md#the-configuration-record-and-its-identity-words)).
- **DAC cursor** (`P+3554` set, the channel's rectangle has valid = 2). Address 0x0b00 + 0x100*channel, data 0 then 2, which selects indexed DAC register 0x200; then four writes to block address 0x0b02 + 0x100*channel (the indexed-register data port), the address re-sent before each, carrying x low byte, x high byte, y low byte, y high byte. The position is scaled to the channel's output size: `x_out = dac_xout * (x - x1) / (x2 - x1) - dac_hotx`, `y_out` likewise (divide-by-zero is trapped with `teq`, so a degenerate rectangle halts the kernel thread).

`kona_enable_dac_cursor` writes eight channel blocks: for channel n it writes address 0x0b00 + 0x100*n with data 4 then 2 (two consecutive data writes to the same address, **established**), then address 0x0b02 + 0x100*n with 5 if n is the cursor channel and the DAC flag is set, otherwise 0. If the DAC flag is set it first writes address 0x103 with 0.

**Inferred.** 0x100-0x103 are the cursor registers of the display generator (channel, glyph address, position, mode), from the values each carries; the IR diagnostic's XMAP register list names registers 0-3 `XMAP_CURSOR_CHAN_ID`, `_GLYPH_BASE`, `_POS` and `_ENABLES` ([DG.h](../DG.h)), so address 0x100 + n is **inferred** to be XMAP register n. The 0xb00 blocks are per-channel registers of eight video channels, from the stride of 0x100 and the eight-iteration loop; the 5 is a "DAC cursor on" encoding (bits 0 and 2), a guess from its being 0 for all other channels. Whether the 0x102 form needs coordinates aligned to four pixels is **unknown**; a read of the textport's cursor routines for a mask of both coordinates would settle it. The "4 then 2" pair is the video DAC's two-byte index 0x204, the cursor control register ([below](#the-firmwares-display-bus-window)), and the glyph address is a word address in the cursor memory, slot x 260 ([cursor memory](#cursor-memory)). No code writes an address 0x22: the position bytes go to the data port of the channel's DAC block, as above ([the DAC cursor findings](findings/dac-cursor.md)).

### Choosing the cursor channel

**Established.** The driver keeps 32 channel rectangles, 16 bytes each, at `P+0x1168` (4456), one per logical video channel. `kona_set_channel_rect` fills one from the 6.5.5 `kona_set_channel_rect_args`: valid (0 invalid, 1 xmap cursor, 2 DAC cursor), a signed priority, four halfword corners x1, y1, x2, y2, signed hot spot bytes and two halfword output sizes (DG.h has the offsets). `kona_get_xy_channel` (the get XY channel Kona driver request) and `kona_determine_cursor_channel` scan channels 31 down to 0. A channel is a candidate if it is valid and `x1 <= x < x2`, `y1 <= y < y2`. Among candidates the one with the **smallest** priority value wins. In `kona_get_xy_channel` ties go to the lowest channel number (the scan accepts on equal, so the last, lowest index stays). `kona_determine_cursor_channel` adds retention for the channel that owned the cursor before. **Established** (`kona_video.o` 0x14d8-0x1694, read in full; the IP27 build): it loads the previous owner from the state byte +28 (0x14dc); during the scan it sets a flag (`movn` at 0x1574 and 0x15f0) when the scan index equals the previous owner and that channel is accepted as a candidate (the compare is at 0x1568 and 0x15d4); and after the scan, when the previous owner's priority byte (0x1628, 0x1648) equals the winning priority and the flag is set, it does not store the lowest-index winner into +28. Otherwise it stores the winner into +28 (0x1644, 0x1690) and returns 1. So on an equal-priority tie the channel that last showed the cursor keeps it, and only a strictly smaller priority, or a previous owner whose rectangle no longer holds the position, moves it. When the winner is channel 8 or above, or no channel, the routine clears the DAC-cursor flag byte at +26 if it was set (0x1614-0x1624) and returns 1 in that case. When the winner is channel 0-7 the routine instead recomputes the DAC-cursor flag byte at +26 from the winner's valid byte (equal to 2, 0x1650-0x1658), even when the previous owner is retained, and returns 1 if that flag changed (0x166c-0x167c). The 6.5.5 header comment says "higher priority channels get the cursor": the code compares numerically, so a smaller number wins; whatever scale the X server uses, the kernel is not inverting it. The result 32 means no channel.

Channels 0-7 are the ones the display generator has cursor registers for (the same loop count as `kona_enable_dac_cursor`). For a winning channel of 8 or more the function takes a different branch that reports a change when the DAC flag was set (clearing it) and when the winner changed; what the logical channels above 7 map to is **unknown**. *Test that would settle it:* read the callers of the set-channel-rectangle request in `ddx/kona.so` for the range of channel numbers they pass with a nonzero valid byte, and the cursor display requests in `ucode/dg_dispatch.tsv` for any that accepts a channel above 7. If the X server never sends a valid rectangle above channel 7, the branch is dead code on this configuration; if it does, the request that receives the channel names the register block it reaches.

## Buffer swap and retrace wait

**Established.** A swap is not a register write. `KONAschedswapbuf(P, buffer, index, mode)` sends commands in the pipe's stream through the kernel kick sequence of `kona_kern.h` (0x30000 before the first token, 0x10000 before payload and later tokens, 0 at the end), then asks to be told when the pipe passes a marker. The stream, tokens from `GE.h`:

1. `VALIDATE_BANK` (0x1f4), two words: the halfwords at offset 18 of the objects at buffer+120 and buffer+128. Then token 0x172 (`HP_GED_NOP`) with one 0 word.
2. A member of a multi-pipe network (`P+5488` nonzero, `P+5500` not -1 and equal to the halfword at +248 of the buffer) sends `HP_DPLEX_SWAP` (0x166) with payload 1, then the `DISPMODE` packet of step 3, then always takes the retrace wait below, whatever `mode` is: no swap-group logic runs, and mode 1's immediate completion does not apply.
3. `DISPMODE` (0x1e6), three payload words: the word at buffer+20, `index`, and a mode byte kept per index at `P+4360+index`. The byte's bit 0 is set from the halfword at +18 of the buffer's +120 object when `index` is below 64, bit 1 when it is 64 or more. `KONAsetdisplaymode` (the display-mode ioctl) stores a caller-supplied byte there and sends the same token with payload 0, index, byte. The value comes from the X server: it is the `hwd_mode` word `konValidateMode` builds and passes through the load-display-mode resource-manager request ([opengl.md](opengl.md#display-modes-x_loadxmap_did-and-the-load-display-mode-resource-manager-request-1017) lists its bits by the module's own visual cases). The firmware's `arm_dispmode` writes the byte unchanged to the display-id mode table. What the XMAP does with each bit beyond that is unknown: no shipped software or published source depends on it; routes tried: `arm_dispmode`, the X module's builder in `konValidateMode`, the kernel's two senders.
4. Outside a network, with `mode` 1 or a buffer in no swap group (buffer+120's +160 is 0): the `DISPMODE` packet, then mode 1 calls `kona_swap_complete` at once with no wait, and any other mode takes the retrace wait. This path sends no `HP_TBUS_1`.
5. A buffer in a swap group (the record at buffer+120's +160: member count +0, members still due +4, sequence number +8; members linked in a ring through +168, each with an arrived byte at +176) holds the swap back until the last member arrives. When the due count is 0 it is reloaded from the member count, every arrived byte is cleared and `SWAP_CNTRL` (0x1db) with 0 goes out for each swap-table entry naming the group; a member whose byte is already set sends nothing more. A first arrival sets its byte, calls `kona_retrace_setup` with `kona_swap_complete`, keeps the returned number at group +8 and counts down; while members are due it stops there. The last member sends a `DISPMODE` packet for every ring member, clears the bytes, sends `SWAP_CNTRL` with 1 for each table entry naming the group and calls `kona_retrace_activate` with the number kept at +8. Only then, and only for `mode` 2, does it send token 0xe2 (`HP_TBUS_1`) with 0x478478 twice and call `rrmValidateBuffer` (in the video module's disassembly, the `bne` on mode 2 before `li $a1,226`). By inference from the token's handler `mgesi_TBUS_1`, which takes three words (a bus-mode code, then the low and high halves of a 64-bit raster-bus word; [GE.h](../GE.h) at `HP_TBUS_1`): the kernel's two words are a mode of 0x478478 and the low half, and the pipe takes the next word written to the command port as the high half, since the token map counts three.

When the marker is reached, `kona_swap_complete` runs. `kona_mswap_complete` is the matching path for the managed (multi-pipe) swap, `KONAschedmgrswapbuf`, with a 96-entry table at `P+3976` and `P+3592`; it is not read further.

### Retrace sequence

- `kona_retrace_setup` takes the next number from the counter at `P+3528`, stores it in the buffer's retrace record (record +0, record at buffer +112) together with the callback (record +16), and appends the record to a queue whose tail and head are at `P+3536` and `P+3544`.
- `kona_retrace_activate` arms a software timeout (`kona_timeout`, record +8 holds the handle) and sends the stream command `RETRACE_SEQID` (0x1e7) with the sequence number as its one payload word.
- The pipe processes the packet in order with the rest of its stream. The driver then waits for a video interrupt. `kona_video_intr` reads `HH_SEQID` (0x800248, HIP.h), and for every queued record whose number is not greater than that value, cancels its timeout and calls its callback with a 0 argument. If the timeout fires first, `kona_retrace_timeout` removes the record and calls the callback with a nonzero argument, and `kona_swap_complete` logs a message (cmn_err tag 2103; `kona_gsync_complete` uses 2104).

**Established** (`arm_retrace_seqid` 0x0c013f5c, `init_dg_board` 0x0c003d3c). The firmware turns `KONA_HP_RETRACE_SEQID` into six engine display-bus writes of 1 to 6 at address 0x7f, the last slot of the display-id mode table, and then a raster-bus register write of the sequence number to index 0x420 (`tbus_regwrite()`), so the number travels behind everything drawn before it; at start-up it writes 0 to the same index. The kernel reads the number back from `HH_SEQID` in the video-interrupt handler. **Inferred:** index 0x420 is the register `HH_SEQID` reflects, and the six writes push earlier display-bus traffic ahead of it. **Unknown: no shipped software or published source depends on it:** whether `HH_SEQID` changes when the write arrives or at the next vertical retrace, and what raises the video interrupt (bit 3). Routes tried: the kernel's retrace queue and handlers, the firmware's sequence-number path and its start-up, `irsaudit`'s interrupt helpers ([interrupts](#interrupts)), and the netlists.

### First tag, hardware tag and the activation window (6.5.21f and 6.5.30m `kona.a`, IP27)

**Established** (`kona_alloc_bdata`, `kona_edtinit.o` +0x38; `kona_retrace_setup`, `kona_retrace_activate`, `kona_video_intr`, `kona_retrace_timeout`, `kona_video.o`):

- The tag counter at `P+3528` has exactly two writers, `kona_retrace_setup` and `KONAschedmgrswapbuf`, each storing counter + 1 under the `P+3520` lock; `kona_nclops_bind` (+0x9c) only reads it, to snapshot it into the member's `P+5504`/`P+5508` pair. Nothing else in `kona.a` stores it. The pipe state comes from `kern_malloc(5544)` followed by `bzero`, so the first tag handed out after boot is 0. `KONAstart` does not touch it: it reads `HH_INTR_STATUS`, writes the interrupt mask, and sends `PIPE_SETUP` (0x1f1); no kernel path sends `RETRACE_SEQID` except the two swap paths.
- No kernel path writes `HH_SEQID` (it is read only, and `kona_video_intr` is its only reader in the driver).
- `kona_video_intr` completes a record when `rectag <= hwtag` (`sltu` at 0x185c stops the walk when hwtag < rectag). With a hardware value of 0, tag 0 is therefore complete on any video interrupt, whether or not its token has been processed.
- `kona_retrace_activate` does not take the `P+3520` lock. It calls `kona_timeout` first, stores the handle at record +8 (+0x78 from the node's private record) only afterwards, and only then sends the token. The video interrupt takes the lock, so it can run between `kona_retrace_setup`'s unlock and the handle store. In that case it finds handle 0, `kona_untimeout` has nothing to cancel, the callback runs and its slot is cleared; then `kona_retrace_activate` stores the live handle. When the timeout fires, `kona_retrace_timeout` tests only the handle (record +8), not the callback, and calls the callback slot unconditionally, which is the NULL call at the panic RA. This follows from the code and holds for any hardware value of `HH_SEQID` at or above the record's tag; for tag 0 a hardware value of 0 is enough.

**Inferred.** Firmware writes 0 to raster register 0x420 at the end of `init_dg_board` (ucode/arm1_functions.md), and 0x420 is the register `HH_SEQID` reflects (above), so a pipe that has run its start-up reads 0. The same driver code therefore completes tag 0 early on the first video interrupt, on real hardware as much as on a model; what differs is how often an interrupt lands in the short window between the unlock and the handle store, not whether the hole exists.

**Inferred** (video cause rate). The kernel increments the three frame counters in `kona_video_tick` at the top of every `kona_video_intr`, whatever is queued, and `RRM_GetVideoSync` returns one of them. The published OpenGL manual (007-2392-003, SGI_video_sync) says that counter is incremented on each vertical retrace, per field on an interlaced monitor, and runs as long as the graphics subsystem runs. So the video cause is raised once per retrace or field, not only on fields that honour a request. The cursor position (`KONApositioncursor` latches for `kona_video_intr`) is consistent with that and does not show per-field-with-request behaviour: a latched value is applied at the next interrupt, which must therefore keep coming with nothing queued. This is software and manual evidence, not a hardware measurement.

**Unknown.** What `HH_SEQID` reads after a hardware reset and before the firmware has run `init_dg_board`, and whether the hardware latches the register at the write or at the next retrace. *Test that would settle it:* on a real pipe, read 0x800248 (a single read-only host-window access) immediately after the pipe is released from reset and again after firmware start-up with no `RETRACE_SEQID` sent; then send `RETRACE_SEQID` with a value and poll 0x800248 across a vertical retrace to see whether it changes before the retrace. Needs real hardware; no document read states it.

`kona_swap_complete` finds each buffer pointer (`buffer+120`'s +160 field) among the entries listed at `P+184` (count `P+176`), and for every match writes data 2 to address 0x80 (the swap strobe, DG.h), then calls `rrmValidateBuffer`. `kona_gsync_complete` ends with `rrmValidateRetrace`; `KONAschedretraceevent` queues a bare retrace sequence with a callback taken from the driver's slot table. `kona_voc_intr` (the video-option interrupt, bit 9 of `HH_INTR_STATUS`) calls `rrmGenlockNotify(-1)`.

`kona_video_tick` at +0x1468 of `kona_video.o` (112 bytes, the same code in both kernels) is **established** as the per-frame bookkeeping of the video interrupt.
The video-interrupt service `kona_video_intr` calls it before anything else.
When the word at `P+144` is nonzero it first signals the share group whose pointer is at `P+152` (`sendgroupintr`).
It then adds 1 to the three frame counters at `P+124`, `P+128` and `P+164`.
Last, when either doubleword at `P+136` or `P+168` is nonzero, it calls `rrmValidateVideoSync` with `P`, which wakes the video-sync and swap-interval sleepers ([kernel.md](kernel.md)).

## Start-up and reset as the ARM firmware performs them

The video timing and combination handling the kernel never touches is in the ARM firmware ([ucode/arm1_firmware.md](../ucode/arm1_firmware.md), IRIX 6.5.30m); [ucode/tport.md](../ucode/tport.md) covers a second image with the same code. Labels as above.

**Established** (`init_dg_board` 0x0c003d3c, `DoDGRqstAutoInit` 0x0c004674). At start-up the ARM configures the display-generator board through the boundary-scan chain (`init_dg_jtag`), blanks every channel (`dgTempBlankAllChannels`), runs `dgAutoInit` and refreshes its configuration record (`dgUpdateConfigInfo`). `dgAutoInit` reads a stored combination from EEPROM (`eeprom_read`) and loads it (`dgLoadCombo`); a bad magic cookie, a combination too large for the scratch memory or a failed flash image falls back to the emergency backup format, as the messages in [ucode/tport.md](../ucode/tport.md) say. Not run when simulated. The 93 requests of `arm_video_cmd` that follow are in [ucode/dg_dispatch.tsv](../ucode/dg_dispatch.tsv).

**Established.** The run-time reset is the request `DoDGRqstResetRMBoards`: blank all channels, shut down the requesters on each present video output chip, wait, reset the raster boards' pixel chips ([rm.md](rm.md#reset-of-the-raster-boards)), restart the master video output chip, with the log lines "ResetRMBoards starting..." and "ResetRMBoards complete!". **Unknown: no shipped software or published source depends on it:** a display-generator reset register. No software writes one. The board is brought to a known state by writes alone: the scan-chain configuration, `DoDGRqstFetal`'s defaults for the XMAP, every present VOC, the video and gain DACs, the encoder and the option boards (`dgMake*Fetal`), then the copy-buffer strobe. The values are in [DG.h](../DG.h). Routes tried: `init_dg_board`, `DoDGRqstResetRMBoards`, `DoDGRqstFetal`, `DoDGRqstXServerVideoInit` (its 0xc000 strobe belongs to an option board), the kernel's `HH_RESET` paths ([xg.md](xg.md)), and `irsaudit`'s `base_xmap_init`, `dg_clock_setup` and `reset_dacs`. The last is a video-DAC sequence on 0x1711, 0x8000 and 0x1900.

## The far side of the video-controller port

**Established** (diagnostic netlists, `usr/diags/IR/data/dg4_2voc.netmap.Z` and the `fpln_*` set, IRIX 6.5.30m; pin names are SGI's). The 8-bit video-controller bus of the host-interface chip (`vc_data[8]`, `vc_fifof`, `vc_req_l`, `vc_rdy_l`, `vc_wr_l`, `vc_in_en_l`, `vc_out_en_l`, and `vint[2]` for interrupts) reaches one chip on the display-generator board, `fm0`, through its `dg4_dat[8]` pins (net `vc_data[0]` on `fm0:dg4_dat[0]`). `fm0` is a bridge, not a video chip: it presents a 16-bit local address (`loc_add[16]`) and 32-bit data (`loc_dat[32]`) to the chips of the board, whose nets carry the same names (`locadd`, `locdat`, `dac_dat`, `x_dat`, `v_dat`, `opt_data`), and drives the chip selects: `voc_sel_l[9]` (VOC chips), `xmap_sel_l`, `vdac_sel_l[8]`, `gdac_sel_l[5]`, `enc_sel_l`, `fast_sel_l`, `slow_rdy_in`. It also takes the swap handshake (`do_swap[10]`, `swap_rdy_in`/`swap_rdy_out`), per-VOC video requests (`vidreq_i_voc[10]`, `req[10]`, `req_ack[10]`) and the two interrupts `int1`, `int2` (nets `vc_int1_l` and `vc_int2_l`) and `voc_intr_l`. **Inferred:** the data the driver writes after `HH_VC_ADDRESS` ([above](#what-the-driver-can-reach)) is a local-bus access to one of those chips, `fm0` decoding the address into a select; this is what the "indirect port" is. The `HH_VC_ADDRESS` bit layout that picks the chip is **unknown: no shipped software or published source depends on it** beyond the address ranges in the table in [command-table.md](command-table.md) (section 6.2), which are the values software sends. Routes tried: the kernel, firmware, diagnostic and setup-tool address uses, and the board netlists (`dg4_2voc.netmap` and its variants list which pins each net joins, with no decode logic in them); the kernel's addresses 0x100-0x103 (cursor), 0x0b00 + 0x100n (channel blocks) and 0x0b02 + 0x100n (the DAC block's data port, which carries the DAC cursor position) are the values that decode.

Board composition, **established** (`dg4_2voc`): `fm0`, two VOC chips (`voc00`, `voc01`; the 8-VOC variant has eight), four XMAP chips (`xmap0`-`xmap3`), two DACs (`dac0`, `dac1`, four 8-bit pixels per colour per clock: `reda[8]`..`redd[8]`) and one video encoder (`encoder`, with `Zcvbs[8]` composite output); variants add `dacsamp`, `dvp`, `hdgvo`, `dplex` and `lvds` option chips. The VOC chip's outputs are exactly the 14 signals of the `.vof` sequencer ([ucode/dg.md](../ucode/dg.md)): `Zhsync`, `Zvsync`, `Zcsync`, `Zcblank`, `Ztrisync`, `Zfield`, `Zframe_st`, `Zimpreg_ld`, `Zxmapreg_ld` and `Zvideo_out`/`vact`, so the format files program a sequencer whose pins these are (**inferred** by the name match). The XMAP has a 40-bit pixel input, 17-bit colour-map address with 32-bit data, three 16-bit gamma-RAM addresses and 12-bit per-colour outputs to the DAC.

## The firmware's display-bus window

How the ARM firmware (`arm1.u`, IRIX 6.5.30m) reaches the display-generator board, from its own code. [DG.h](../DG.h) has the addresses and fields; [ucode/dg_access.tsv](../ucode/dg_access.tsv) lists every access whose address the code builds from constants (435 of them, written by [retools/tools/kona/dg_access.py](../retools/tools/kona/dg_access.py)).

**Established** (`DoDGRqstVCWrite` 0x0c012200, `DoDGRqstVCRead` 0x0c012250). Display-bus address A is ARM address 0x00600000 + 4 x A, one 32-bit word per address. The two requests let the host read or write any address. Every firmware access sits between two short delay loops (three iterations of a stack counter).

**Established** (the access table). The space divides by function family:

| Bus addresses | Used by | Chip (inferred from names and the fm0 chip selects) |
|---|---|---|
| display id | `arm_dispmode` (engine path): the DISPMODE mode byte at address = display id | per-display-id mode table |

The kernel's own accesses ([above](#what-the-driver-can-reach)) land in the same blocks with the same values: cursor registers 0x100-0x103, the swap strobe 0x80, and the video-DAC blocks, where the kernel's "4 then 2" on register 0 of block 0xb00 + 0x100n is the two-byte index 0x204 (the DAC's cursor control) and its 5 or 0 on register 2 is that register's value. **Inferred:** the kernel's `HH_VC_ADDRESS` value is this bus address.

### VOC registers

**Established.** Per-channel requests address VOC register r of channel id at 0x200 + 0x100 x id + r (id from payload word 0). [DG.h](../DG.h) lists the offsets 0x00-0x9d with the functions that use each and the fields the code builds; the names in brackets there are the `vof/` comment list's VOC register names matched by role. The sequencer is loaded through four of them, all by `DoDGRqstLoadFormat`:

- 0x06 (VOF control): bit 3 is set and cleared before the state table is written; bits 8-4 select a line type (0-31) or a signal (0-13) for the next accesses.
- 0x09: the state-table port. The firmware writes the state words one after another to this one address. **Inferred:** it auto-increments from the pointer bit 3 cleared.
- 0x0a and 0x0b: the selected line type's two words (edge mask for edges 0-31; length minus 3 in bits 30-18 and the edge mask for edges 32-49 in bits 17-0).
- 0x0c-0x13: edge slots of the selected signal. The firmware walks `EdgeDescArray` (0x0c00d140: 14 {name, slot count} pairs with counts 4, 4, 8, 6, 6, 2, 2, 2, 6, 2, 2, 2, 2, 2) and writes each signal's slots to 0x0c + slot. A slot word holds the edge position in bits 12-0, or 0x1fff when unused.

Option-board VOCs use ids above 7: `DoDGRqstLoadFormat` loads a format into the partners of ids 0x1e/0x1f, 0x2e/0x2f/0x30, 0x5e/0x5f/0x60, 0xc6/0xc7 and 0xc9/0xca by calling itself with the partner id. **Unknown: no shipped software or published source depends on it:** which option board each id pair belongs to beyond the function names (`dgConfigureHDGVO` for 0x5e). Routes tried: the firmware's request code and the X module's channel table.

## The LoadFormat request (383 words)

**Established.** On the host the X server module builds the request. In `kona.so` (`konad.so`, `konal.so` and `konas.so` export the same `vfmt*` functions with the same sizes) `vfmtReadKonaVideoFormat` (0x4319c0) opens the `.vfo` file, clears a 2020-byte format record, and calls seven readers at 0x42f280-0x4314d0 that fetch fields by name and pack them; the request is the record's 1532 bytes from offset 452. The unnamed function at 0x4fcfd0 (**inferred** to be `konLoadVideoFormat`, a name the module's section-name strings carry) fills the clock words and the vertical-phase words, then calls the display-command sender at 0x5341a0 with command 22 and 1532 bytes. The sender stores the command number at the command window + 0x34c0 (32 x 0x1a6, the `HP_VIDEO_CMD` token in the address), each payload word at + 0, then the sum of the command number and the words as a checksum. Two words of a screen record (+1200, +1204) divert the same call to two other functions. **Inferred:** they build an EEPROM image instead of sending (the module carries the section names `StoreEEPROMRqst` and `StoreEBFRqst` and the string "XVC_MAKE_EBF"), which is how a combination is stored for `DoDGRqstAutoInit`; `ireeprom` also carries the name "LoadFormat".

Each channel's description word (a record the module keeps per pipe channel, reached through word +500 of a 504-byte entry) decides some steps: bit 1 of its first word marks the channel that runs `SCHPhase`, **inferred** the encoder-capable channel; its word +24 is 1 on the path that prints the PAB pixel-mux messages, 3 and 4 elsewhere. **Inferred:** word +24 is the option-board channel type of the 6.5.5 the Kona kernel driver header 2 configuration record (none 0, PAB 1, VEG 2, DGO/GVO 3, DVP 4, DPLEX 5), from the value match and those messages.

The steps, in order (display-command numbers from [dg_dispatch.tsv](../ucode/dg_dispatch.tsv), payloads as the module stores them):

1. Command 30 (`DoDGRqstCursorPriority`): the VOC id and `CursorPriority`.
2. The format: the source channel's `.vfo` is read into the request (above), words 1, 26, 27, 275-278, 301 and 302 are set, and a channel that copies another one takes the source's name and date words. On a field-sequential channel that copies another, word 25 is cleared.
3. On channel 14 only, command 91 (`DoDGRqstVBOBCommand`, 42 words): 1, 161 and a sync byte, 0x80 | s << 4 for formats whose `TotalLinesPerFrame` is neither 525 nor 625, else 0x08 | s, with s = 3 when `VbobSyncSource` is set and 0 otherwise. The other 39 words are not written (stack contents). Word 275 of the format then becomes 1. **Inferred:** the byte selects the VBOB option's sync input and standard; the firmware passes it to the option over I2C ([display requests](#display-requests)).
4. Command 22 (LoadFormat), through 0x4fcfd0, which also computes the clock and genlock words.
5. Command 88 (`DoDGRqstDataFormat`): the VOC id, `DataFormat` (0-9 passed through, anything else 3) and a flag from the helper at 0x47ad00.
6. Command 86 (`DoDGRqstBufferParams`): the VOC id, `Letterbox`, and `SafeArea` clamped to 50-100 and multiplied by 65536.
7. Command 79 (`DoDGRqstVampire`, 7 words): the VOC id, the source's VOC id, the output width and height (`OutputSize`, or on channels 8 and 11 with `Letterbox` set a size from `SafeArea` and the input's aspect; the width rounded down to a multiple of 4, the height to an even number), `FieldLayout` (5 for a record marked stereo), and the two `FilterSize` values truncated.
8. Command 20 (Resize, [below](#the-resize-request-8-words)): the input rectangle with its y turned into a top line, 1, `FlickerFilter` == 0, 0.
9. Command 67 (`DoDGRqstPlacementRes`, 9 words): the VOC id, the x code (`PlacementRes` x 0 gives 0, 1 gives 4, 2 gives 160 when the channel is its own source and 4 otherwise), the y code (0 gives 0, 1 gives 1 or 4 by the same test), 4 when the channel copies another or its format runs two pixels per clock (word 25 of the format copy the channel record keeps at +716) and 0 otherwise, 1, `MaxSize` and `MinSize`. **Inferred** from the Combiner user guide's placement menu (Locked, Pixel, Tile; files store x 2 and y 1, its defaults Tile and Pixel): the codes are the panning step, 0 none, 4 pixels (one groupxel) or 1 line for Pixel, 160 pixels (one tile) for Tile.
10. Sync, for channels 0-7, 10 and 12: command 35 through the sender at 0x555cf0 (**inferred** `konSetOutputSync`): the auxiliary port gets horizontal TTL sync when `HSync` is 1 and composite TTL sync otherwise. With `TriLevelSyncEnable` set, each colour port whose `SyncComponent` entry is set gets composite tri-level sync and the others none; without it, each set entry gets composite sync and the others none. Select codes and refusals are in [DG.h](../DG.h) (`KONA_SYNC_*`).
11. Controls, through 0x548db0 (**inferred** `konSetControls`, attribute codes 5-11): `Gain` (command 33), `SetupEnable` (command 37, pedestal), `HPhase` (command 11), `VPhase` (command 13), blanking (command 31: 1 when `Blanking` is set or the channel copies another channel, except on channel 11, which sends `Blanking` alone), and on the encoder-capable channel `SCHPhase` (command 49) and `VPhase` again. Attribute codes 1-4 are per-colour gains the module refuses ("CTRLRedOutputGain( %g ) not supported").

**Established** (absence): `SyncSource` (+660), `SyncMethod` (+708) and `HalfLineInterp` (+336) are read but no step above sends them, and no other load of +660 or +708 exists in `kona.so` (the loads at +336 elsewhere are screen function-table calls). **Unknown: no shipped software or published source depends on it:** what the hardware would do with those three fields. Routes tried: every load of those offsets in `kona.so`, `ircombine`'s channel form (no control stores them), the Combiner user guide, `setmon`.

## Option-board channel slots and what the software refuses

First configuration only: the facts below are read from IRIX 6.5.30m binaries and the shipped `ircombine(1)` page. They say what the software expects of a pipe with an option board; they are not measurements of hardware.

### Slot numbers of the option channels

**Established** (`usr/gfx/ircombine` 6.5.30m, the channel-name parser at 0x10073e94-0x10074124: seven string compares in turn, each followed by the store of a constant). The `-channel` argument of `ircombine` names a slot of the 15-slot combination record ([above](#loading-a-combination-channel)). A decimal number selects slots 0-7 directly. The names select:

| `-channel` name | Slot | Compared string at |
|---|---:|---|
| `encoder` | 8 | 0x100aaa10 |
| `sirius` | 9 | 0x100aaa18 |
| `dvp` | 10 | 0x100aaa24 |
| `gvo` | 11 | 0x100aaa20 |
| `dplex` | 12 | 0x100aaa28 |
| `tvo` | 13 | 0x100aaa30 |
| `hdgvo` | 14 | 0x100aaa38 |

No other name is accepted (the parser stores -1). The manual page lists the same names: `gvo` is "the 601 serial digital video out board", `hdgvo` is "the tvo board combined with vbob acting as hdgvo" (`usr/share/catman/u_man/cat1/ircombine`, published with the shipped system). It also says that only the encoder, Sirius and GVO channels can run in dependent mode (`sourcechannel` naming another channel), that a channel's source channel defaults to itself, and that the GVO default format is `CCIR601_525_DGO`; those are **established (published)**.

**Established**, by agreement with facts already in this chapter: slot 12 has the 140 million pixels a second ceiling in the checker's rate table, the same figure the DPLEX rule file refuses at; slot 14 is the only slot that gets the VBOB command; slots 8 and 11 are the two that take the letterbox size; slot 10 has the 230 million escape. So the numbering above is the one the loader and the checker use, and the **inferred** option-board reading of slots 8-14 under [DAC limits](#combination-limits-infinitereality-video-format-combiner-users-guide-007-3279-003) is now named slot by slot.

A GVO combination therefore keeps the desktop on slot 0 (or 1) and puts the GVO video format in slot 11. **Inferred** from the slot parser, the man page and the combination files Discreet's installer builds (they pass `-channel gvo` and no source channel): the GVO channel runs independent, reading its own 720x486 rectangle from the managed area. **Unknown:** how the X server numbers the channels it reports through the video-control extension; see below.

### The hardware description and the option rules

**Established** (`usr/lib/X11/dyDDX/konal.so` 6.5.30m: `vfmtActualHWToKonaTarget` 0x13a77f0-0x13a7d10, the combination checker 0x13a8c30 called from `vfmtIsKonaCombinationValidForTarget` at 0x13a7e34). The target description the checker takes has, by word: +0 class, +4 raster-manager count, +8 pixel depth, +16 display channel count, +20 display revision, +24 option board type, +28 option revision. `vfmtActualHWToKonaTarget` fills it from the board information (ioctls 101 and 102) as follows: the class from the configuration record's `bdset` (0 stays 0, 2 stays 2, 6 becomes 3, anything else 1); the raster-manager count (1, 2 or 4); the depth; and the four words +16 to +28 from the record's `dg` block at record offsets 68, 72, 76 and 80 ([kernel.md](kernel.md#the-configuration-record-and-its-identity-words)): channel count, revision, option type, option revision. The option type codes the checker and `ircombine`'s hardware form use are 0 none, 1 Sirius, 2 TVO, 3 GVO, 4 DVP, 5 DPLEX ([setup-tools.md](setup-tools.md#the-hardware-description-and-the-channel-limit-ircombine-6530)).

Before it looks at any channel, the checker refuses these target descriptions, each with its own catalogue code and message (strings at 0x1511028-0x15111e8):

| Condition on the target | Message |
|---|---|
| class not 0, option 1 | Onyx2 does not support Sirius option board |
| class 0, option 3 | Onyx does not support GVO option board |
| class 0, option 5 | Onyx does not support DPLEX option board |
| class 0, option 2 | Onyx does not support TVO/HDGVO option board |
| class 2, four raster managers | Onyx2 Reality does not support 4 raster managers |
| class 0, option 4, channel count not 2 | DVP only works with 2 channel systems |
| option 3, channel count not 2 (any class) | GVO only works with 2 channel systems |
| option 5, channel count not 2 (any class) | DPLEX only works with 2 channel systems |
| option 2, channel count not 2 (any class) | TVO/HDGVO only works with 2 channel systems |

So a pipe whose record says eight channels and option type 3 fails every combination against the actual hardware. **Inferred** that the X server then declines the load: the module carries the text "combination %s not loadable on current hardware: %s" and an environment switch `XVC_RAMBO_LOADS` with the text "Ramboing invalid combination", but the routine that reaches them was not traced. The same module also prints "Warning: %d channels defined on a %d channel system!". The published statement that every option board sits on a two-channel DG5-2 ([above](#video-option-boards)) is the product-level reason; whether any DG5-8 with an option board shipped is **unknown** (the guides' tables list the options only on the DG5-2).

### Where the record's channel count and option type come from

**Established** (`arm1.u` `init_config`, [setup-tools.md](setup-tools.md#the-infinitereality-report-of-gfxinfo)): the firmware takes the display board's identity word: channel count is bits 18-16 plus one (record +20), the option type is bits 21-19 (record +24, numbered 3 TVO, 4 DPLEX, 5 DVP, 6 GVO on board sets other than 0; on set 0, 1 DVP and 2 Sirius, here called PAB in the firmware strings), and bits 4-1 go to +72. **Established** (`usr/gfx/gfxinit` 6.5.30m, `kona_info` 0x1000a538-0x1000a564, 0x1000a66c-0x1000a678 and the string loads at 0x1000a8b0-0x1000a8f4): `gfxinfo` prints its option line from that +24 field with the same numbering ("GVO option detected" for 6 on a nonzero board set, "TVO" for 3, "DPLEX" for 4, "DVP" for 5; on set 0 "Sirius video option detected" for 2 and "DVP" for 1) and "Display has N channels" from +20.

**Unknown: no shipped software or published source depends on it, so far as read:** which routine writes the `dg` block words at +68 to +80 that the checker reads, and how the checker's option numbering (3 GVO) relates to the firmware's (6 GVO). The two numberings differ, so a translation exists between the identity-word field at +24 and the option type at +76; the kernel header's option-channel names ([above](#loading-a-combination-channel): none 0, PAB 1, VEG 2, DGO/GVO 3, DVP 4, DPLEX 5) match the checker's, not the firmware's. Routes tried: the display requests of `arm1.u`, the kernel configuration-set ioctl (it copies the record whole), `kona_info`, `vfmtActualHWToKonaTarget`. Next route: the stores to record +68..+80 in `gfxinit` and in the `arm1.u` configuration builder. The X module's own count and option channels do not use that record: they come from the request-18 reply, which carries a third numbering, a bit mask with 0x10 for GVO ([below](#the-screen-record-and-the-option-channels-konalso-builds)).

First configuration only, and read from installed X modules, not measured on a pipe. Builds read: the installed 6.5.30m `konal.so` (sha256 `37c26ff4e3cdd6616389e21ca3698b18c642b3e8815d37900001329754b5f156`, addresses below), the 6.5.30 overlay build (`c57b4f113941a6f569eb7a163380f0e4a0699959ecb33a0dca326c62f7144346`), the 6.5.21 build from an installed system (`49f00ead3825f93fd8cd635a219445254694bf0773b8464ccfd69a0ec3e0da1b`) and the 6.5 base-media build (`2b13033aa6db990cb077cb45f38f2d574ae183ef0349b06b71844d71783c2dd8`). The same routine is in all of them, and in the `kona.so`, `konad.so` and `konas.so` modules of the installed 6.5.30m set.

**Established** (`konAttachXvc` 0x14d5bb0 calls the routine at 0x1474490 with the screen and passes its result to `XSGIvcScreenInit`). That routine builds the per-screen record the video-control extension reads. It first sends display request 18 (`DoDGRqstGetBoardConfig`, one payload word) and reads the type-6 reply of 20 bytes (the five-word record that `dgGetBoardConfig` fills; [firmware notes](../ucode/arm1_functions.md)). It logs the first four words as "DG board version %d (brd mask=0x%x, opt mask=0x%x, opts=0x%x)" (string 0x150d4e0). Those are, in order: 1, the channel mask (the word at offset 4 of the display-generator state), 0, and the option bit mask. `dgGetBoardConfig` builds that mask from the board's video-option number: on board sets other than 0, option 3 gives 0x40, 4 gives 0x20, 5 gives 0x8, 6 gives 0x10 and 7 gives 0; on set 0, option 1 gives 0x8 and option 2 gives 0x1 (`arm1.u` 0x0c00d29c-0x0c00d2e4). Option 6 is the "GVO option detected" value of the display identity word's bits 21-19 ([setup-tools.md](setup-tools.md#the-infinitereality-report-of-gfxinfo)), so a GVO board reports option mask 0x10.

**Established** (0x1474490-0x14772e0, 6.5.30m). What the routine does with those words:

- The channel count is the number of set bits among the low eight bits of the channel mask, plus one for each of the option masks 0x1, 0x2, 0x8, 0x10, 0x20 and 0x40 (a jump table at 0x150d520 over values 0 to 0x40), plus 0x16 for 0x4. Any other mask value (two bits set, or a bit outside the table) logs "illegal options present (0x%08x)" (0x150d628) and the routine gives up. The count is stored at record +4.
- The option mask picks the extra channel records, each carrying a physical id: 0x1 gives 0x1e, 0x8 gives 0x2e (0xc9 when a word two pointers down from the per-screen state, at +0x28, is nonzero; what that word is was not traced), **0x10 gives 0xc6 (the GVO channel)**, 0x20 gives 0xde, 0x40 gives 0x5e. The masks 0x2 and 0x4 stop the routine with "Vegematic detected but not yet supported!" and "22 channel option detected but not yet supported!" (0x150d750, 0x150d780). For GVO the code sets 0xc6 at 0x1476794, fetches that channel's configuration with request 19 (`DoDGRqstGetChannelConfig`) and reads its 0x4c-byte type-7 reply (0x14767d0-0x1476810) and stores 0xc6 in the new channel record at +0x1e8 (0x1476854). This confirms, from the X module, that the GVO channel's physical port is 0xc6 (the earlier reading rested on the VOC pair id alone).
- The record's fixed fields are written once: +0 is 0, +4 the count above, +8 0, **+0xc 2**, +0x10 1, +0x14 1, +0x18 -1, +0x2c 1 (stores at 0x1474868-0x14748e4; the 6.5.21 build has the same stores at 0x102456c-0x10245e4). Nothing in the routine reads a hardware value into +0xc.

**Established** (`ProcSGIvcQueryVideoScreenInfo`, `Xsgi` 6.5.30m, sha256 `45a61c37ce61cf808eb05a895022a6dbdd8fdcaaba75e497aa87c48b88385078`, 0x101246e0-0x101248f0; the 6.5.21 build, sha256 `82be9cad98a8d2013ed3f0e99001c83bf52375f44aa7cfb6ebc95e5061490de4`, has it at 0x1012d2b0). The reply's channel count is the word at +4 of the screen's video-control private (0x101247c8-0x101247cc), its flags word is the word at +0xc (0x101247d0-0x101247d4), the lock flag is the byte at +0x14 and the external-sync count the word at +0x2c. The graphics name comes from the board-type byte through `ddxGetBoardName`. So the flags a client sees are 2, "formats change via combination", on every pipe these modules drive. Bit 0, "formats change per channel", is not set by the DG5-2, the DG5-8, the option boards or the firmware's identity words: no hardware-reported value feeds either bit.

**Inferred:** that no other store changes +0xc after the routine returns. The 65 places in `konal.so` that load the private through the screen's private array (`vcScreenPrivateIndex`) were scanned for stores to +0xc and +4, and a scan of the whole text for stores to 0xc after an or-mask found none that touches this record; the scan is not a proof. Also **inferred:** that the object the routine returns is the one the server reads through `vcScreenPrivateIndex`. The store that installs it in that slot was not located (`XSGIvcScreenInit` writes it into the `XSGIvcScreens` array).

**Unknown:** which index the extension gives the GVO channel, and how the channel record's +0x1e8 reaches the `physicalID` word of the channel-info reply. The routine creates the option channel after the display channels (**inferred** from the order of the code), which would put the GVO channel after the two display channels of a DG5-2; the handler that fills the reply (`ProcSGIvcQueryChannelInfo`, `Xsgi` 0x10138660) was not traced.

## Genlock parameters (command 25)

**Established** (the combination loader, 0x4fb4c0-0x4fbd24). When the combination names an external sync format, the loader reads that `.vfo` ("failed to load external sync format %s!") and keeps four values in its combination state: the sync format's `TotalLinesPerFrame`, its `PFDVOFVerticalPhase`, its frame rate and its line rate. The first two feed LoadFormat words 295-298 (above). It then fills the 16 words of `DoDGRqstLoadGenlockParams`:

| Word | Value |
|---|---|
| 0 | 0 |
| 1-3 | timing values computed from the sync format's `FormatInfo_H_Sync` (bounded by three times itself), `TotalPixelsPerLine` and a factor 0.33, each multiplied by the ratio of 50 MHz to the sync format's pixel clock (50 MHz is the fastest `PFDClockSpeeds` entry) |
| 4 | 1 |
| 5 | `FormatInfo_H_BackPorch` / 4, scaled the same way, at most 8191 |
| 6 | `FormatInfo_H_BackPorch` / 2, scaled, at most 63 |
| 7, 8 | `PFDTable`, packed into two words by the format reader |
| 9 | `PFDInvert` |
| 10 | `PFDClockSelect` |
| 11 | `PFDComparatorPrecision` |
| 12-15 | 1, 1, 2, 7 |

The firmware handler keeps the words and `dgLoadChannelGenlockParams` writes VOC 0x30-0x32 from them ([display requests](#display-requests)); **inferred** from the `.vof` register list that 0x30-0x32 are `VOC_PFD_CONTROL` and `VOC_PFD_SEQUENCE_LO/HI`, which matches words 7-11 being the frame-detection fields. **Established** (absence): `PFDRegularLines` and `PFDValidTable` are read into the format record (+1996, +2012) and no code in `kona.so` loads them again. **Unknown: no shipped software or published source depends on it:** their role, and the meaning of words 1-6 and 12-15 in the hardware. Routes tried: the loader, the format readers and every load of the record offsets in `kona.so`, the firmware handler, the Combiner user guide, and the same loads in `setmon` (whose copy of this builder loads the same six fields) and `ircombine` (which carries the reader and loads none of them).


## The Resize request (8 words)

**Established** (`DoDGRqstResize` 0x0c00fe84, `dgResize` 0x0c00efc8). Word 0 is the VOC id. Words 1-4 are copied as a block to the channel record + 0x50 and, when word 7 is 0, also to + 0x60. Word 5 sets record flag bit 23 and word 6 bit 22. Word 3 rounded up to a multiple of 4 and word 4 are compared with the channel's output size (record + 0x80, + 0x84; "Illegal x output size %d, clipping to 2" below 2) to compute the scaler steps in 12.20 fixed point, written to VOC 0x90-0x9d, with VOC 0x02 written 0 then 1 around the update and 0x8f rewritten. When the channel has a vampire partner (record + 0xbc > 0) the request is repeated for every present VOC through `dgResizeVampire`.

**Established** (`dgResize` 0x0c00efc8, read at 0x0c00f0f0-0x0c00f11c): the request's width (word 3) is rounded up to a multiple of 4 (add 3, clear the low two bits) before the scaler steps are computed, and so is the channel's output width (record + 0x80); the heights are used as sent. A rendered size therefore moves in steps of 4 pixels across, which is the 4-pixel increment the recollected Performer behaviour ([published-sources.md](published-sources.md)) steps by. Neither `dgResize` nor `ChannelRect` (which forwards its four numbers unchanged) sets a floor near 320 by 320: the firmware clips an output width below 2, and in all 66 enabled channels of the shipped combinations the minimum size (`MinSize`, command 67) is 4 by 1 for the 63 RGB channels and 640 by 486 for the three encoder channels. **Unknown: no shipped software or published source depends on it:** the 320 by 320 figure; it is the posted tool's own policy. Routes tried: `dgResize`, `DoDGRqstResize`, `ChannelRect`, and the `MinSize` field of every shipped `.cmb`.

**Inferred**, from the firmware and from libGLcore's `ChannelRect`, which sends `a0, a1, a2 + a4 - 1, a3, a4, 0, 0, 1`: words 1 and 2 are the source rectangle's x origin and top line (the caller turns a bottom-left y into a top line), words 3 and 4 its width and height, words 5 and 6 two mode flags that libGLcore always clears, and word 7 = 1 means "do not make this the channel's default rectangle". **Unknown: no shipped software or published source depends on it:** what flag bits 22 and 23 change in the scaler; no caller sets them. Routes tried: libGLcore's `ChannelRect`, the X module's resize calls and `dgResize`.

## XMAP registers, memories and the fast list

The XMAP registers beyond the diagnostic's list, read from `irsaudit` (IRIX 6.5.30m, register helpers at 0x1013afe4-0x1013c5xx and `vcWrite`/`vcWriteFastlist`/`vcRead` at 0x1014071c-0x10140bac) and the firmware. Numbers are XMAP register n at bus address 0x100 + n. Established for the numbering: the firmware's request that turns the substitute colour off (`DoDGRqstDisableDiagXmapColor`, 0x0c008120) stores to ARM address 0x600414, which is bus word 0x105 (the ARM window is 0x600000 plus four times the bus address), the register this section calls 5. The register-by-register uses below carry their own grades. [DG.h](../DG.h) has the fields.

**Established.** Both programs end every group of XMAP register writes by writing 1 to register 4 (`xmap_copybuffer`, `dgForceXmapCopyBuffer()`). `irsaudit` also writes 4 after moving the cursor (`load_cursor_cntrs`). Register 5 turns the substitute colour in 6 and 7 on and off. Register 8 takes the XMAP number 0-3 in the read-back sequence of `TEST_xmapmem`: the address goes to 0x11, the chip to 8, 1 to 4, then 0x12 is read. Register 9 is 0 after the firmware's start-up and 2 after `irsaudit`'s. It also takes the X module's `KONA_HP_X_LOADXMAP_CONFIG` word, 1 when a window is created and 0 when one is destroyed, which `arm_x_loadxmap_config` (0x0c03dc44) writes to bus address 0x109 through the engine. Register 0x10 is written 0 at start-up and nothing else touches it; nothing touches 0xa. **Inferred**, from the function name and the XMAP pin names in the diagnostic's pin list (`xmap_force_curs_pos`, `xmap_rd_id_match`): 4 bit 0 copies double-buffered registers into use and bit 2 forces the cursor position; 8 picks the chip that answers a read; 0x12 is read data. **Unknown: no shipped software or published source depends on it:** what 9, 0xa and 0x10 do beyond these values. Routes tried: the firmware, the kernel, the X module, `irsaudit`'s XMAP tests and its pin list.

**Established** (`vcWriteFastlist`). The diagnostic reaches 0x118-0x11f, the XMAP's indirect memories, in one of two ways. It can write `HH_VC_ADDRESS` with the register number or-ed with 0x10000, then `HH_VC_DATA`. It can also send a raster-bus word: 0x041 in bits 63-52, the bus address in bits 47-32 and the data in bits 31-0 (`bloTbusWrite`). The plain `vcWrite` uses `HH_VC_ADDRESS` without bit 16. The firmware reaches the same registers through the engine (`mgesi_VCbusWrite`). **Inferred:** bit 16 of `HH_VC_ADDRESS` selects the in-band path the XMAP calls the fast list, whose chunk size is register 0xf (`DoDGRqstFastlistChunksize`).

| Register | Use (established) |
|---|---|
| 0x118 | address for the data ports below: memory address and select bits, or a channel or display id |
| 0x119 | colour-map and cursor data; consecutive words go to consecutive addresses (`irsaudit` `load_cmap` writes one address then n words) |
| 0x11b | gamma data (`load_gamma_table`, `arm_x_loadgamma`) |
| 0x11c | display-id table data (`arm_x_loadxmap_did`) |
| 0x11d | channel set-up, channel number in 0x118 (`define_xmap_channel`): bits 3-0 gamma page, 4 external gamma, 5 no gamma, 6 alpha to blue, named by the function's debug line |
| 0x11e | once after a gamma load (`irsaudit`, data 0) and after every firmware load |
| 0x11f | data 0 after a colour-map or cursor load (`irsaudit`, once; the firmware three times, then 0x11e, then three more) and three times before a new address (`change_fastlist_addr`) |

**Inferred:** 0x11f moves earlier list entries through without storing anything, and 0x11e ends a load. **Unknown: no shipped software or published source depends on it** beyond the order above. Routes tried: both programs' loaders, the X module and the pin list.

## Colour maps and gamma tables

**Established** (`irsaudit` `load_gamma_table` 0x1013bbd4, `load_full_gamma` 0x1013bf80, `make_gamma_addr_legal` 0x1013c214). A gamma load writes 0x118 with entry bits 11-0, colour bits 13-12 (0 red, 1 green, 2 blue), page bits 17-14 and a flag in bit 18. It then writes the entries to 0x11b, then 0x11e once and 0x11f three times. `load_full_gamma` fills 4 x 1024 entries per colour and page. `make_gamma_addr_legal` masks the address to 19 bits and clears bit 13 when the colour field is 3, which gives colour 1 (green) (`irsaudit` 0x1013c228-0x1013c2c4). Below bit 18, it copies bits 9-8 or 11-10 into bits 1-0 (or bit 8 into bit 0), chosen by bits 11-9 and the caller's mode. **Inferred:** page and entry are the 16 address bits of each of the three gamma RAMs (`xmap_gam_ad_red`, `_green`, `_blue` in the pin list), and the low-bit copy reflects which pixel bits feed the gamma index at narrower pixel sizes.

**Established** (`kona.so` `konStore24DCColors`; `arm_x_loadgamma` 0x0c03d6fc). `KONA_HP_X_LOADGAMMA` has two forms.

- **XMAP form**, for each colour of each X colour cell that changes: four words. They are the address (a per-visual base + 2 x pixel index + 0x1000 x colour), the count 2, and then the 12-bit value twice, which is the top 12 bits of the 16-bit X colour. The firmware writes the address to 0x118, streams the counted words to 0x11b through the pass-through counter, then writes 0x11f three times, 0x11e once and 0x11f three times. Each colour index fills two consecutive gamma entries. The module also keeps the values in a 1536-word shadow, three blocks of 512.
- **External form**, first word 0xdeadfeed: sent by `setmon` (the function at 0x10027da0, reached from its video-request switch) and by `kona.so` (the unnamed function at 0x498ff0). Both take a 4096-entry table of 12-bit values per colour, pick every (n / 1024)th entry, and send 0xdeadfeed, 1024 and then 1024 words packed red << 20 | green << 10 | blue, each the 12-bit value shifted right by 2. The firmware clears bits 11-8 of bus address 0xc104 and sets bits 8-7 of 0xc006. It writes the words to 0xf000 + i, the last one through the last-word port, then restores 0xc006. By inference, a 1024-entry 10:10:10 table in the external gamma RAM behind the option-board window. The 6.5.5 board-interface configuration record has an `extgamma` size field, and `init_dg_board` warns "external gamma forced to internal for down rev XMAPs".

`KONA_HP_X_LOADCMAP` (`arm_x_loadcmap` 0x0c03d5e8) is the XMAP form with data port 0x119 and any count. Counts above 0x200 go in 0x200-word pieces, and the same seven writes to 0x11f and 0x11e follow.

## Cursor memory

**Established.** The cursor image goes through 0x118/0x119 like a colour map. `irsaudit`'s `load_cursor` is its colour-map loader with 260 words, and the firmware's `arm_x_loadcursor` (0x0c03d9c4) moves 1 + 260 words. `kon_initCursorCaches` in the X module builds 39 cache entries of 16 bytes, so cursor slots 0-38 sit at slot x 260. The crosshair address 9884 equals 39 x 260 - 256. The crosshair's colour block, at address + 0x100 where `arm_x_loadcursorcolor` (0x0c03daa0) puts it, is therefore the four words 10140-10143 just past the last slot, and the 256 image words it would cover overlap slot 38's image but are never loaded for it. **Inferred:** the cursor lives in the XMAP's external colour-map RAM. That RAM's address bus (`xmap_cmap_addr`) and the cursor glyph-base register are both 17 bits wide.

**Established** (block layout, from the X module's builders and `DoDGRqstDiagCursorFromImage` 0x0c0081a0). There are 64 rows of four words. Each row holds plane A as 64 bits (pixel 0 in bit 31 of the first word) and then plane B. A pixel's value is A << 1 | B. Words 256, 257, 258 and 259 are the colours of values 3, 2, 1 and 0, each 10:10:10. The diagnostic request builds the planes from bit 1 and bit 0 of each image pixel, and it writes its colours 3, 2 and 1 followed by a stack word it never sets. The X module puts the source bitmap in plane A and the mask in plane B. So 256 is the foreground (or the module's third colour), 258 the background, and 257 the foreground again, for source-without-mask pixels. **Inferred:** value 0 is transparent and word 259 is never shown, since no sender sets it. **Unknown: no shipped software or published source depends on it:** which of the four words the crosshair draws with, because the module loads the same colour into all four. Routes tried: the X module, the firmware's cursor and diagnostic handlers, `irsaudit`'s cursor helpers (`easy_xmap_cursor`, `load_cursor_cntrs`).

## The video requester

**Established** (`dgConfigureVideoRequester` 0x0c00e324, `dgLoadVocIwsc` 0x0c00e104; field names from the `.vof` comment list, [ucode/dg.md](../ucode/dg.md), matched by content). The VOC fetches its channel's window from the framebuffer in tiles of 160 pixels by 8 lines. Pixels are counted in groupxels of four, so a tile line is 40 groupxels. Per channel, the firmware writes:

- the input window: screen width in groupxels - 1 (VOC 0x03), origin x / 4 and y (0x04), size in groupxels and lines (0x05);
- the line requests: a request word holds tiles - 1 in bits 2-0, groupxels - 1 in bits 13-3, a valid bit 14 and a repeat count in bits 22-15. A window that fits one request of at most 8 tiles (4 on board type 2) fills only the END word (0x49) and zeroes START (0x47) and MIDDLE (0x48). A wider one is split into a START request from the window's first groupxel to its tile boundary, a MIDDLE request of whole tiles repeated, and an END request;
- the pan, (x mod 160) / 4, in VOC 0x4a bits 5-0, and x mod 4 in bits 7-6 (`dgConfigureVideoRequester` reloads x at 0x0c00e45c after its divide by 160). **Inferred:** bits 7-6 pick the first pixel inside the first groupxel, so the window can start on any pixel;
- per field f, the first tile address (tile row x tiles per row + x / 160) in bits 19-7 of VOC 0x50 + f and 0x58 + f, and the field pattern in 0x60 + f;
- the requester control VOC 0x44, with bits from LoadFormat words 26 and 27 ([DG.h](../DG.h)), and the tiles per framebuffer row in 0x45.

`irsaudit` prints the same three-request split ("requesting START (%d,%d) (%dx%d) tileaddr %d tilecount %d groupxels %d", MIDDLE with a repeat, END) in its own requester code. **Unknown: no shipped software or published source depends on it:** which control bit is pixel size, dither, transfer size and transfer alpha. Routes tried: the firmware, the `.vof` list and `irsaudit`'s format checks ("XferSize 12 on non-RGB", "XferSize 10 && XferAlpha").

**The pixel format on the video bus.** **Established:** the transfer size is 10 or 12 bits per component with an optional alpha transfer, and 12 is allowed only for RGB (`irsaudit`'s format checks). The 40 wires into each XMAP come from four IMP output lanes of 8 bits ([rm.md](rm.md#display-and-scanout-from-the-raster-boards)). **Inferred:** one 40-bit word per XMAP per clock, enough for a 10:10:10:10 or a 12:12:12 pixel. **Unknown: no shipped software or published source depends on it:** the bit order on the wires. Routes tried: the netlists, the firmware's requester code, `irsaudit`'s video tests (which compare CRC signatures, not wire values) and the `.vof` list.

## Interrupts

**Established** (`irsaudit` `vdEnableDgInterrupts` 0x10130c98, `vdCheckDgInterrupts` 0x10130d90; kernel `kona_video_intr`, `kona_voc_intr`). The diagnostic enables exactly bits 3 and 9 of `HH_INTR_ENABLE` (0x208, after `HH_INTR_INFO` = 0x8000 and `HH_GINTR_INFO` = 0x30000). It reports bit 3 as "got video interrupt" and bit 9 as "got voc interrupt", then writes the status back and 0 to `HH_INTR_ACK`. The kernel treats bit 3 as the per-frame video interrupt (retrace queue, cursor, swaps) and bit 9 as the genlock notifier. In the firmware, `VOC_CONTROL` interrupt bits are set only by `dgLoadChannelGenlockParams` (bits 5-4 set, bit 6 cleared). **Inferred:** from the `.vof` field order, those are the external-sync-loss and external-frame interrupt enables, which makes bit 9 the VOCs' own interrupt line, raised by genlock events. The master VOC's status bit 7 pulses once per frame (`dgSyncWithMasterVoc` waits for it to rise and fall). **Unknown: no shipped software or published source depends on it:** the exact condition behind bit 3 and its timing within the frame. Routes tried: the kernel handlers, the firmware (no code arms an interrupt on `fm0`), `irsaudit`'s video tests and the netlists.

## What the published manuals add

SGI's own manuals describe the display generator from the user's side. They give no register, but they fix limits and meanings that the firmware and the combination files only imply. Labels follow [published-sources.md](published-sources.md): **established (published)** is a first-party statement about the shipped product; where a binary read in this chapter agrees, the line says so. Page numbers are PDF page indexes of the stored copies in [docs/sources/](sources/README.md); the printed page of each manual is lower by its front matter (14 for the combiner guide, 10 for the DPLEX guide, 12 for the HD GVO guide and the DVP2 specification, 18 for the Onyx2 and Onyx 3000 owner's guides).

### Channels and boards (owner's guides, IR4 addendum)

- **Board names (established, published).** The display generator is the DG5, one board per pipe, always in the rightmost slot of the pipe. DG5-2 has two high-resolution channels. DG5-8 is a DG5 with the VIO5H daughterboard and has eight, monitors 0 to 7 on 13W3 connectors. The other options all sit on a DG5-2: GVO (two CCIR 601 serial outputs on BNCs), TVO or HD GVO (two TMDS outputs) and DPLEX. Every DG5 carries an S-Video output, two composite outputs (RCA, BNC), a StereoView connector, genlock in, genlock loop-through and swap ready. 007-4264-002 PDF p. 61-62 (table 2-1), 007-3454-005 PDF p. 64-65 (tables 4-1 and 4-2), 007-4525-001 PDF p. 2. Agrees with the board-composition line under [Start-up and reset](#start-up-and-reset-as-the-arm-firmware-performs-them) (two voc chips in `dg4_2voc`, eight in the 8-VOC variant) and with `NIC_channels` ([above](#firmware-data-and-board-identification)).
- **VIO5H adds six channels, eight in all (established, published; the "five" is a prose slip, inferred).** The Onyx2 guides say the VIO5H "outputs five high-resolution video channels" (007-3454-005 PDF p. 67; the rack guide repeats it on PDF p. 80). Against that: the same guides' connector table gives "Monitor 0 through 7" on 13W3 connectors for DG5-8/VIO5H (007-3454-005 PDF p. 65), their figures label monitors 0 to 7 on the DG5-8 panel (007-3454-005 PDF p. 67; 007-4264-002 PDF p. 66), the DG5-2 base board has monitors 0 and 1, and the IR4 addendum says the daughterboard "adds six monitor connectors, for a total of eight" (007-4525-001 PDF p. 2). Eight minus the base two is six. The shipped software knows no five-channel board: the hardware form of `ircombine` has a "Number of Channels" menu with two entries, and `twoVOC` and `eightVOC` (0x100566b0, 0x10056360) store 2 and 8 into the form's hardware description (the word at +16 of the record at +120 of the form). The "five" is the only count that fits neither the connector list nor the software; why the sentence says it is **unknown**.
- **Maximum scan-out (established, published).** The deskside guide gives the board's maximum output bandwidth as about 300 million pixels a second, with a 1920 x 1200 at 66 Hz SuperWide monitor as the default; more than two monitors must fit inside that total (007-3454-005 PDF p. 65). The combiner guide is more specific (next section). The guide's own arithmetic for two monitors (188 Mpixel/s) is not reconciled with 300; **unknown** which of the two figures it describes.
- **Encoder and VTR channel (established, published).** The packet bus carries processed video to one of the video output channels or to the NTSC or PAL encoder (VTR channel); a video output controller feeds a three-DAC array (007-3454-005 PDF p. 65). Agrees with the encoder commands of [Display requests](#display-requests).
- **Texture and frame memory per board set (established, published).** See [rm.md](rm.md#what-the-published-manuals-add) for the memory and configuration figures.

### Combination limits (InfiniteReality Video Format Combiner User's Guide, 007-3279-003)

- **Channels and tiles (established, published).** A channel takes pixels from a rectangular area of the framebuffer, two to eight areas per pipe, each with its own timing; channels may overlap (PDF p. 15). The framebuffer is addressed in tiles 160 pixels wide and 8 high and whole tiles are transferred on each line; per-pixel panning costs one extra tile per line (PDF p. 33-34); a 1280 pixel width takes exactly eight tiles and 1281 takes nine (PDF p. 41). This **confirms** the tile size that [DG.h](../DG.h) takes from the code (`KONA_TILE_WIDTH`, `KONA_TILE_HEIGHT`) and the `KONA_CMB_TILE_W` rounding that was only inferred from `allocatedSize`.
- **Placement modes (established, published).** The X placement choices are locked, pixel or tile (tile is the default for X, pixel for Y; PDF p. 35). This is the user-level meaning of the `PlacementRes` codes of command 67 (0 gives 0, 1 gives 4, 2 gives 160 in the list under [Loading a combination channel](#loading-a-combination-channel)): **inferred** locked, pixel and tile, in that order.
- **Pixel depth classes (established, published).** The managed area is allocated in one of Small, Medium, Large or X-Large pixel depth, or "Deepest" (the default), which picks the deepest class that fits the managed area on the installed RM boards. The framebuffer is a fixed amount of memory re-cut into more or fewer pixels; deeper pixels cost a little rendering and video bandwidth; changing depth needs graphics restarted, and a configuration the hardware cannot hold (for example too few RM boards) falls back to the emergency combination (PDF p. 42-44). Agrees with the `Medium pixel depth` line of the `gfxinfo` sample below.
- **Swap rate (established, published).** Every channel of a combination, option boards included, must have the same swap rate, because the display subsystem does its housekeeping (cursor, resampling parameters) for all formats at once, at field, frame or multi-frame boundaries. Rates within about 2 percent count as equal; 525-line formats imply 60 Hz and 625-line formats 50 Hz; 120 Hz stereo and 180 Hz field-sequential formats swap at the 60 Hz frame rate (PDF p. 61-62). Gives the user-level reason a combination whose formats disagree is invalid.
- **Video transmission bandwidth (established, published).** The path from the framebuffer to the video subsystem carries about 290 million pixels a second of 10-bit RGB or 12-bit field-sequential video and about 210 million of 10-bit RGBA or 12-bit RGB; each channel's stream has one type and precision, different channels may differ, and the total is independent of the number of RM boards (PDF p. 62-63). Adding RM boards adds fill, not video bandwidth, and spreads the refresh overhead (PDF p. 21, 64). The bandwidth and "reduced fill" scales of the combiner are percentages of these two (PDF p. 21).
- **Video bandwidth check in the shipped checker (established for the arithmetic, inferred for the meaning of each sum).** `vfmtIsKonaCombinationValidForTarget` (`kona.so` 0x428590-0x428fec) walks the 15 channel slots; for every enabled slot it takes the maximum size (channel +288, +292) as the channel's width W and height, and divides the height by the first field's line skip plus one (+2508; a format with the old-style stereo flag at +1160 halves the height instead). The swap rate R is the format's swaps per frame (+1156) times the channel frame rate (+304) in single precision; fields per swap is the format's field count (+1248) divided by the integer part of R over the frame rate. A channel in pixel format 0 or 4 counts 32 bits a pixel and one in 1-3 counts 42. Its tiles per line are (W + the origin x mod 160 + 159) / 160, plus one when the placement code (+328) is 1 or the aligned tile count differs from the plain one, and its requests per line are tiles over `MaxTilesPerRequest` (+696, forced to 4 on a class-2 target), rounded up. A channel that is its own source (+260 equals its slot) adds three terms, each times fields per swap and R: requests per line times height; 160 times tiles times bits times height; and W times height scaled by ((fastlist chunk size at +548 / 31) x 9 + 102) / 100, so 1.0229 for the shipped chunk size of 1.0. Any enabled channel whose output size is smaller than its input size in either axis marks the combination as resampled. The base rate is 62.5 million when anything is resampled and 75 million otherwise; the capacity is four fifths of it, and the three sums are held against: capacity x 0.01 (x 1/165 on class 2), capacity x 160, and four times the base, each cut by 8 percent (one minus 8/100). The routine reports each sum as a percentage of its capacity and refuses the combination, with "Video bandwidth exceeded" (catalogue code 2), when the largest is above 100. The raster-manager count never enters; a further cycle total built from the pixel-depth resolver and the helper at 0x427ce0 is only printed. The data-bit capacity is 8.832 billion bits a second on the 60 million side (0.92 x 160 x 60 million), which is 276 million 32-bit pixels or 210 million 42-bit pixels a second, close to the published 290 and 210 million ([published-sources.md](published-sources.md)); that agreement is **inferred** support for the reading, not an independent measurement. [scripts/combination_bandwidth.py](../scripts/combination_bandwidth.py) is a port of the three sums with the field offsets above; it reads a `.cmb` and the `.vfo` files it names. It accepts all 26 shipped combinations on a class-1 target, the heaviest at 90.3 percent (`1280x1024+1920x1080_72`, pixels) and the 8-channel ones at 54.6 (`8@640x480_60`) and 85.4 percent (`8@800x600_60`). The posted mix of two 1024x768 and six 640x480 channels at 60 Hz, built into the layout of `8@640x480_60`, reads 48.0 percent requests, 77.5 data bits and 76.0 pixels: accepted, as the post says. The same script puts the boundary for eight channels of those two sizes between three 1024x768 plus five 640x480 (96.2 percent data bits packed, 89.5 with each origin on a multiple of 160; accepted) and four plus four (101.5 percent in both layouts; refused); eight 1024x768 channels read 149.6 and four 1280x1024 channels 114.0 percent. On a class-2 target (four tiles per request, a smaller request capacity) four shipped combinations fail on the request sum, at 113.8 (`1280x1024+1920x1080_72`), 110.2 (`3@1280x1024_60`), 180.8 (`7@800x600_60+NTSC`) and 172.2 percent (`8@800x600_60`); the other 22 pass on all four classes. **Unknown, not needed by any shipped tool:** the real hardware's actual limit; the script reproduces the software's check, not the bus.
- **DAC limits (established, published).** The DACs of channels 0 and 1 stop at 220 million pixels a second and the other six at 170 million; the manual says to give the fastest formats to channels 0 and 1 (PDF p. 63). A channel's output can be larger than its framebuffer rectangle because of dynamic resampling (zoom). The image-quality paper gives the same 220 Mpixel/s DAC figure (specs/sgi-onyx2-image-quality-whitepaper-20000613.html).
- **DAC limits in the shipped checker (established, five binaries).** The combination checker in `kona.so` is a static routine at 0x4294b0 (it calls the exported `vfmtUpdateFormatInfoInCombination` at 0x429320 first, and `vfmtIsKonaCombinationValidForTarget` calls it; objdump labels its body with the nearest exported name). It walks the 15 channel slots, skips a slot whose `Enable` word (channel +676) is zero, and for each enabled slot k multiplies the format's `TotalLinesPerFrame` (channel +1252, format-block word 21) by its `TotalPixelsPerLine` (+1256, word 22) and by the channel's `FrameRate` float (+304). That is the format's pixel clock with blanking included, the figure `FormatInfo_PixelClock` stores. The product is compared as a float with a 15-word table of whole numbers in `.data` (0x58a3f0 in `kona.so`): 220, 220, 170, 170, 170, 170, 170, 170, 170, 170, 230, 170, 140, 220, 220 million, indexed by slot number. A rate above its slot's entry fails with the message "%s channel format too fast for this channel" (display-catalogue code 36); a rate equal to the entry passes. Slot 10 has one escape: a rate above 230 million but below 305 million (the float at gp-26948) passes when the target's board class (its first word) is not 0, so on board set 0 the 230 million ceiling is hard. `konal.so` (0x196458) and `konad.so` hold the same fifteen values at the same relative place. `ircombine` (table 0x100a6248, compare at 0x10084ea8-0x10084f20) and `setmon` (table 0x1003ff78, compare at 0x1001b3b8-0x1001b430) carry their own copy of the checker with the same field offsets, the same slot indexing, the slot 10 escape and code 36, so a combination refused in the X module is refused in both tools. Slots 0 and 1 are the two fast DAC channels of the manual's 220 million figure, slots 2-7 the 170 million ones, slots 8, 9 and 11 also 170, slot 12 140, slots 13 and 14 220. **Established:** slots 8-14 are the encoder, Sirius, DVP, GVO, DPLEX, TVO and HDGVO channels, in that order ([slot numbers](#slot-numbers-of-the-option-channels)); the table itself does not name them. Applied to the 74 shipped `dg4/vfo` formats ([display-formats.md](display-formats.md)): the fastest, `2048x1120_72` at 219.969 million, sits 31 thousand pixels a second under the 220 million entry, and no format exceeds it; the seven formats above 170 million (`1280x1024_114s` 199.363, `1280x1024_120s` 209.856, `1920x1080_60` 180.001, `1920x1080_72` 215.999, `1920x1200_60` 185.738, `1920x1200_66` 218.296 and `2048x1120_72`) are therefore accepted only in slots 0, 1, 10, 13 and 14, as the manual's advice to give the fastest formats to channels 0 and 1 implies. The shipped 1920x1200 timing (2560 by 1292 total) reaches 220 million at 66.52 Hz, so 66 Hz is the highest whole rate the check lets through on slots 0 and 1 and a 67 Hz version (221.6 million) is refused. The three shipped colour-field-sequential formats are far under every entry (`640x480_180q` 82.368, `640x512_180q` 87.437, `1280x1024_180qi` 160.884 million), since their stored line counts (1560, 1656 and 3270) already hold the three colour fields of a frame. The 222 million figure in the recollected posts ([published-sources.md](published-sources.md)) belongs to a field-sequential format none of the shipped files provides; a format at that rate would be refused in every slot but 10 (230 million), which on a class-0 target is itself the hard ceiling.  Routes: disassembly of the `kona.so`, `ircombine` and `setmon` routines, the table bytes of all five binaries, the format reader at 0x42f280 (it stores the field count at block +80, the total lines at +84 and the total pixels at +88 of the format block that starts at record +452), and the pixel-clock column of the shipped formats. The `vfc` rule files carry no such limit (their clock limits are the 12-35 and 13-36 MHz compiler figures above), so the format compiler cannot reject these formats; the check runs when a combination is loaded.
- **Pixel formats (established, published).** Per-channel output pixel format: RGB10 (default), RGBA10, RGB12, a 24-bit Z and a colour-field-sequential format "FS"; only the Sirius Video channel really outputs RGBA10, any other channel puts the 10-bit alpha on the blue port when "Alpha On Blue" is on (and then gamma is bypassed for that channel); Z output lets a second channel carry depth for virtual-set masking (PDF p. 30-31, 38-39). Dither adds a fixed noise pattern before truncating to the output depth (PDF p. 31). Compare the `PixelFormat` and `AlphaOnBlue` rows of the [channel record](#loading-a-combination-channel).
- **Gamma and gain (established, published).** The factory gamma is 1.700 for each component; a two-channel board uses one gamma table (gamma map 0) for both channels, an eight-channel board can have per-channel gamma when the global gamma box is off (PDF p. 36-38). Gain runs 0.0 to 10.0 (default 1.0), is rounded to what the output stage can realise, and a mid-range 6.0 gives 700 mV peak white (PDF p. 39). The `Using Gamma Map 0` line in the `gfxinfo` sample below shows the same map index.
- **Cursor priority (established, published).** The cursor shows on one channel at a time; priority is 0 to 255, a lower number wins; on a tie the channel that last showed the cursor keeps it, and if neither did, the lower channel number wins (PDF p. 32). The smaller-number-wins rule agrees with `kona_determine_cursor_channel` ([Choosing the cursor channel](#choosing-the-cursor-channel)); the "last shower keeps it" rule is what `kona_determine_cursor_channel` does on an equal-priority tie ([Choosing the cursor channel](#choosing-the-cursor-channel)); only `kona_get_xy_channel` takes the lowest index.
- **Sync (established, published).** Composite sync on green is always present; the alternate sync port carries horizontal or composite sync (composite is the default); R, G and B each have a sync-enable box; tri-level sync is available on the colour ports but not on the composite port; pedestal ("setup") is off by default and must stay off for PAL and Japanese NTSC (PDF p. 31, 35-36). Phase: horizontal phase is a floating-point value, positive values delay the genlocked channel, vertical phase runs from 0 to lines minus 1 (PDF p. 35). Sync source is internal or the genlock input, with a sync format file; with none given the lowest-numbered valid channel's format is used (PDF p. 44). These are the user-level names of the `SetupEnable`, `TriLevelSyncEnable`, `HSync`, `HPhase`, `VPhase` rows of the channel record and of [Genlock parameters](#genlock-parameters-command-25).
- **Textport channel and persistence (established, published).** The combination names one channel for textport output, which shows boot information; `setmon -x` or "Save to EEPROM" stores a combination that takes effect at the next graphics start; `setmon -n` or `ircombine -dest active` loads it at once, and `setmon` rejects an invalid combination that `ircombine` can still save (PDF p. 22, 40, 42, 45). Agrees with `DoDGRqstAutoInit` reading the stored combination from EEPROM.
- **Emergency combination (established, published).** If the stored combination cannot be loaded at boot (for example it exceeds the hardware), the software runs a built-in one: one RM board, two channels, no option boards, a single `1280x1024_60` format on channel 0, editable only by SGI (PDF p. 64). Agrees with the fallback in `DoDGRqstAutoInit` ([Display requests](#display-requests)) and names the format it falls back to. **Established** (`arm1.u`): the built-in block at 0x040402c8 holds a LoadFormat request for `1280x1024_60.vfo` (1280x1024 active, 1680x1065 total, 60 Hz), loaded when the stored combination's magic word is wrong or its load fails; [ireeprom](setup-tools.md#ireeprom) shows how `-c` takes that path.
- **Target hardware facility (established, published).** The combiner can validate a combination for a hardware set it does not run on; the choices are the graphics type (Onyx InfiniteReality, Onyx2 InfiniteReality, Onyx2 Reality), 1, 2 or 4 RM boards, 2 or 8 channels, and the option board (Sirius Video, DVP or GVO) (PDF p. 45-46). This is the manual's list of the board-configuration cases `init_config` keys on (`NIC_channels`, `NIC_rm_config`, `NIC_dgopt_type`).
- **Encoder channel (established, published).** The encoder channel replaces channel 1, can be a window on another channel's pixels or the whole channel (a roaming window saves bandwidth), and is a pass-through for pixel clocks above 120 MHz, where only a pannable NTSC or PAL sized region is recorded (PDF p. 47-48). "Dependent" mode adds no bandwidth or fill, "independent" mode does (PDF p. 21).

### Video option boards

- **Option set (established, published).** On Onyx2 the options appear in the combiner as dedicated channels: Sirius Video (live video in, with alpha, chroma or generated keys), the Digital Video Port (DVP) and the Graphics to Video Option (GVO) (007-3279-003 PDF p. 16-17). The VFC rule files name the same option hardware strings: `Presenter`, `DDO2` and `GVO` (007-3402-003 PDF p. 83), matching the `dg4_ddo_gvo.def` rules of [ucode/dg.md](../ucode/dg.md).
- **DVP and DVP2 (established, published).** Both stream the framebuffer's pixels in raster order, one pixel per pixel clock, 36 bits wide (12 bits per RGB component, no alpha) through a CrayLink-type cable from a daughterboard on the DG5, as 45 differential 5 V PECL pairs: 36 data, two clock pairs (half-rate clock and its quadrature), CBLANK, CSYNC, VSYNC, FIELD and VOC_SWAP, reserved pairs, a receiver-power sense line and an I2C pair. CBLANK leads the data by three pixel clocks. VOC_SWAP is a catch-all that can be set to line start, field start, frame start, tri-sync, the requester-enable window (`vdrc_en` gated by the swap latch), or held high or low; the default is "first frame after a swap". Added latency is 0, 2 or 3 pixel clocks for clock ranges 2.5-60, 60-120 and 120-230 Mpixel/s (the same three break points in both documents). DVP is programmable from 2.5 to 175 MHz and designed for 230; DVP2 from 2.5 to 175 MHz guaranteed, designed for 260, and uses a separate high-speed clock above 220 Mpixel/s, selected by `ircombine`. Timing signals come from the video format compiler. 16-bit luminance goes out on RED[11:0] and the top bits again on GREEN, with the four low bits on BLUE[3:0] and a copy of the top eight on BLUE[11:4]; it needs a 16-bit luminance X visual. The DVP2 block diagram names an ICS1522 video PLL, an MC12439 high-speed clock, ECL shift registers and a Philips PFC8584 I2C controller. DVP2 differs from DVP in connector footprint, timing signals and clock limits. 007-3651-001 PDF p. 13-24, 007-3594-001 PDF p. 13-19. Compare: `DoDGRqstDVPMult2Freq` (command 90) writes 0x3400 and 0xcd00 ([Display requests](#display-requests)); **inferred** that it selects the DVP2 high-speed clock, because the published rule is "clock above 220 Mpixel/s uses the second clock" and the request name says "multiply by two frequency". The I2C controller of `i2c_init` is **inferred** to be the PFC8584 on this board for the same reason; `read_edid` is the VESA DDC use the specification names.
- **DPLEX (established, published).** DG5-2 plus a DPLEX daughtercard, IRIX 6.5.3 or later (the datasheet says 6.5.2), Onyx2 only, not in older Onyx InfiniteReality systems, not on a pipe that has a DVP2 (also called DDO2, DPLEX is code-named DDO3). Pipes are daisy-chained by 40-pin LVDS cables, digital video "out" of one to "in" of the next, no ring and no terminators; the pipe whose analog output drives the display does not use its out connector. All pipes must be genlocked, from pipe 0 or from house sync, by a 75 ohm chain with the last loop-through terminated (for more than four pipes through a distribution amplifier), and swap-ready cabled together with BNC T pieces and no terminators. The combiner sets the sync source to "Loopback Ch1" on the master and "External" on the others; every pipe runs the same format, 31 to 110 MHz pixel clock, 8 bits per component. Each pipe contributes at least one frame, switching on frame boundaries, in a user-programmable sequence, with no hardware master; added latency is N-1 frames for N pipes. The block diagram has a display sequence controller, a digital video output controller, a swap controller and a host interface. 007-3849-001 PDF p. 11-19, 41-44, 51-54 and 007-4264-002 PDF p. 61 (the board table), datasheet 2003 (specs/sgi-2003-dplex-datasheet.pdf). The register addresses `DoDGRqstDataFormat` uses for DPLEX (0x8001, 0xe300, 0xe500) have no published counterpart; the manual gives none. The two documents disagree on the pixel clock range and the IRIX release. **Inferred** (IRIX release): the guide's 6.5.3 is the requirement of the shipped option, because the datasheet is the August 1998 edition (document 2003 8/98) and says DPLEX "is scheduled to begin shipping by the end of calendar 1998" (specs/sgi-2003-dplex-datasheet.pdf PDF p. 1 and 2), a pre-release statement, while the guide is a 1999 publication (007-3849-001 PDF p. 13). The 6.5.2 and 6.5.3 release notes would establish it; the Library holds neither (its earliest IRIX update guide is 6.5.7). **Established** (`usr/gfx/ucode/vfc/rules/dplex.def`, 6.5.30; [ucode/dg.md](../ucode/dg.md#format-compiler-rules-usrgfxucodevfcrules)): the DPLEX rule file raises "format too fast for dplex" for any format whose frames per second times total pixels per line times total lines per frame (the product the `.vfo` files store as the pixel clock, [display-formats.md](display-formats.md)) is 140 MHz or more, and it has no pixel-rate floor of its own: its only lower limits are the 12 MHz system clock and 13 MHz DAC minimums, which no tool reads back. The shipped ceiling is neither document's: the user's guide supports 31 to 110 MHz (007-3849-001 PDF p. 13, 45, 52), which lies inside it, and the datasheet's "up to 175 MHz" (specs/sgi-2003-dplex-datasheet.pdf PDF p. 2) lies above it, so a format of 140 to 175 MHz that the datasheet promises is refused by the 6.5.30 rules. **Inferred:** the guide's 110 MHz is the supported range and the rule file's 140 MHz a hard refusal above it; the datasheet predates shipment (August 1998). The 31 MHz floor has no counterpart in the rule file. The IRIX release the DPLEX first needs (6.5.2 in the datasheet, 6.5.3 in the guide) is **unknown** here: the 6.5.30 files carry no release gate for it, and the release notes of 6.5.2 and 6.5.3 are not held.
- **HD GVO / TVO (established, published).** A TMDS Video Output daughterboard on a DG5-2 sends digital pixels as two TMDS links (A and B) to the SGI Video Breakout Box, which makes serial HD and SD video: a subset of ATSC table 3 (at least 720p and 1080i at 59.94 Hz) and CCIR 601 with NTSC or PAL timing, with alpha or key out (needs the RGBA10 pixel format) and genlock from the box's timing output into the board's genlock input. It needs IRIX 6.5.10 with a patch, cannot share a pipe with DVP2, and `ircombine` configures 1920 x 1080 for it by default. 007-3868-001 PDF p. 13-26; the box's firmware needs flashing for DG5-2/TVO (007-4636-001). The `HDGVO_*.vfo` files of [display-formats.md](display-formats.md) are its formats. The original GVO is the same idea with two CCIR 601 BNC outputs from the board itself (007-3279-003 PDF p. 17; 007-4264-002 PDF p. 61-62).

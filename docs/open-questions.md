## Display back end: cursor, display ids, colour path, gamma pages, overlays (2026-11-07)

Five questions from an emulator back-end design (InfiniteReality2 on Onyx2, one pipe), each previously inferred from one window-manager recording. Answered from the 6.5.30m X server modules (`kona.so`; `konal.so` and the others share the readings), the visual tables in `konavis.so`, the display microcode (`arm1.u`), `irsaudit` and the published papers. Grades follow the rest of this file. One correction up front: the binaries contain no field of the display id "bits 7:2" (question 2), and the recording's order for the cursor (question 3) holds only for the DAC cursor.

**1. Cursor glyph bit pairs, crosshair, DAC cursor channels.**

- *Established: the requester's pairing is right.* Colour builder at 0x531f50 in `kona.so` writes three 10:10:10 words into the glyph block: word 257 from the cursor's foreground (halfwords +4, +6, +8 of the cursor record), word 258 from the background (+10, +12, +14), word 256 from a separate third-colour record when its byte +6 is set, else a copy of the foreground. Word 259 is never written. The image has two 64-bit planes per row, source in plane A and mask in plane B, pixel value A<<1|B ([dg.md](dg.md#cursor-memory)), and the colour words are those of values 3, 2, 1, 0. So source-and-mask (both bits) shows word 256 (the third colour, or the foreground when none), source-only shows 257 (foreground), mask-only shows 258 (background), neither shows 259. *Inferred:* neither is transparent, because no sender ever loads 259. This pins the layout both X-side builders produce; that the chip indexes the words as 256 + (3 - value) is read from the diagnostic's builder of the same block (`DoDGRqstDiagCursorFromImage`), not from the chip.
- *Established: what the crosshair is made of.* It is cursor mode 1 in XMAP register 0x103, hot spot (32, 32), colour block at address 9884 + 0x100 (words 10140-10143, just past the 39 glyph slots); no image is ever loaded, and the module writes the same colour into all four colour words. *Unknown: its shape* (arm lengths, thickness, full-screen or 64 x 64). Nothing in the binaries or the published papers draws it; the (32, 32) hot spot and the +32 position bias suggest a 64 x 64 extent, which is a weak *inference*.
- *Established: DAC cursor channels.* There are eight DAC blocks at 0xb00 + 0x100 n. The kernel enables the cursor on exactly one: the channel that owns the cursor gets 5 in indexed DAC register 0x204 and every other block gets 0, and in that case XMAP cursor mode 0x103 is written 0, so the XMAP cursor and the DAC cursor are alternatives, never both. A channel is DAC-capable when its rectangle record has valid = 2 (valid = 1 is the XMAP cursor), and only channels 0-7 can be; the owner is the lowest priority number whose rectangle holds the pointer, with the previous owner retained on a tie ([dg.md](dg.md#choosing-the-cursor-channel)). The position goes in as four bytes (x low, x high, y low, y high) to indexed registers 0x200-0x203, scaled to the channel's output size minus the DAC hot spot. The DAC image and colours are loaded by display request 56 (263 words). *Unknown:* the layout of those 263 words and what each bit of the value 5 does.

**2. Display-id window kinds.** *Established: no, the set is larger, and "bits 7:2" is not a field the software defines.* Two separate per-id words exist.

- The id table entry (XMAP register 0x118 = id, data to 0x11c), built by `konValidateMode` (0x4601e0) and `konChangeDIDCmap` (0x44f1d0): bits 23:7 colour-map base (the colour map's slot number << 7), bits 6:3 number of index planes minus one (a visual's plane count, capped at 12 when a per-screen flag is set, then decremented; 0 stays 0), bit 2 "lum" (visual flag 0x20000), bit 1 "grey" (0x10000), bit 0 unused. The firmware's textport initialisation writes id 0 = 0x80050 (base 0x1000, field 6:3 = 10, bits 2:0 clear; the textport colours are loaded at 0x1000 + index, index below 0x1000).
- The mode byte (`DISPMODE`, written to bus address = id): bit 0 back buffer shown (the kernel rewrites bits 0-1 at each swap), bit 1 stereo (main planes), bit 2 non-colour-index RGB below 24 bits ("RGB"), bit 3 colour-index or luminance, bit 4 "DC RGB" (direct colour), and for overlays bits 3:1 hold the code 2, or 3 when double-buffered and starting in the back buffer (plus 4 for an underlay) with bit 0 set for non-RGB overlays and bit 4 set for opaque ones. 30-bit RGB10 main windows send no bits. Established from the case split in `konValidateMode`; what the XMAP does with bits 2-4 stays unknown ([opengl.md](opengl.md#display-modes-x_loadxmap_did-and-the-load-display-mode-resource-manager-request-1017)).

The complete set the X server can create, from every visual set in `konavis.so` (small, medium and large, all three pixel-depth revisions): main-plane colour index at 8 and 12 planes (also 15- and 16-plane luminance/grey), direct colour and true colour at 8, 12, 24 and 30 planes, stereo variants, the popup (2-plane colour index, fixed id 63), overlay colour index at 2, 4 and 8 planes in transparent and opaque forms (ids 64 and 65), and a 15-bit RGB overlay in both forms (ids 66 and 67); overlay window ids run 64-95 and main-plane ids 0-62 (`konInitDIDState`). No shipped visual is an underlay although the code handles one. Id values therefore fit in 7 bits.

*Where the id sits in the pixel: established, two layouts.* `kon_drawDid` (0x4715c0) builds the 64-bit foreground that paints an id into the framebuffer from the id split as low nibble and the rest. With the larger ("imp9") pixel layout the nibble goes to bits 6:3 of the high word and the remaining 12 bits to bits 19:8 of the high word, plane mask likewise; with the "imp8"/"imp8c" layout it goes to bits 12:9 and 25:14 of the low word. The layout follows the board's pixel depth (the visual set chosen at screen start). This split (nibble plus a 12-bit part at bit 4 up) may be what the recording's "bits 15:4" shows.
*Where a CI8 index sits: unknown.* The X server hands the 8-bit pixel value to the pipe as the plain foreground (masked to the depth); nothing translates it, and the placement inside the framebuffer pixel is done by the raster hardware. What is known is that the id table's index-width field is 7 for an 8-plane visual and 11 for a 12-plane one. Note that a 24-plane RGB visual also gives 7 (23 and 15 = 7) unless the per-screen cap applies, so the width field alone does not tell colour index from RGB; the mode byte does.

**3. Colour map, gamma, cursor order; 10 to 12 bits.**

- *Colour map then gamma: inferred, solid.* The XMAP has a 17-bit colour-map address with 32-bit data and three 16-bit gamma-RAM addresses with 12-bit outputs to the DAC (netlist, [dg.md](dg.md)); the published display description says colour index is looked up in a 32K map and that "colour component width is maintained at 12 bits through the gamma table outputs".
- *Cursor: the recorded order (cursor last) is right for the DAC cursor only.* The DAC cursor is inside the video DAC, after the 12-bit gamma outputs (*established*: the XMAP drives the DAC). The XMAP cursor is different: the published paper says the cursor "is also injected" at the pixel de-serialise / de-interleave stage, ahead of the colour map, and its colours are 10:10:10 words held in the colour-map RAM, in the same form as colour-map output. So *inferred*: the XMAP cursor replaces the pixel's colour before gamma, and gamma applies to it. *Unknown:* whether gamma is bypassed for it; the published note that cursors and pop-ups "appear in their true colours" is about field-sequential video only.
- *Colour-map entries are 10 bits: established* (the server loads the top ten bits of each 16-bit X colour, red 29:20, green 19:10, blue 9:0). *The gamma index is 12 bits: established* (`irsaudit` loads 4096 entries per colour and page). *Widened to 12 before gamma: inferred, padding rule unknown.* The diagnostic's address-legalising step copies bits 9:8 or 11:10 into bits 1:0, which suggests replication of the top bits, and the external-gamma loader treats the same index as 10 bits (it takes every fourth of 4096 entries).

**4. Gamma pages past the first. Established.** Pages are selected per video channel, not per pixel or id. Display request 15 stores a map index 0-15 in the channel record (-2 means no gamma) and the channel's XMAP set-up word (register 0x118 = channel, data to 0x11d) carries it in bits 3:0, with bit 4 external gamma, bit 5 no gamma, bit 6 alpha-to-blue (`dgResolveXMapChannelFormat`, `DoDGRqstChannelGammaMap`). On the load side the gamma address is entry 11:0, colour 13:12 (red 0, green 1, blue 2; the module advances 0x1000 per colour), page 17:14, flag bit 18. `konReloadAllGammas` uses address 0 for a map of kind 0, (map << 14) + 0x40000 for kind 1, and the external 1024-entry form for kind 2. *Unknown:* what flag bit 18 does, and which maps are kind 0 or kind 1. Published: a two-channel board uses one gamma table; an eight-channel board can have one per channel.

**5. Overlay and popup composition.**

- *Established (the software contract):* three layers. Each overlay or popup visual advertises a frame-buffer layer (main 0, overlay 1, popup 2) and, for the transparent forms, a transparent pixel of 0; opaque overlays (visual flag 0x40000) advertise none. The X server reserves colour-map entry 0 in overlay and underlay colour maps. The id's mode byte carries an "opaque" bit (0x10) for those visuals.
- *Inferred:* popup over overlay over main, with overlay or popup pixel value 0 letting the lower layer through and any other value replacing it; an opaque overlay replaces the whole window. This is the advertised X contract; the hardware choice is read nowhere in software. *Unknown:* whether the per-pixel zero test happens in the XMAP from the mode byte (likely, given the opaque bit) and how a window's overlay planes pair with the id of the main window beneath. The 15-bit RGB overlay's transparency rule is also unread.

## Vertex-bus contents, colour interpolation and window-coordinate rounding (2026-11-07)

Three questions from an emulator back-end design (InfiniteReality2 on Onyx2, one pipe), answered from the 6.5.30m geometry microcode listings ([ucode/ge_listing/](../ucode/ge_listing/)), the diagnostic's vertex writers ([rm.md](rm.md#primitive-set-up-happens-in-the-pixel-generator)) and the published papers ([published-sources.md](published-sources.md)). Grades: established (read from a binary or stated by a paper), inferred (reasoned, reasoning given), unknown. No hardware was used. The geometry engines only store floats; the float-to-fixed step and everything after it is chip hardware with no program, so the chip-side parts of these questions can only be bounded here.

**1. Does a perspective term cross the vertex bus, so texture is perspective-correct? Inferred: yes, as the last of four texture words per vertex; whether that word is 1/w or q/w (or 1/q) is unknown.**

- *Established (paper).* Section 2.5 says the bus carries "only screen space vertex information" and that the fragment generators assemble strips and fans and compute slopes. Section 2.6 says the scan-converter and texel-address ASICs perform "color and depth interpolation, perspective correct texture coordinate interpolation and level-of-detail computation". The technical report (perspective correction subsection) says the raster subsystem does the per-pixel correction for textures and fog. So the raster side must receive per-vertex data to correct with, and no source names the field.
- *Established (listings).* Every vertex-output module (the triangle, line, point and multisample-point output modules) stores texture words 0xf, 0x10, 0x11 and 0x12 of the vertex record to four vertex-packet slots (control addresses 0xd1, 0xd2, 0xd3, 0xd4), beside window x, y, depth and colour ([ge_compute.md](../ucode/ge_compute.md#triangle-output-udrawtris)). Those four words are written only by the textured screen-space routines (`mmo_ToScreenSpaceInvQ` at 0x1113 and its variants `lSC3` 0x1121-0x116c, `lSC5` 0x11c1, stores at 0x1165-0x1168 for words 0x12 and 0xf, and the 0x10 and 0x11 stores around 0x1169-0x116c). The plain divide `mmo_ToScreenSpace` (0x10c9, loop `lSC1` 0x10d4) writes only window x, y, z (words 0x23-0x25) and keeps 1/w to itself. The textured routines run reciprocal seeds and Newton-Raphson steps on both w and q (`lSC3` 0x114b-0x1152, seeds 0x114f-0x1152), run the s, t, r, q inputs through the texture matrix first (32 multiply-adds, 0x1121-0x113c), and scale the results with 1/w before they store words 0xf-0x12.
- *Established (diagnostic).* The raster-bus texture-coordinate packet the diagnostic builds (`tbTextureCoord`, `irsaudit` 0x1013ecf0, code 10; second set `tbTextureCoord1` 0x1013eda0, code 11) is four words: three integers then one single-precision float. Callers pass 0, 0, 0 or 0x800000 for the integers and 1.0 (0x3f800000) for the float.
- *Inferred.* In the output modules the subtracts that touch window x, y and texture words 0xf, 0x10 and 0x11 do not touch word 0x12, which is only moved (and stored predicated). That matches three words converted to integer form and one word left as float, as in the diagnostic's packet. The float is therefore the perspective term, which has to stay a float because its range is large and which is 1.0 in the diagnostic's flat tests. Which of 1/w, q/w or 1/q it is: unknown. The listings compute all three ingredients and the store pipeline's nine-word delay makes the register tracing ambiguous; the raster side that consumes it is not readable. For an emulator the observable consequence is that texture on a textured vertex is perspective-correct and an untextured vertex carries no w of any kind.
- Fields of the packet for x, y, depth and colour: unchanged from [rm.md](rm.md) (command nibble, unsigned 12.8 x and y, 32-bit depth, four 13-bit colours); the vertex bus has no separate 1/w field for untextured primitives.

**2. Is colour interpolated linearly in screen space or perspective-corrected? Inferred: linear (strongest for untextured primitives).**

- *Established (paper).* The scan-converter text above names perspective correction for texture coordinates only; the technical report names textures and fog. Colour is described as interpolated ("color and depth interpolation"), with no correction named.
- *Established (listings).* No textured or plain screen-space routine reads the colour words of the vertex record (words 0x1b-0x1e): there is no `D=0x1b-0x1e` operand in the screen-space routines. The only arithmetic on colour in the output path is one multiply per component by the colour scale (4095.9998 for RGBA, set by `mgeb_RGBA_Mode`; `lDI3` 0x28ba-0x28c1, `r95` = 0x33 stores). So the geometry side never pre-divides colour by w, the usual way to make a linear interpolator perspective-correct.
- *Inferred.* An untextured vertex carries no w, so its colour cannot be corrected and is interpolated linearly in screen space. For a textured vertex a perspective term is present, and this data cannot exclude the raster side using it on colour too; nothing published or read says it does, and the paper's wording implies it does not. Treat colour as linear and fog as perspective-corrected (technical report).

**3. Rounding of window x and y to 12.8, and whether z is clipped.**

- *Rounding: resolved (2026-11-08), see the architecture-plan section, question 2, below.* The microcode never makes the fixed-point value. It stores window x and y as floats (record words 0x23 and 0x24, written by the divide at 0x115f-0x1164, 0x10e6-0x10eb) after one subtract of a scalar kept in control word 0xc4 (loaded into register 1 at 0x2893 in the triangle module and used with `r148` = 1 at 0x28ac and 0x28b0 and in the other drawing modules); the paper says "a dedicated float-to-fix converter follows each core" (geometry engine section). The converter has no program and the diagnostics compare chip signatures, not converted words. Nothing sets word 0xc4 in the program (no immediate-addressed store; the ARM writes control memory at other addresses), so whether the subtract is a plain origin, or a bias that makes the engine's own adder do the rounding, is not settled. So truncate, round-to-nearest and floor are all consistent with what can be read. Route not tried (needs a running pipe or the chip documentation): feed the converter a value with a known fraction and read the vertex-packet word. The published 8 x 8 sub-pixel accuracy (technical report) describes sample locations, not the converter. Keep the VPro choice as the working default and mark it unknown for this family.
- *Z clip: inferred, z is clipped; correct the "no z clip" default.* Established: the vertex-transform microcode (starting at 0x1218; stores 0x123f-0x124a) computes six plane distances per vertex into special registers 0x10-0x15, and the post-clip flag recompute in the polygon clipper (0xef8f-0xef98) names them: registers 0x10-0x13 are the guard-band-scaled w minus x and minus y (the four guard-band factors sit in control words 0x71-0x74), registers 0x14 and 0x15 are the unscaled w plus the matrix's clip z and zero minus that clip z (question 3 of the numbered list in the architecture-plan section below corrects the earlier w-minus-z reading). The hardware turns their signs into clip codes (special register 0x0d) and the clipper's driver calls its Sutherland-Hodgman plane step for each plane a code names. So near and far are geometric clips against the exact planes, while x and y are clipped only at the guard band and the raster stage scissors the rest (the second-chance path at 0x10b8). The window depth that leaves the divide paths is also passed through a minimum (0x10ea, 0x1163), a clamp from above only. Caveats, all inferred: the composite matrix replaces the projection's third row with (z - w) / 2 ([ge_compute.md](../ucode/ge_compute.md#matrix-maintenance-umatrixs)), and with that third row the two z tests cut the exact near and far planes (question 3 of the architecture-plan section below); the clip codes come from fixed hardware not readable here; a user-clip-plane mode may differ.

Where this lives for the next reader: the packet fields are in [rm.md](rm.md#primitive-set-up-happens-in-the-pixel-generator), the routines in [ge_compute.md](../ucode/ge_compute.md#perspective-divide-and-viewport-uscreen2s).

1. **Set-up arithmetic. Inferred for the reduction, unknown for the rest (rechecked 2026-11-08, no new evidence).** Vertices arrive as unsigned 12.8 (established), the report's 8 x 8 sub-pixel accuracy implies the 1/256 fraction is cut to a 1/8 grid inside the pixel generator (inferred); the plane-equation widths and the reference point are not stated anywhere read ([rm.md](rm.md#primitive-set-up-happens-in-the-pixel-generator)).
2. **Window-coordinate rounding at the float-to-fix converter. Resolved for the engine side (2026-11-08): the engine subtracts the constant 49152.0 (control word 0xc4, set once at start-up by `ge.S` 0xb21e), which puts x and y on the 1/256 grid by float rounding; only the converter chip's bit extraction stays unread ([command-table.md](command-table.md#77-window-and-clip-set-up-request-token-0x1f3-eleven-words)).** Earlier text: The microcode stores floats after one scalar subtract and the converter has no program; truncate, round and floor all fit ([vertex-bus section](#vertex-bus-contents-colour-interpolation-and-window-coordinate-rounding-2026-11-07), question 3).
3. **Far-plane range cut by the z clip. Settled: the far plane is a real cut at clip z = 0; arithmetic established, the zero register and the hardware sign-to-code step inferred.** The composite matrix gives clip z' = (z - w) / 2, which is -w at the near plane and 0 at the far plane (established, in the composite-matrix rewrite). The earlier reading that the second z distance is w - z' (a cut at z = 3w, leaving the far plane to the depth clamp) was wrong. Trace of the vertex-transform microcode at 0x123b-0x1244: the unit-1 add at 0x123b (0x123c for the second vertex) is w, stored to record word 0x1a; the add at 0x123d (0x123e) is z', stored to word 0x19. Register 0x14 is the add at 0x1242 (0x1244 for the second vertex) of those two forwarded results, `r128` = 0x19 taking the w result seven words back and the z' result five back (0x1244 takes w from register 7): 0x14 = w + z' (established, forwarding rule of [ge_isa.md](../ucode/ge_isa.md#operand-ports-and-result-forwarding)). Register 0x15 is the unit-1 subtract (M = 0x462, low part 0x62) at 0x1241 (0x1243), whose port 1 is register 0x1e (`r148` = 0x3df, bits 9-5) and whose port 2 forwards the z' result four words back (`r128` = 0x28; five back, 0x29, at 0x1243): 0x15 = register 0x1e - z', and port 1 minus port 2 is established. Register 0x1e reads as zero (inferred, from the copy idiom that adds it to finished sums in the matrix-multiply routines, [ge_isa.md](../ucode/ge_isa.md)), so 0x15 = -z'. The post-clip flag recompute in the polygon clipper (0xef93-0xef94) forms the same pair after clipping: 0xef93 is an add (M = 0x6e0) of the record's z (word 0x19, read through address register 6) and a previously loaded word, 0xef94 a subtract (M = 0x6e2) of that loaded word from register 0x1e (`r148` = 0x3c0); that the loaded words are w and z respectively rests on the selector-3 rule (inferred), and the trace at 0x1218 carries the conclusion alone. So the tests are w + z' >= 0, which is clip z >= -w (the exact near plane), and -z' >= 0, which is z' <= 0, clip z <= w (the exact far plane). The rewritten third row is what lets the far test compare against zero instead of w. The far plane is therefore a geometric clip, not left to the depth clamp. Still inferred: that register 0x1e is zero in the clip units, and that the clip hardware turns a negative distance into a code bit (special register 0x0d is hardware not read here); the z-clip caveat in the vertex-bus section is settled by this entry.

13. **The 0x1f3 words 0-10 and the 0x1f4 halfwords. Established for 0x1f4; 0x1f3 data flow established word by word, a few role names inferred.** 0x1f4 carries the display-bank halfwords at +18 of the draw and read buffers. 0x1f3 is the window and clip setup request and takes eleven words. Per word (E = established from the instructions, I = inferred role name):

    - Words 4-7 -> 0x86c, 0x86e, 0x870, 0x872 (E, from the scissor-resolve step: clip rectangle x origin, y origin, width, height; the far corner is origin + size - 1). Together with the user scissor at 0x844-0x850 (when the flag at 0x76c is set) and clamped to the screen extent at 0x40/0x42, they give the resolved scissor halfwords 0x87a-0x881 (x0, x1, y0, y1; E).
    - Word 8 -> 0x874 (E: its difference from the old value is added to six single-byte fields at 0x1d6-0x1db, and the buffer-configuration handler seeds 0x1d6 from this halfword plus one at 0x0c013294-0x0c0132a0; I: a per-window framebuffer address base). The six bytes are the six 6-bit address fields that the same handler packs into register 0x1c0b (below), so word 8 shifts every buffer's base by the change in its value.
    - Word 9 -> 0x876 (E: window id; 0-0x3e used as is, 0x40-0x5f as a masked group, 0x3f takes the special value id 0x800 with mask 0x800, anything else prints a bogus-id message and is treated as 0x3f). It is encoded into register 0x1c06 as id bits 1-12 and a mask in bits 13-24 (0x0c0184a8-0x0c0184dc; E).
    - Word 10 -> 0x878 (E: a flag; nonzero sets bit 0 of the same register 0x1c06 value; I: window-id test enable).

    Registers written (E): 0x1c0b (descriptor 0x584fc800, data 0x013b1c0b; the framebuffer-address register of [ge-shadow-words.md](ge-shadow-words.md)) packed from the six bytes at 0x1d6-0x1db that word 8 adjusts, so only word 8 reaches it; 0x0807 and 0x0808 (window offset x and y) as the negated, halved values of the origin sums above, rounded by adding 15 and 3 to the 0x800 base and clearing the low 5 and 3 bits (0x0c018344-0x0c0183dc); 0x1c06 as above; 0x1133fc2 and 0x1143fc3 (scissor x and y bounds, packed x0 << 3 | x1 << 18 and the same for y) in the scissor-resolve step; the same scissor bounds offset by the origin into the on-chip RAM block at 0xc04 through the RAM-write helper; the viewport-resolve step writes the clipped viewport values through the engine port. The word sent at the end (operand 0x1c3c at port 0x474, data word 0 << 16 | word 1, then the halfword at 0x11c) is a combined origin pair, not a rectangle (E for the packing, role I).

    Still unread: which hardware fields the 0x1133fc2 and 0x1143fc3 packing feed beyond the names in [ge-shadow-words.md](ge-shadow-words.md); the unit behind the port at offset 0x3c that supplies word 10; the meaning of the six bytes at 0x1d6-0x1db beyond their update rule; the read-back companion of this request (handler at 0x0c018574), which is not covered here.

# XG: attach and reset sequence

What the 6.5.30m kernel driver does to the pipe's Xtalk-side registers when it attaches and resets a pipe. Source: `kona_kernel/disasm/kona_edtinit_hip2/kona_edtinit_hip2.text.s`, functions `kona_attach` and `kona_reset_adaptor`. Facts are labelled **established** (read from the disassembly), **inferred** (with the reasoning) or **unknown**. The first configuration read is one IP27 Onyx2 with one InfiniteReality2 pipe.

Notation: `P` is the driver's pipe state (offset 2376 holds the base of a 16 MB window the driver maps onto the pipe, mapped with `xtalk_piomap_alloc` for 0x1000000 bytes in `kona_attach`). Every register access below is a 32-bit `gfx_pio_read_32` / `gfx_pio_write_32` at `window + offset`. Offsets below 0x800000 are called the XG window here and offsets from 0x800000 the host-interface window (`HIP.h`). **Inferred** from the split in the kpm register tables and from the driver using only these two ranges; offsets 0x04-0x3c are the generic Xtalk widget registers (WIDGET_ID 0x04, WIDGET_CONTROL 0x24, REQ_TIMEOUT 0x2c, INTDEST_UPPER_ADDR 0x34, INTDEST_LOWER_ADDR 0x3c in Linux's `arch/mips/include/asm/xtalk/xwidget.h`), **inferred** because the driver's writes fit those layouts field for field (below). The chip-specific registers from 0x5c have no public name and are named by offset. **Established:** `kona_init` registers the driver for Xtalk part 0xc102, manufacturer 0x2aa, the numbers the same Linux header lists for "InfiniteReality3 / Kona GFX".

## Attach, `kona_attach`

**Established.** In order:

1. Finds the pipe's Xtalk widget info and its id; the low 8 bits are the widget number, used to find or claim a free pipe record (byte at `P+2208` holds it). The check `lw 100(base)` & 7 must be zero before it goes on (INFERRED role: a status word of the node's widget window, not the pipe's).
2. Maps the window, calls `kona_init_flow_control`, adds a hardware-graph edge.
3. Allocates three Xtalk interrupt handles, stored at `P+2240`, `P+2256` and `P+2264`, and connects each to a driver handler taken from a handler table. The device description used for the first sets the interrupt target CPU; the second and third reuse it. The handlers are `kona_xg_intr_handler`, `kona_intr_handler` and `kona_ge_intr_handler`, assigned in that order to the handles at `P+2240`, `P+2256` and `P+2264` (**inferred** from the order of the driver's handler table; `docs/hip.md`, interrupts).
4. Writes 0x8800 to window+0x8003c0 (`HH_VC_ADDRESS`) and reads window+0x8003d0 (`HH_VC_DATA`) (**established**; the names are from `HIP.h`).
5. Calls `kona_reset_adaptor` (below) when a driver-wide debug flag word at `0($gp)` allows, otherwise skips it; calls `kona_report_errs`.
6. Reads XG window+0x04 and stores its bits 28-31 at `P+2196`; reads XG window+0x64, takes bits 3-5 (default 8 when zero) and stores them shifted left by 15 at `P+2312`.
7. Writes 0x0b00 to `HH_VC_ADDRESS` again, reads `HH_VC_DATA`, and uses bits 0-1 of the first value read to pick one of several board-name comparisons (`strncmp` against a name string, then `kona_extract_nic_info`, `kona_init_board_mapping`, `kona_inventory_board`).

**Unknown:** what the video-controller indirect register (`HH_VC_ADDRESS` 0x8800 and 0x0b00) holds, and what the values chosen by bits 0-1 mean. *Test that would settle it:* a trace of the two attach-time reads on a live pipe of each product (IR2, IR3, IR4), or the frame-manager chip's decode table; the required values per product are in [findings/ir2e-ir3-products.md](findings/ir2e-ir3-products.md) (Q5). The shipped binaries do not answer it: the kernel only consumes the bits.

## Reset, `kona_reset_adaptor`

**Established.** Given the pipe state P, in this order (all writes are 32-bit):

1. `xwidget_gfx_reset(P+200)`: the kernel's own widget reset for the Xtalk widget handle at `P+200`. It is not a register write in this driver. **Established** from the kernel itself (`root/unix`, 6.5.30m, `xwidget_gfx_reset` at 0xc00000000006c908): it calls `xswitch_reset_link`, which is `xbow_reset_link`, and then `hub_widget_reset` for the widget's master hub. `xbow_reset_link` works on the crossbar's register block for the pipe's port (crossbar base + 0x100 + 0x40 x (port & 7)): it saves the word at +0x0c, writes 0 to +0x34, then polls bit 31 of +0x14 with `us_delay` until it is set or a timeout passes, and on success writes the saved word back to +0x0c. `hub_widget_reset` raises the interrupt level, walks the hub's eight I/O response-buffer entries (the 64-bit words at +776 of the hub's register block, one per entry), and for each valid entry (bit 56 set) whose bits 31-24 name this widget it zeroes the entry and writes (entry | 0x10) to +904, asserting if bit 4 reads back set; it then calls `hub_setup_prb(node, widget, 3, 2)`. **Inferred:** the crossbar side resets the Xtalk link to the pipe (the register at +0x34 is a link reset, bit 31 of +0x14 is link-alive and +0x0c is the link control it restores), and the hub side discards outstanding responses for the widget and reprograms its response-buffer credits; the XG therefore sees a link reset, not a write to any of its own registers. What the XG does internally on a link reset is **unknown: no shipped software or published source depends on it**: the driver rewrites every XG register it relies on afterwards (steps 2-10) and expects only the map RAM to survive ([below](#what-the-software-expects-of-the-xg-beyond-its-registers)). Routes tried: the 6.5.30m kernel and base kernel, kpm's XG table, and Linux `xwidget.h`.
2. Gets the interrupt target address (`xtalk_intr_addr_get`, 64-bit, call it A) and target number (`xtalk_intr_target_get`, call it T) from the first interrupt handle (`P+2240`).
3. Reads a word W from a per-node table indexed by the halfword at `P+2210`, at offset 4. N = 4 when bits 12-27 of W are nonzero; otherwise N = 3 if bits 28-31 of W are below 3, else 4. (The word's meaning is **unknown**; it is the same word class as the one stored at `P+2196` during attach, which suggests it is a copy of XG window+0x04. **Inferred.**)
4. Writes XG+0x24 = (T & 0xff) << 22 (masked to 0x03c00000) | (byte at `P+2208` & 0xf) | ((N << 12) & 0xf000) | 0x00240200, then reads XG+0x24 back.
5. Writes XG+0x3c = A bits 0-31, and XG+0x34 = ((T & 0xff) << 16, masked to 0x000f0000) | (A bits 32-47).
6. Reads the vector number of each of the three handles (V1 for `P+2240`, V2 for `P+2264`, V3 for `P+2256`) and writes XG+0x5c = 0x00020000 | ((V1 << 18) & 0x03fc0000) | ((V2 << 9) & 0x0001fe00) | (V3 & 0xff).
7. Calls `kona_report_errs`.
8. Reads XG+0x6c, writes XG+0x2c = 0, reads XG+0x6c again and writes the value read back to XG+0x6c.
9. Reads XG+0x24 and writes it back with bit 17 (0x20000) set.
10. Reads XG+0x74 and writes back ((bits 16-21 of it) << 16) | ((bits 22-27) << 22) | 0x3f40, dropping every other bit of the old value.
11. Writes 0xfff to window+0x800238 (`HH_INTR_STATUS`), and 0 to window+0x800390 and window+0x800398 (`HH_GV_ERR_STAT1` and `_STAT2`).

**Inferred** (generic widget layout from the Linux header): in step 4 the low half of WIDGET_CONTROL takes the widget number in bits 3-0, `SYS_END` (0x200) and N in the crossbar-credit field (bits 15-12); N follows the revision of the word read in step 3, which fits that word being the crossbar's own WIDGET_ID (older crossbars get 3 credits). Step 5 fills INTDEST_LOWER and INTDEST_UPPER (target id in bits 19-16, address bits 47-32) and leaves the generic vector field (bits 31-24) zero, because the three vectors go in the chip-specific 0x5c. Step 8 zeroes REQ_TIMEOUT. Bits 16-31 of WIDGET_CONTROL are chip-specific: 0x240000 is always set, the target number goes in bits 25-22 and bit 17 is set last.

**Inferred:** steps 4-6 set up how the pipe signals interrupts to the host. The packing shows a target number, a 48-bit target address and three 8-bit vector numbers, which matches an Xtalk interrupt destination. Step 8's read, clear, read, write-back pattern on XG+0x6c looks like an error or status register that is cleared by writing back the bits read. Step 11 clears the interrupt-status bits and both error-status words. None of this is confirmed against a register description.

**Established since** (kpm's XG register table, `diags/kpm/xg_registers.tsv`, 6.5.30m; the names are kpm's and the full field list is in [XG.h](../XG.h)): 0x24 is `XG_XT_CTRL`, and the driver's constant 0x00240200 sets `SYS_END` (bit 9), `MAPRAM_ENA_PAR` (bit 18) and `GUAVA_ENA_PAR` (bit 21); the target number goes in `DMA_DEST_ID` (bits 22-25), and the bit set last in step 9 is `INTERRUPT_ENA` (bit 17). So the driver enables map RAM and host-interface-bus parity first and interrupts last. 0x5c is `XG_XT_INTRVEC`: V1 lands in `XG_INTR_VEC`, V2 in `INTR_VEC1` with `BARRIER_VEC1` (the 0x20000), V3 in `INTR_VEC0`. 0x74 is `XG_HI_LO_WATER`: step 10 keeps the command-FIFO low and high water marks (bits 16-21, 22-27) and sets the output-DMA marks to low 0x40, high 0x3f, which is the 0x3f40 constant. The step-8 register 0x2c is the generic `REQ_TIMEOUT` (kpm has no record for it). The reset values of the command water marks, which the driver keeps, are **unknown: no shipped software or published source depends on them** (routes tried: the 6.5.30m kernel, kpm's XG table, which has masks and no defaults, the strings of kpm, irsaudit, postmortem and ireeprom, the 6.5.5 headers and Linux `xwidget.h`). The values are unknown. The same holds for the reset value of every other XG register: the driver writes each one it relies on.

## The rest of the window

**Established** (kpm's XG table; the 6.5.30m driver for what it uses). Beside the registers above, the XG window holds:

| Offset | kpm name | Who uses it | Grade |
|---|---|---|---|
| 0x0c | `XG_XT_STAT`: pending count, link size and retry flags, transmit and receive counts | kpm only | established |
| 0x64 | `XG_CONFIG`: `SUBSYSTEM` (bits 0-2), `MAPRAM_SIZE` (3-5), `MAPRAM_TYPE` (6-7) | `kona_attach` reads `MAPRAM_SIZE` | established |
| 0x6c | `XG_ERR_STAT`, 31 error bits (XG.h gives each kpm name next to the driver's message) | `kona_report_errs`, `kona_reset_adaptor` | established |
| 0x7c | `XG_GFX_DET`: `DETACH` (bit 0), `RES_TNUM` (bits 1-5) | every packet sender, the map and suspend paths: attach writes 34 (`RES_TNUM` 17, the constant `gfx_flow_credit_tnum_get` returns, kept at `P+2248`), detach writes 1 ([kernel.md](kernel.md#flow-control-layer)) | established |
| 0x84, 0x8c | `XG_GFX_AVCC` (available cache-line credits), `XG_GFX_AVDWC` (available doubleword credits), 12 bits each | kpm only | established |
| 0x94 | `XG_MAP_ADDR`, an 18-bit map RAM address | kpm only | established |
| 0x9c | `XG_NIC`: the serial-number one-wire port (`RD_DATA`, `DONE`, `SAMPLE`, `PULSE`) | kpm; the kernel reads the board serial numbers through its NIC code | established |
| 0xa4 | `XG_XT_LLP_LOG`: link sequence-number and check-bit error counts | kpm only | established |
| 0x100000-0x1fffff | `XG_MAP_RAM`, 32-bit entries: `PPN` bits 0-27, `INVALID` bit 28, `PAGESIZE` bits 29-30, `ODD_PARITY` bit 31 | `kona_mapram_init` writes 0x10000000 \| index (invalid), `kona_mapram_map` writes 0x20000000 \| frame (page-size code 1, the driver's 16 KB page) | established |
| 0x800000 | `XG_CLIENT_REGS`: the host-interface registers | the kernel's register accesses (HIP.h) | established |
| 0xc00000 | `XG_FC_CLIENT_REGS`: the host-interface registers again | the kernel's `HH_GINTR_INFO` kick at 0xc00108 | established |
| 0xc10000 | `XG_FC_GFX`: the graphics FIFO | the user command FIFO page (`KONAmapgfx`, [kernel.md](kernel.md#what-a-process-maps)) | established |

Each register is the low 32-bit half of a 64-bit slot at 8n (offset 8n + 4); the generic Xtalk widget registers sit at 0x04, 0x24, 0x2c, 0x34 and 0x3c the same way. **Inferred:** "FC" is flow control: the kernel sends its kick through 0xc00000 and maps the user's FIFO from 0xc10000, both paths that must stay ordered behind the flow-controlled user stream, and uses 0x800000 for every other register access. Offsets the table and the driver do not name are **unknown: no shipped software or published source depends on them** (routes tried: the 6.5.30m kernel objects, kpm's table, the 6.5.5 headers, Linux `xwidget.h`).

### Map RAM page-size codes and the entry test

The two-bit `PAGESIZE` field in a map RAM entry is a code, and the IRIX 6.5-base driver names the page size each code stands for. Its table (`kona_xg_psize_shift_to_index`, `kona_mapram_hip2.o` in the 6.5-base `kona.a`) reads 0 as 4 KB, 1 as 16 KB, 2 as 64 KB and 3 as 1 MB. The 6.5-base map routine writes `(code << 29) | (physical >> 12)` with a page size chosen per buffer. The 6.5.30 driver always writes code 1 with 16 KB pages, `0x20000000 | ((physical >> 14) << 2)`. The table is a software expectation of what the codes mean, so the mapping of codes to sizes is **inferred**; the field position is kpm's, and the 6.5.30 write is **established** from its disassembly. The 6.5-base entries come from a disassembly pass whose 6.5-base objects are not in this repository, so they have not been re-checked here.

The attach-time test in `kona_mapram_init` needs every entry below the entry count to hold exactly the value it was given. It stores `0x10000000 | index`, reads the entry back, and compares all 32 bits with no mask. The first mismatch ends the test and kills the pipe. The stored value uses bits 17:0 and bit 28 only, so the test cannot tell a 32-bit entry from one that keeps fewer bits. The entry width, the meaning of bit 28 and the reset contents of the table are **unknown**.

## What the software expects of the XG beyond its registers

**Established as the driver's expectation** (6.5.30m). After `xwidget_gfx_reset` the driver rewrites `XG_XT_CTRL`, both interrupt destination words, `XG_XT_INTRVEC`, `REQ_TIMEOUT`, `XG_ERR_STAT` and the output-DMA water marks, so it assumes none of them survives the link reset. The recovery in `kona_flow_await_returned_credits` runs `kona_reset_adaptor` and the `HH_RESET` pulse but does not rerun `kona_mapram_init`, so it expects the map RAM and the I/O-space mappings already handed out to survive both. `KONAinitialize` does rerun it.

**Unknown: no shipped software or published source depends on it** (routes tried: the 6.5.30m kernel objects including `kona_report_errs`, kpm's register table and its error strings, the IR diagnostics' strings, the 6.5.5 headers, Linux `xwidget.h`): how the XG splits host DMA into Xtalk requests (size, ordering, how many outstanding; the driver leaves `XG_XT_CTRL.MAX_TRANS` at 0), and the exact condition behind each `XG_ERR_STAT` bit beyond what kpm's field name and the driver's message say. The driver treats every bit alike: any of them raises the XG error interrupt, which prints the set bits and kills the pipe with reason 12 ([hip.md](hip.md)). Which bit a given fault sets is unknown beyond the field names.

## Pipe reset, `KONAinitialize` and the credit-wait path

**Established.** The host-interface reset register `HH_RESET` (0x800300, bit 0 is the reset bit in `HIP.h`) is pulsed in two places. Both run `kona_reset_adaptor` first and then the same four accesses: write 1, read back, write 0, read back.

- `KONAinitialize` (`kona_kernel/disasm/kona_setup/kona_setup.text.s`), after registering the board with the host-transfer layer and setting `P+2368` to 256: the pulse, then write `P+2368` (256) to `HH_INTR_ENABLE` (0x800230), write 0x8000 to `HH_INTR_INFO` (0x800220) and to its shadow at `P+2364`, `kona_mapram_init`, then under the interrupt-priority lock detach from the flow-control group if attached, reset the flow-control state (`gfx_flow_reset`), re-run `kona_flow_init`, and clear the word at `P+2172`.
- `kona_flow_await_returned_credits` (`kona_kernel/disasm/kona_flow/kona_flow.text.s`): when the returned credits stay below the bias, it polls the credit count up to 1000 times, one microsecond apart. If, at any poll, the word at `P+2344` is zero, the word at `P+2172` is nonzero, and bit 2 of the word at offset 4 of the object at `P+72` is set, it takes the reset path: `kona_reset_adaptor`, the `HH_RESET` pulse, then flush, detach, `gfx_flow_reset`, re-attach to the flow-control group, write 34 (the credit-return transaction number 17 in `RES_TNUM`) into `XG_GFX_DET` at window offset 0x7c (as in `kona_kern.h`) and finish the attach. If the poll runs out, it reads `HH_GFIFO_LEVEL` (0x800208) and, when it is above `P+2332`, forces a reschedule of the current process; otherwise it returns. With neither path taken, no reset happens, and `kona_die` is the only other recovery code.

**Inferred:** the path through `kona_flow_await_returned_credits` is a recovery used when a pipe stops returning credits while an extra flag (`P+2172`, cleared by `KONAinitialize`) is set. What `P+2172` and bit 2 of the word at `P+72`+4 mean is **unknown**.

**What the pulse clears, from the driver.** *Established* (kernel): every kernel pulse is 1 then 0, so it never sets the start bit (bit 1, `ARM_START` in kpm's table) and leaves the register at 0. What the kernel then rewrites tells which state it does not assume survives: the interrupt enable (`HH_INTR_ENABLE` = 0x100, `KONAinitialize`), the global interrupt enable (`HH_INTR_INFO` bit 15), the map RAM (`kona_mapram_init`), the flow-control state (`gfx_flow_reset`, then `kona_flow_init`, which writes `HH_GFIFO_HI` = 0x700), the window register at 0x7c. The recovery path in `kona_flow_await_returned_credits` does the same re-attachment. It does not rewrite the DMA registers, `HH_GFIFO_LO` or any ARM register.

*Inferred:* the pulse returns the host-interface registers the driver rewrites to their reset state (interrupt enable, global enable, credit threshold) and empties the map RAM's valid state, from the rewriting. A reset with the start bit set restarts the ARM: **inferred** from `init_graphics` in `kona_tport.o` (kernel-functions.md), which writes 3 then 2 to start a pipe that does not answer.

**Unknown: no shipped software or published source depends on it:** the pulse width (the two reads between the writes are the only delay), whether the 1-to-0 sequence with the start bit clear stops a running ARM, and what happens to the graphics FIFO contents, the DMA and event counters and the token map. After every pulse the kernel rewrites the registers it relies on and restarts flow control, and the firmware rebuilds the token map and reloads its tables in `init_hip` and `init_ged` each time it starts ([arm1_firmware.md](../ucode/arm1_firmware.md)), so no shipped program reads any of that state across a reset; the only state the driver expects to survive is the map RAM ([above](#what-the-software-expects-of-the-xg-beyond-its-registers)). Routes tried: the 6.5.30m `kona_reset_adaptor`, `KONAinitialize`, `kona_flow_await_returned_credits` and `kona_tport_reset_adaptor`, the ARM firmware's start-up, kpm's table and the 6.5.5 headers. `HH_JTAG_RESET` (0x378) is not accessed by the driver.

## Serial-number records on the one-wire port

**Established** (`kona_extract_nic_info` in `kona_edtinit_hip2.o`, and the printed `gfxinfo -vv` output of published captures). A pipe's description carries 13 one-wire records, in this order: the geometry board (GE), the Ktown board (`KT`), the four raster boards (`RM0`-`RM3`), the four texture boards (`TM0`-`TM3`), the backplane (`BP`), the display generator (DG) and the display option (`DGOPT`). The `gfxinfo` verbose form prints each one as its family code, serial number and part number, and the very verbose form adds revision, group, capability, variety and name. A slot with no board prints "No NIC serial number available". That covers the deskside Ktown, empty RM and TM slots and the backplane.

The parser matches the labels `Revision`, `Capability`, `Variety`, `Laser`, `Part`, `Name`, `Serial` and `Group`, and has a branch for a `Name` that starts with `KTOWN`. The driver does not check what it parsed, so an empty or missing record does not stop the attach.

**Inferred:** the kernel's own chain on the XG one-wire port (`XG_NIC`, 0x9c) carries only the GE and Ktown records. Where the other eleven are read from is unknown. The PROM reads the same chain through its own one-wire accessor at widget offset 0x98, which has its own protocol and is not a plain register read. Whether 0x98 and 0x9c reach the same records is **inferred** from one four-node boot capture, not from the PROM code.

## What the published manuals add

Labels follow [published-sources.md](published-sources.md); page numbers are PDF page indexes of the stored copies ([docs/sources/](sources/README.md)).

- **The host link is called Crosstown (established, published).** The Origin and Onyx2 theory-of-operations manual calls the board that carries XIO outside the chassis the Crosstown board, abbreviated KTOWN: it converts the XIO STL signals to differential 3.45 V PECL levels and a cable attachment, and supports XIO devices up to 3 m away; "Crosstown is primarily used to support graphics configurations" (007-3439-002 PDF p. 87; its figure shows a crossbar's XIO link feeding a KTOWN, then two GE14, two DG5 and four or two RM7/TM7 in one graphics chassis). The Onyx 350 and Onyx 3000 guides call the second-generation board Ktown2 and its two connectors Crosstown2 ("Xtown2"): one Ktown2 per graphics module converts the data from the host to differential signal levels, the top connector serves the right (first, up to four RM) pipe and the bottom one the left pipe; each connects to the XIO port of a compute, I/O, X- or N-brick through a NUMAlink 3 cable carrying 800 MB/s in each direction (007-4632-001 PDF p. 116 and the compute-module section, 007-4264-002 PDF p. 58-60; 3000 family reference guide PDF p. 12-13). The G-brick Ktown2 has two connector LEDs: yellow when the cable is seated and green when the link negotiated (007-4264-002 PDF p. 57). The names KTOWN, Ktown and Ktown2 therefore stand for the board that makes the XIO link leave the chassis, not for a graphics chip; no software read here talks to it, and `gfxinfo -v` lists it as `KT` with no serial number ([dg.md](dg.md#gfxinfo--v-sample-dplex-guide)).
- **Link bandwidth (established, published).** The InfiniteReality4 datasheet gives the host connection as an XIO channel of 1.6 GB/s per pipe (specs/sgi-3353-infinitereality4-datasheet.pdf PDF p. 2), which is the 800 MB/s each way above. The 1997 architecture paper's 400 MB/s host path (source 1) belongs to the first generation.
- **N-brick (established, published).** The N-brick connects up to four C-bricks to up to four InfiniteReality pipes in the G-brick, with four pairs of 800 MB/s connectors, in place of an X-brick or a second I-brick. It adds no PCI or XIO capability, does not change the one-to-one ratio of C-bricks to pipes, and needs IRIX 6.5.13 and L1 firmware 1.6.0 on every brick (007-4424-001 PDF p. 1; 007-4264-002 PDF p. 27). It is for Onyx 3000 systems with InfiniteReality only.
- **Pipes on the Onyx 3000 (established, published).** The G-brick is 18U with 11 board slots (Ktown2 plus two pipes), its own L1 controller and a direct 220 V power connector; V-bricks hold InfinitePerformance pipes instead and the two kinds cannot be mixed in one system (007-4264-002 PDF p. 28, 57-58). Where the host talks to a pipe, the compute brick's XIO port ("II" connector) is the one used for an InfiniteReality pipe or a PCI expansion module (007-4632-001, compute module section). These are the topologies in which the `kona_attach` path of this chapter runs; they say nothing about the widget registers.
- **Where an Onyx 3000 pipe appears (established, public capture; the path is inferred for the rest of the family).** The pipe is a widget of the Xbridge in the I-, X- or N-brick its Ktown2 is cabled to, not of the C-brick: the C-brick reaches a G-brick only through one of those bricks (007-4264-002 printed pp. 8, 10, 15-16). In the one Onyx 3000 `hinv -vm` found (Nekonomicon thread 16719632, 2008-12-05) both pipes of a two-pipe G-brick are at widget 11, one under `Ibrick/xtalk/11` (with the `KTOWN2` record) and one under `Xbrick/xtalk/11`, each brick under its own C-brick's module; no router is in the path. The smallest InfiniteReality system is the Onyx 3200 with one C-brick, one I-brick and a one-pipe G-brick. The widget behind an N-brick is unknown. Full grading and the settling captures: the chips repository's Onyx 3000 graphics-brick topology page.

## Widget identity and board type

Facts from the CPU PROM's board classifier and the widget's standard configuration layout. Both are **inferred** (software expectations from shipped firmware, not measured on a pipe), except where the note says otherwise.

- **WIDGET_ID (`+0x04`) layout (inferred).** Bit 0 is a presence bit, bits 1-11 are the manufacturer, bits 12-27 the part number and bits 28-31 the revision. The PROM takes the part number from bits 12-27 at every site that tests it, and takes the manufacturer from bits 1-11 for inventory text only. The revision field is never checked by the PROM.
- **WIDGET_CONTROL (`+0x24`) rewrite (inferred).** The PROM classifier rewrites this register once, unconditionally: it clears bits 0-3 and 12-15, copies the aperture's bits 24-27 into bits 0-3, and sets bits 12-15 to 3. The classifier runs on every board it sees, so bits 12-15 of this register end up holding 3 whatever the part number.
- **Board-type byte (inferred).** The classifier reads the part number and writes a board-type byte into the board record at offset `+0x5` (the offset the kernel's own lookup reads, [kernel.md](kernel.md)). Part `0xc102` gives `0x51`, the published Linux `KLTYPE_GFX_KONA` value, which is the pipe this document covers. Part `0xc003` gives `0x53` (the published MGRAS type). Part `0xc013` gives `0x54` (`odsy` in this repository's naming; no published name). Any other part gives `0x50`, a generic graphics board. Source: the CPU PROM classifier routine at image address `0x1fc4291c`.

Only part `0xc102` and the type `0x51` are checked against a kernel path in this repository. The `0xc003` and `0xc013` rows are PROM facts that no software here has run on a machine.

# The GLX client library (`libGL.so`): function reference

Sources: `usr/gfx/arch/IP27KONA/libGL.so` (6.5.30m N32; the other builds under `usr/gfx/arch/` have the same names). Roles are **inferred** from the names, the neighbouring documents and the ioctl numbers the functions send (found by reading the code: the numbers cited are constants loaded immediately before the ioctl call). `libGL` is the library an OpenGL program links: it opens the GLX connection to the X server, picks a visual, creates a context and then either renders directly (a "direct context": the process attaches to the graphics board through the kernel driver and `libGLcore`, [libglcore.md](libglcore.md), writes commands straight to the pipe) or encodes each call into the GLX wire protocol (the "indirect" path, handled by `glx.so` in the server, [x-server-glx.md](x-server-glx.md)).

## Video-sync and swap-interval routines read in full

Three SGI-extension entry points read from the `usr/gfx/arch/IP35KONA/libGL.so` (O32) and `usr/gfx/arch/IP35KONA32/libGL.so` (N32) builds of 6.5.30m. All three start from the process page: the word at 4096+20 is the current context, whose word at +276 is the drawable-side record `d`, whose word at +196, when non-zero, selects the path through the pipe driver and whose word at +204 is sent as the first word of each pipe request. The graphics descriptor is the word at (context + 4 times the context word at +264) + 4. The ioctl numbers are `RRM_GETVSYNC` (1022), `RRM_WAITVSYNC` (1023) and 1006 ([kernel.md](kernel.md#private-ioctls) for the pipe side). Every ioctl result is ignored.

- `glXGetVideoSyncSGI` (`usr/gfx/arch/IP35KONA/libGL.so` 0xd823e34, 152 bytes):
  **Established.** `a0` is the address that receives the count. With no `d` record (word at +276 zero) or a zero word at `d`+196 it returns 5. Otherwise it stores `d`+204 at sp+36, sends `ioctl` (slot 96) request 1022 (0x3fe) with the address sp+36 on the pipe descriptor, stores the second word of the request block (sp+36 plus 4, which the driver fills in) through `a0` and returns 0. The test of `d`+196 is a branch-likely, whose delay slot loads `d`+204.
- `glXGetVideoSyncSGI` (`usr/gfx/arch/IP35KONA32/libGL.so` 0xd824f64, 140 bytes):
  **Established.** The N32 build of the same routine, with the same steps. The result 5 is loaded into `v0` before the tests (0xd824f6c) and returned unchanged by the two failing branches; the block starts at sp+0 (the handle at +0, the driver's reply at +4) and `a0` is kept at sp+8. It sends `ioctl` (slot 96) request 1022, stores the block's second word through the saved `a0` in the delay slot of the return and returns 0.
- `glXWaitVideoSyncSGI` (`usr/gfx/arch/IP35KONA/libGL.so` 0xd824750, 200 bytes):
  **Established.** `a0` is the divisor, `a1` the remainder and `a2` the address that receives the count. It returns 5 when `d` is missing or `d`+196 is zero. It then returns 6 unless the divisor is positive, the remainder is not negative and the remainder is below the divisor (the last test is a branch-likely on `slt`). It stores `d`+204, the divisor and the remainder at sp+36, sp+40 and sp+44, sends `ioctl` (slot 96) request 1023 (0x3ff) with the address sp+36, stores the fourth word of the request block (sp+36 plus 12, which the driver fills in) through `a2` and returns 0.
- `glXWaitVideoSyncSGI` (`usr/gfx/arch/IP35KONA32/libGL.so` 0xd824ff0, 200 bytes):
  **Established.** The N32 build of the same routine. The divisor and remainder checks run only after the two checks that return 5, and each failing test returns 6 (the value is loaded into `v0` at 0xd824ffc). The block is at sp+0: the handle at +0, the divisor at +4 and the remainder at +8, with the driver's reply, the fourth word of the block, stored through `a2` (kept at sp+16) after `ioctl` (slot 96) request 1023.

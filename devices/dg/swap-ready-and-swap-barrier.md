# Swap-ready, framelock and the swap barrier

How a KONA pipe drives and samples the shared swap-ready line, how the DPLEX option uses it, and what the kernel, the X server and the field diagnostics do and expect for multi-pipe swap groups (`glXJoinSwapGroupSGIX`, `glXBindSwapBarrierSGIX`). First configuration only (IP27 Onyx2, IRIX 6.5.30m). Companion pages: [genlock-and-lock-status.md](genlock-and-lock-status.md), [gvo-option.md](gvo-option.md).

Grades and citations as in the genlock page. Display-bus addresses are word addresses ([firmware window](README.md#the-firmwares-display-bus-window)). Kernel facts that earlier pages already hold are summarised here with a link, not re-derived: the swap-group state machine is [Buffer swap and retrace wait](README.md#buffer-swap-and-retrace-wait), the DPLEX ring is [Multi-pipe (DPLEX) display-port writes](../../software/kernel/kernel.md#multi-pipe-dplex-display-port-writes).

## Summary

| Question | Answer | Grade |
|---|---|---|
| What is the line? | One shared swap-ready line per pipe set, cabled between the pipes' Swap Ready connectors with BNC tees and no terminators; it is wired-AND ("another pipe pulling SWAP READY low" holds off everyone's swap) | established (published; the diagnostic's own text) |
| How is it driven? | One output bit per pipe: display-bus 0x1920 bit 0 (DG5 without DPLEX) or 0x8001 bit 0 (boards the firmware flags as DPLEX), written 1 by the firmware's `SWAP_CNTRL` token; on DPLEX also 0xe500 bit 0 (`SWAP_RDY_DRV`) | established as writes; polarity unknown |
| How is it sampled? | No register reads the line level. Its only observable effect is that the VOC double-buffered copy ("NEXT to NOW") and the DPLEX `NOW` status do not happen while another pipe holds it low | established (messages), inferred (mechanism) |
| Does the kernel or X server read it? | No. They count swaps in software (swap group counters, the DPLEX ring token) | established (absence) |
| Does a client see a swap-group or barrier event? | No. The X server sends none; the only hardware-driven X event is the genlock lock change ([Xsgi events](../../platforms/ir/xsgi-events-and-manager-messages.md)) | established for the routines read |
| How many barriers? | One | established |

## 1. The line and its hardware

- **Published (established).** The OpenGL guide (007-2392-003 PDF p. 333-335) says `SGIX_swap_barrier` works only on InfiniteReality, offers one barrier, and needs a coaxial cable between the Swap Ready ports with the pipes genlocked. The DPLEX guide (007-3849-001 PDF p. 17) adds that swap-ready is one shared line cabled with BNC T pieces and no terminators, and that without it the DG5 buffers transfer video data at the wrong interval. **Established** by `konQueryMaxSwapBarrier` (`kona.so` 0x44f1b0), which returns the constant 1.
- **Netlist pins (established).** `irsaudit` names the frame-manager chip's pins `fm_do_swap` (string 0x10184058; ten outputs `do_swap[0..9]`, strings 0x101c49e0-0x101c4a70), `fm_swap_rdy_out` and `fm_swap_rdy_in` (0x101840d8, 0x101840e8; `swap_rdy_out` and `swap_rdy_in` at 0x101c4900 and 0x101c48f0 for the chain-scan form). So the frame manager has one swap-ready output and one input, and ten per-swap-group strobes. **Inferred:** `do_swap[n]` are the ten swap-group lines selected by the display-id table at bus 0x81 + n ([dgUpdateFMDidSwapTable](../../software/ucode/arm1_functions.md), `arm1.u` 0x0c0101b4) and the output ANDs with the input before the VOCs copy their double-buffered registers.
- **VOC side (established).** A VOC register set with `dbuf_mode` = 2 (`copy_swap`, VOC control register 0x01 bits 1-0) copies its pending ("NEXT") values into the active ("NOW") set on a swap pulse; mode 3 copies on frame start; `dbuf_request.enable` (register 0x02 bit 0, the diagnostic's `DBL_BUF_EN`) arms it. The diagnostic's tests call the pulse `SWAP_VOC` and fail with "Didload too long!" or "DBL_BUF_EN timeout!" when the copy does not complete (`TEST_odma` 0x1007dfe4, `TEST_pab2voccpbuf` 0x1007ea10, `TEST_tvo_voccpbuf` 0x100ac5e8; strings at 0x1019b438 and 0x1019b4e8). The VOC status bits `xmapreg_load` (12) and `impreg_load` (11) show the loads ([VOC registers](../voc/registers.md)).

## 2. How a pipe drives the line

- **`SWAP_CNTRL` (established, `arm_swap_cntrl` 0x0c013e50).** After the privilege check it writes the payload word to bus 0x80 (the swap strobe, [fm registers](../fm/registers.md)). If bit 0 of the payload is set it also writes 1 to bus 0x1920, or to bus 0x8001 when the board-flag word at 0x04067edc is non-zero (a DPLEX-type board; `DoDGRqstFetal` and `DoDGRqstDataFormat` write 0x8001 only for the DPLEX option). The payload the kernel sends is 0 or 1 only, once per matching swap-table entry ([step 5 of the swap sequence](README.md#buffer-swap-and-retrace-wait), `kona_video.o` +0x9c8 and +0xcd0); it carries no line number, so which line is driven is a property of the table position, not the value.
- **`DPLEX_SWAP` (established, `arm_dplex_swap` 0x0c013ef4).** Writes the payload to bus 0xe500; kernel swap-group members of a DPLEX network send it with payload 1 ([swap sequence](README.md#buffer-swap-and-retrace-wait), step 2).
- **DPLEX control (established, `irsaudit` `TEST_ddo3_ctrlreg` 0x1013022c).** Bus 0xe500 bit 0 is `DDO3_MUXDELAY_SWAP_RDY_DRV`; writing 1 makes bit 5 (`0x20`, `DDO3_STATUS_SWAP_RDY_DRIVE_MASK`) of the status word 0xe200 read 1 within 100 reads (the test counts a mismatch per read, so a model must show it on the first read), writing 0 makes it read 0. Bus 0xe300 bit 0 is `NEXT` (control); 0xe200 bit 0 is `DDO3_STATUS_NEXT`, the echo (write 1, expect 1; write 0, expect 0). The test prints status masked with 0xf3.
- **Auto-configuration (established, `TEST_ddo3_autoconfig_loopback` 0x101305d8).** Writes 0xe500 = 1 and 0xe300 = 1 and polls 0xe200 up to 100000 reads for bit 1 (`NOW`): "NEXT to NOW transition successful in %d cycles", otherwise "NEXT to NOW transition unsuccessful! Could not configure DPLEX for autoconfiguration" with the advice "Check to see if there is an external SWAP READY cable. If another pipe is pulling SWAP READY low, the NEXT to NOW transition will not happen and autoconfiguration is impossible" (0x101bed58). Then writes 0xe300 = 0xa0 and polls 0xe200 up to 100000 reads for bit 7 (`AUTO_CONFIG_DAT_RCV`), writes 0xe300 = 0x20 and expects bit 7 clear within 49 reads. The messages "GOOD: DDO3_STATUS_AUTO_CONFIG_DAT_RCV: high/low" and the repeated advice require the LVDS connectors cabled back to back.
- **Non-DPLEX option video (established, `run_optvideo` 0x100976e8).** The option-video test arms the option VOCs, loads format files, polls for the `NEXT` to `NOW` transition (message "NEXT to NOW transition successful in %d cycles", up to 100000 reads of a register at an option-VOC offset (the code adds 0x200, 0x300 and 0x500 to a base held in a register, `run_optvideo` 0x1009826c-0x100982c0, so which VOC is not resolved); unsuccessful text with the swap-ready advice at 0x101a0f30: "...local video will not be multiplexed to the output"). So for the GVO, DVP and TVO too, the NEXT to NOW copy is the observable consequence of swap-ready.
- **Diagnostic that exercises the output (established, `TEST_swap` 0x1010538c, group `swap`, "Swap Ready test").** It waits for HH_GFIFO_LEVEL (host-interface offset 0x208) to read 0 (a polling loop with a delay of 5 between reads, 0x101053bc-0x10105404), disables credit flow with the diagnostic ioctl 10101, then calls `swap1` (0x1010554c): `reset_dacs`, load `1280x1024_60.vfo`, two `tst_multi_voc` runs, then prints "Attempting to toggle the swap ready line / Check the output of the SWAP READY connector / HIT ENTER WHEN READY", and toggles bus 0x1920 (1 then 0) or, on the other branch of the loop, 0x8001 (0x101056e8-0x1010577c; the branch condition was not identified, **inferred** the DPLEX flag), with a delay of 10 between writes, until the operator hits a key, then asks "Did you see the SWAP READY toggle(y/n)?". The result is the operator's answer: the routine has no automatic check. **Established:** a model passes by accepting the writes and the operator replying y.

## 3. How the line is sampled (the open part)

- **Established (absence).** No firmware, kernel or diagnostic routine read here reads a register that reflects the swap-ready input level. `irsaudit` has no `fm_swap_rdy_in` register read; the only status words that change with it are the DPLEX `NOW` bit (0xe200 bit 1) and the VOC copy completion.
- **Inferred.** The sampling happens inside the frame-manager and VOC logic: a swap pulse is released to the VOCs only when `swap_rdy_in` is high. Because the pipe also drives the line (a pipe holds it low until its own local swap is armed and releases it at the strobe), every pipe's swap waits for the slowest. Polarity (high = ready), the release timing and the glitch filtering are **unknown: no shipped software or published source depends on them**. Routes tried: the firmware's writes to 0x80, 0x1920, 0x8001, 0xe300, 0xe500; the diagnostic's DPLEX, option-video, swap and VOC tests; the kernel's `kona_nclops` functions; the published guides. What would settle it: a scope capture of the swap-ready connector with two pipes, or the frame-manager chip's datasheet (not held).

## 4. The kernel and X server barrier

- **GLX (established, `glx.so` `glxBindSwapBarrierSGIX` 0xeb0830-0xeb0b3c).** Looks up the drawable, creates a swap group for it if it has none (ioctl 0x3f5 = 1013, `RRM_SwapGroup`), then ioctl 0x3fb = 1019 (`RRM_SwapReady`) with {window id, barrier number, on/off} (on when the request's word is non-zero). errno 16 and 37 become a GLX bad-value error; other failures are generic. `glxJoinSwapGroupSGIX` uses 1013 alone.
- **Kernel (established, `rrm.o`).** `RRM_SwapReady` (+0x3d84): a barrier number at or past the board's line count (word +176, the number of swap-ready lines) gives 37; no pane gives 2; a pane on another pipe 6; no group 15. On: an empty slot in the table at pipe state +184 takes the group (0), the same group again gives 17, another group 16. Off: the group's slot is cleared (0), otherwise 9. `rrmSwapUnGroup` clears every slot equal to the group when the group dies. **Inferred:** the table is the same one the swap sequence walks to send `SWAP_CNTRL`, one entry per swap-ready line. The line count is a field of the board record built from the configuration; its source for IR2 is not read (the X module reports 1, section 1).
- **What happens at a swap (established).** The group's members arrive one by one ([swap sequence](README.md#buffer-swap-and-retrace-wait)); the last member sends `SWAP_CNTRL` 1 per bound line and calls the retrace activate. For a barrier the cross-pipe wait is therefore done by the hardware line, not by software: the kernel of one pipe never talks to another pipe's kernel. **Inferred** from the kernel not reading any line state and from the published statement that the cable is required.
- **Interrupts and registers (established).** None are specific to swap-ready. Completion arrives through the ordinary retrace path: the swap marker `RETRACE_SEQID` and the video interrupt (HH_INTR_STATUS bit 3, [Interrupts](README.md#interrupts)).
- **What multi-pipe software expects (established, published).** A two-pipe swap group hangs until both pipes have swapped, and unregulated swap-ready lets buffers transfer at the wrong time ([published](#1-the-line-and-its-hardware)). The model's swap-group tests (`glXJoinSwapGroupSGIX`, `glXBindSwapBarrierSGIX` users) need only the kernel behaviour above.

## What a model must do to pass

1. **Single pipe, no cabling.** The line is never pulled low by anyone else. NEXT to NOW therefore completes at once: DPLEX 0xe200 bit 1 reads 1 on the first read after 0xe300 bit 0 is set, option-video and VOC copy-buffer tests see their copy complete before the polling limit.
2. **DPLEX registers.** 0xe300 write 1 → 0xe200 bit 0 = 1; write 0 → 0; 0xe500 write 1 → 0xe200 bit 5 = 1; write 0 → 0, each on the first read. With the LVDS loopback present: 0xe300 = 0xa0 → bit 7 of 0xe200 reads 1; 0xe300 = 0x20 → reads 0, within the retry counts. Without a loopback the autoconfig test fails; that is the real board's behaviour as well.
3. **Swap-ready output.** Accept writes of 1 and 0 to 0x1920 and of 1 to 0x8001 and 0x80; no reads depend on them. `TEST_swap` is passed by the operator.
4. **Swap groups.** `RRM_SwapReady` semantics as above; one barrier; a swap group whose members have all arrived completes without an external line.
5. **Gating (optional realism).** If two models share a line, delay NEXT to NOW until both have armed their swap; no shipped software observes the timing.

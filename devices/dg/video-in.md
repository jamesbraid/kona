# Video into the frame buffer on KONA

Can the display generator, the GVO or any option board bring video into the pipe's frame buffer or texture memory, and what does shipped software do about it? First configuration only (IP27 Onyx2, IRIX 6.5.30m, InfiniteReality2 with a DG5-2). Companion pages: [external-status.md](external-status.md), [gvo-option.md](gvo-option.md).

Grades and citations as in the genlock page. Library lookups (`techpubs`, `irix-mirrors`, `origami-docs`) found no document describing the pipe's video bus; the published statements used are the ones already held in [published-sources.md](../../references/documents/published-sources.md).

## Summary

| Question | Answer | Grade |
|---|---|---|
| Can the DG, GVO, HD GVO, TVO, DVP or DPLEX take video in? | No. They are output options: they read the frame buffer and drive a connector. Their pixel path is frame buffer to output ([gvo-option.md](gvo-option.md)) | established for GVO (register map and test); published for the others |
| Which DG option takes video in? | Sirius (the PAB2 board), a first-generation option. The X module refuses it on an Onyx2 | established (checker string "Onyx2 does not support Sirius option board") |
| Does the pipe have a video-in path at all? | Yes: a video bus. The firmware has video forms of copy-pixels, copy-to-texture and read-pixels, a `SetupVbus`/`StartVbus` distributor sequence and a "GPI vid-bus interface" the diagnostics test with output DMA | established (firmware and `irsaudit`) |
| What uses it? | Only a GLX video-source path (`glXCreateGLXVideoSourceSGIX`) that loads `libvl.so`, and the firmware token `HP_VIDEO_SOURCE` that `libGLcore` sends. No kernel driver code, no DG register and no shipped KONA tool starts a transfer | established (absence for the driver) |
| What enables the video forms? | `HP_READBUFFER_CONFIG` with level -3, sent by `kona_readconfig` for a video-source read drawable; see [video-bus.md](video-bus.md) (this corrects the earlier text here, which said no sender was found) | established |

## 1. The DG and its options

- **Output only (established).** The GVO's data path is two VOCs writing a window of the main frame buffer into the option board's own frame buffer and the board reading it out ([gvo-option.md](gvo-option.md)); the diagnostic's `dgo_fb_test` (0x10116fa8) writes the main frame buffer and reads the GVO's two halves back through 0xc600, so the flow is graphics to video. The HD GVO, TVO and DVP are published as output boards ([published manuals](README.md#video-option-boards)); the DPLEX combines pipes' video outputs (a digital multiplexer, [swap page](swap-ready-and-swap-barrier.md)). The DG's own chip set has no capture path: the VOCs' pixel requesters read the frame buffer (`req_window`, [VOC registers](../voc/registers.md)).
- **Sirius (PAB2) (established as detection, published for use).** `irsaudit` probes it (`probe_dg4_chain` "Sirius (PAB2) present in DG option slot." 0x10054c68; `probe_dg5_chain` "Problem: unsupported Sirius (PAB2) present in DG option slot??" 0x10055b2c; `unscramble_dg_boardId` "SIRIUS interface present in option slot." 0x1008d1ec), has a `-pab` test group (`pab2vocreg`, `pab2voccpbuf`, `pab_intbist`, strings 0x10190b28-0x10190f10), loads its logic through requests 53-55 (`DoDGRqstLoadPabXilinx`, [Display requests](README.md#display-requests)) and checks a GPI cable ("GPI cable for Sirius video option present." / "not present (ok).", `TEST_sysprobe` 0x100593f0, 0x10059abc). The only account held (a usenet post, 1997-02-25, graded unverified in [published-sources.md](../../references/documents/published-sources.md)) says Sirius adds an output with two modes ("vampire", copying a raster region, and "requesting", pulling its own pixels); the combination slot is 9. Where its live video goes is not stated in anything held ("live video in, with alpha, chroma or generated keys" is the manual's phrase, 007-3279-003 PDF p. 16-17). On an Onyx2 the checker refuses it (`vfmtIsKonaCombinationValidForTarget`: class not 0 and option 1 gives "Onyx2 does not support Sirius option board"), and the firmware's option numbering for it exists only on board set 0.

## 2. The pipe's video bus (established in the firmware)

- **Video source token.** `HP_VIDEO_SOURCE` (token 0x114, `arm_video_source` `arm1.u` 0x0c013924) takes one word (0-3) and calls `SetVideoFormat` (0x0c02bdfc), which records a source-format description in the per-context state block (+0x6d0, fields +0x0-0x34; the first two codes share constants, the third and fourth each have their own). When the field at +0x18 equals 1 it first calls `SetGedVideoBoard` (0x0c032ccc): zero to descriptor 0x06200020 six times, then three writes to 0x04800020 and four zero writes to 0x04200020 after each. `libGLcore.so` `kona_readconfig` (`kon_context.s`) sends the token with the read drawable's video type mapped as 0x1001 to 0, 0x1000 to 1, 0x1002 to 2, 0x1003 to 3 and anything else to 0 ([GE.h](../ge/GE.h) at `KONA_HP_VIDEO_SOURCE`).
- **Video forms of the pixel handlers.** `videoCopyPixels` (0x0c02bd60: operation word 0x50, transfer flags 0x40000, `resolveVideoPath`, then `StartVbus`), `videoCopyTexImage` (0x0c02c0f8: operation 0x90, starts the video bus transfer after the sub-texture set-up) and `videoReadPixels` (0x0c02c6d4: operation 0x30, packer and send to host) are reached from `arm_copypixels`, `arm_copyteximage` and `arm_readpixels` when the video flag at pixel state +0x348 is set. `EnableVideoCopy` (0x0c02bf28) stores that flag and `EnableInterlace` (0x0c02bf34) the interlace byte at +0x78f and engine external memory word 0xc03; both are called from `arm_slop` (token 0x17f). The flag is also set by `HP_READBUFFER_CONFIG` with level -3 ([video-bus.md](video-bus.md#3-what-enables-the-video-forms-of-copy-copy-texture-and-read-pixels)). `SetupVbus` (0x0c032b9c) selects the video bus instead of the raster bus in the distributor (five words from the per-context record, descriptor 0x04600020); `StartVbus` (0x0c032c30) is a fixed sequence of 14 distributor writes (zero to 0x06200020 six times, 1 to 0x04400020, zero to 0x04200020 four times, zero to three more descriptors) ([arm1_functions.md](../../software/ucode/arm1_functions.md)). So a video-in transfer is a distributor operation in the pipe's own stream: the data arrives on a video bus, not through the DG.
- **Where the data comes from: see [video-bus.md](video-bus.md).** The driving board is the Sirius Video option over its CP bus; the paragraph below predates that page. The pipe's side is the "GPI" flag (expansion unknown) of the geometry-engine identity word ([setup-tools.md](../../software/userland/setup-tools.md): GPI when bits 15-9 are zero and bit 20 is clear) and the optional GPI board; `gfxinfo` prints a GPI option line for it. Which external board drives that bus is not stated in any shipped file read. What would settle it: the GPI board's part number and description in a published inventory, or `libvl.so` and `videod` device tables for a KONA path (those files are out of this repository's scope, [AGENTS.md](../../AGENTS.md)).

## 3. The diagnostic that exercises it

`TEST_gpi` (`irsaudit` 0x100764c4, group `gpi`, "GPI vid-bus interface test", "Requires GPI board", string 0x101919c8) is the only test of the path:

1. It refuses when a Sirius board is present ("Sirius Option board detected. Cannot run this test", 0x10076938).
2. It maps a host buffer with the diagnostic ioctl 10100 (`KONA_DIAG_MAP`, "KONA_DIAG_MAP ioctl failed." on failure) and sets up the geometry-engine distributor (`diag_setupGED` 0x10076084).
3. It programs output DMA channel 0 through raster-bus registers 0x440 (= 0x43), 0x441, 0x450-0x453 with a total of 784 bytes (0x310 = 196 words; 0x452 and 0x453 take 784 and the page registers 0x450 and 0x451 the mapped address).
4. It calls `setupVidbusInterface` (0x10076164, argument 196), writes zeros through `arm_ged_write` to 0x20 and 0x21, runs `vidbusFlush` (0x10076484) and `resetVidbusInterface` (0x100761e4), writes 1 to register 0x477 and polls the host-interface offset 0x278 until the output DMA finishes ("ODMA FAILED on Primary Channel." on a timeout).
5. It compares the 196 received words with the table `gpi_exp_pat` (0x10200740, 784 bytes), 12-bit fields of two halves per word: "bits 0:23 :: Exp: %x Recv: %x" and "bits 24:47 :: Exp: %x Recv: %x"; any mismatch prints "GPI test FAILED !!!" and the test fails.

So the diagnostic does not need an external video source: the pattern comes from the formatter inside the pipe (`formatterFlush` 0x100763e8) and loops through the video-bus interface into output DMA. **Established** as the code path; **inferred** that the formatter is the pattern generator, from the absence of any external-source prompt.

## 4. Driver and VL path

- **Kernel (established, absence).** The KONA driver has no video-in ioctl. Its 6.5.5 ioctl slots and the 6.5.30m `KONAprivate` table ([kernel.md](../../software/kernel/kernel.md)) carry display mode, swap, DMA, memory and hyperpipe operations; the video interrupt (HH_INTR_STATUS bit 3) is the frame interrupt, not a capture event. The only kernel writes to the display bus are the cursor, swap strobe, hyperpipe and display-mode ones ([What the driver can reach](README.md#what-the-driver-can-reach)).
- **VL (established for the client, unknown beyond).** `libGL.so` (the KONA builds) exports `glXCreateGLXVideoSourceSGIX` (o32 IP27KONA build 0xd824988) and `glXDestroyGLXVideoSourceSGIX`, and its extension string lists `GLX_SGIX_video_source`. `__glXInitializeVideoLibrary` (0xd824eb8) calls `dlopen("libvl.so", RTLD_NOW)` (0xd824ef0) and `dlsym("vlGetControl")` (0xd824f20); `videoPackingToInternalFormat` (0xd824d30) maps a VL packing to a GL internal format; the create function sends a GLX request and keeps a 24-byte private. So the VL path is a user-space library choosing a video node, with the GLX request carrying the identifiers to the X server (`glx.so` video-source handlers, [x-server-glx.md](../../software/xsgi/x-server-glx.md)). **Unknown:** the VL device for a KONA video path and the transfer start. What would settle it: `libvl.so` and the VL device list for IRIX 6.5.30m (not held).
- **Inferno's VL (observed, model).** The evidence store shows Inferno's `libimpact` failing with `vlOpenVideo failed` on the Onyx2 model and `vlinfo` "can't open server" (the Discreet Inferno evidence set `inferno-dg52-20261112`, outside this repository); that is the Impact (Octane) VL device library and the model has no VL server, so it says nothing about a KONA video-in path. No shipped software read here uses the pipe's video bus other than `TEST_gpi` and the GLX video-source calls.

## What a model must do to pass the diagnostics

1. **No video in is needed** for any KONA diagnostic except `TEST_gpi`, which a pipe without a GPI board may skip ("Requires GPI board").
2. **If `TEST_gpi` is to pass,** output DMA channel 0 must accept the 784-byte transfer programmed through 0x440-0x453, signal completion at host-interface offset 0x278 within the test's wait, and deliver the 196-word `gpi_exp_pat` pattern from the video-bus interface. The pattern is data in `irsaudit` (not copied here); a model needs the expected words from the binary at build time or must report the test unsupported.
3. **Everything else** (`HP_VIDEO_SOURCE`, `SetupVbus`, `StartVbus`, the video copy forms) is firmware behaviour inside the pipe stream; a model that executes the firmware stream gets it; one that implements the tokens itself can accept `HP_VIDEO_SOURCE` and ignore the rest until a guest uses it.

# The GVO option board (part 030-1184, on a DG5-2)

What the shipped software tells us about the graphics-to-video option board (GVO, internal name DGO): how it is detected, how its logic is downloaded, its register map and status bits, how pixels reach it, how it locks to an external reference, and what software reads back. It is written so an emulator can model the board. First configuration only: one IP27 Onyx2 with one InfiniteReality2 pipe, IRIX 6.5.30m; the plain-DG5-2 load of `1280x1024_30f` is in [combination-files.md](combination-files.md).

Grades: **established** (read in full from a routine or table, cited), **inferred** (reasoned, with the reason), **unknown** with what would settle it. No hardware was used; a diagnostic's expectation is a software expectation, not a measurement. Register names are the vendor diagnostic's own text strings (public in the shipped binary); chip names are those strings too. Bus addresses are display-bus word addresses ([firmware window](README.md#the-firmwares-display-bus-window)): ARM address 0x600000 + 4 x address.

Sources read: the firmware `arm1.u` ([arm1_functions.md](../../software/ucode/arm1_functions.md), [dg_access.tsv](../../software/ucode/dg_access.tsv), and the `OptVocAddress` table decoded from the image), the X module `konal.so` (disassembly), the diagnostic `irsaudit` (its `dgo_*` and `TEST_gvo_*` routines, disassembled, strings resolved through its global table), `dgo.mcs`, the combination files and the published manuals cited in [published-sources.md](../../references/documents/published-sources.md). A Library search of `techpubs`, `irix-mirrors` and `origami-docs` found no GVO register or board description beyond what that page already holds.

## 1. Detection

- **Identity word (established, [setup-tools.md](../../software/userland/setup-tools.md)).** The display board's identity word (`brd:` line's last word) carries the option type in bits 21-19: 6 means GVO on a board set other than 0 (3 TVO, 4 DPLEX, 5 DVP, 7 none). A DG5-2 with GVO reads `f9311002` in the published IR3 capture, a plain DG5-2 `f9391002` (bits 21-19 = 7). The channel count is bits 18-16 plus one (2 for a DG5-2).
- **Option mask (established).** `dgGetBoardConfig` turns the option type into a mask returned by display request 18: GVO gives 0x10 (TVO 0x40, DPLEX 0x20, DVP 0x08, none 0). The X module logs it as "DG board version %d (brd mask=0x%x, opt mask=0x%x, opts=0x%x)".
- **Part numbers (established, published captures).** DG board 030-1242-001 (rev D seen) with a separate option record `DGOPT`: GVO 030-1184-002 (rev B seen), name `GVO`; a plain DG5-2 is 030-1055-001 and its `DGOPT` slot prints "No NIC serial number available". `gfxinfo` prints "GVO option detected" and "Display has 2 channels" ([ir2e-ir3-products.md](../../platforms/ir/ir2e-ir3-products.md)); published `hinv` output has no GVO line in anything held here (**unknown**; a published `hinv` of a GVO pipe would settle it).
- **Firmware probe (established).** In display request 17 (`DoDGRqstFetal`) and request 83 (`DoDGRqstXServerVideoInit`) the firmware walks the 17-entry `OptVocAddress` table (id, board-type mask, board type, flags). The GVO entries are ids 0xc6, 0xc7 and 0xe6, mask 0x7e, board type 6, flags 0xc0000000. A video-output chip (VOC) is present when `dgIsVocPresent` writes id + 0x3e8 to its register 0x31 and reads the same value back. For ids 0xc6 and 0xc7 the VOC base is 0xc800 and 0xc900 (0x200 + 0x100 x id), so the probe is a write and read of bus 0xc831. Id 0xe6 is a broadcast alias at base 0xe800 that writes both VOCs. With option type 6 the firmware also pulses bus 0xc000 (soft reset) 1 then 0 at request 83, and `dgMakeGvoFetal` does nothing. Flags bit 31 makes bit 26 of the channel record's word +0x184 (call it b) equal 1 for all three GVO ids.
- **Kernel driver (established by absence).** The kernel's own display-bus accesses are the cursor, swap strobe and video-DAC blocks through `HH_VC_ADDRESS` and `HH_VC_DATA` ([What the driver can reach](README.md#what-the-driver-can-reach)); no GVO-specific address (0x8900, 0x8a02, 0xc000-0xcfff, 0xe800, 0xf000) is among them, so the kernel does not detect or drive the board. It only carries the one-wire records (`DGOPT` is the 13th, [xg.md](../xg/README.md)).
- **Slot to channel (established, [combination-files.md](combination-files.md#5-are-two-loadformats-on-channel-0-within-one-combination-load-the-expected-sequence)).** The X module builds a 15-entry table mapping combination slot to channel index. A GVO option sets entry 11 to the index of a new channel with physical id 0xc6 (read from display request 19) and puts it after the two monitor channels, so on a DG5-2 with GVO entry 11 is channel index 2 and physical id 0xc6. Without a GVO the entry stays zero (inferred) and slot 11 lands on channel 0.

## 2. Logic download

- **Who sends it (established).** The X module, not the kernel: when the option mask has bit 0x10 set, the screen set-up (`konal.so`, the routine that builds the per-screen record, call at 0x1474c38) calls its loader at 0x13d10d0 before creating the GVO channel; a nonzero failure there aborts the record build. The image is `/usr/gfx/ucode/KONA/dgo1/dgo.mcs`, the same file as `usr/diags/IR/ucode/dgo.mcs` (sha256 `518cd70fa8b714748db380cec7c3340637cbdec4f1847981546cc1b2c4bbf38c`), Intel HEX, 34138 bytes in 2134 data records ([dg.md](../../software/ucode/dg.md#option-board-image-dgo1dgomcs)).
- **Parsing (established, 0x13d10d0).** The loader reads each line, requires `:` first, decodes length, address, record type and data from hex, and sums the bytes. Errors it prints: "illegal .mcs offset 0x%04x!", "unknown .mcs type 0x%02x at line %d", "bad .mcs checksum at line %d (%s)!", ".mcs tailer missing!".
- **Request sequence (established).** First display request 82 with six words: type (0), -1 (clear); it waits for reply 27 (a word, 1 = success), else "error initializing %s xilinx!". Then for each run of up to 16 bytes it sends request 82 with the type, the byte count and the bytes packed four to a word in words 2-5, and waits for reply 27; a status other than 1 prints "error loading xilinx byte %d!". The tail (after the last record) was not read in full; **unknown** whether a final request follows.
- **Firmware side (established, `DoDGRqstLoadXilinx` 0x0c012280).** Type must be 0. Count -1 writes 1 to bus 0x8900 ("load control"), sleeps a fixed delay and replies success. A count above 16 is refused ("illegal packet size"). Otherwise each byte is written to bus 0x8a02 and the firmware polls bit 7 of that word for up to 999 reads; a timeout prints a message and the reply status is 0. The reply is code 27 with status 1 only on success.
- **Diagnostic side (established, `diagLoadDGOXilinxes` 0x1011c44c).** The same protocol straight from the host: parse the file to 0x855a bytes, write 1 to 0x8900, wait one tick ("DGO xilinx cleared..."), then for every byte write it to 0x8a02, write 0 to 0xc008, and poll 0x8a02 for bit 7 set for up to 99999 reads ("Timeout programming xilinx byte %d" on failure), the last byte written once more at the end. The diagnostic retries the whole load up to 30 times (`dgo_loadXilinx_reset`).
- **What the board must answer (established as expectations).** A model needs: 0x8900 accepts a write of 1; 0x8a02 accepts a byte and bit 7 reads 1 once it is taken (immediately is enough); after the last byte the display-bus registers below respond. No done, init or checksum bit is read anywhere: the firmware and diagnostic only poll bit 7 of 0x8a02. The device family of the programmable logic and what the image implements stay **unknown** (dg.md); a datasheet or board netlist for part 030-1184 would settle it.

## 3. Registers and status

The board sits on the display bus, reached through `HH_VC_ADDRESS`/`HH_VC_DATA` or the firmware window; it has no bus of its own. **Established** for every address below as an access by shipped software; names are from `irsaudit`'s register tests and messages and widths from its register-test arguments (`reg_test`, which writes patterns to the stated number of bits and reads them back, so the registers are plain read/write storage unless noted).

| Bus address | Name (diagnostic) | Width, behaviour | Used by |
|---|---|---|---|
| 0x8000 | `DG5_POWER` | written 0 then waited on by the diagnostic's mode set-up | `dgo_setup_fb_mode`, `dgo_ll_path`; the firmware's XMAP clock-select request also writes it, so the overlap is **unknown** |
| 0x8400 | option mode word | bits 12-11 = 1 for GVO (the firmware writes it with GVO data format; TVO also uses 1, DPLEX 2) | `DoDGRqstDataFormat` |
| 0x8900 | logic load control | write 1 = clear and start | section 2 |
| 0x8a02 | logic load data | byte write; bit 7 on read = byte accepted | section 2 |
| 0xc000 | soft reset | writing 1 then 0; the diagnostic reads it back and requires the value written, waiting between steps | `dgo_reset`, request 83 |
| 0xc001 | `DGO1_INTR_ENABLE_SEL` | 9 bits | `dgo_regs` |
| 0xc003 | `DGO1_USTC_CTRL_SEL` | 5 bits | `dgo_regs` |
| 0xc006 | `DGO1_601_CTRL_SEL` | 11 bits, layout below | firmware, diagnostic |
| 0xc007 | `DGO1_DVP_CTRL_SEL` | 2 bits | `dgo_regs` |
| 0xc008 | no name | write-only; the diagnostic writes 0 repeatedly as a delay (`dgo_wait`) | diagnostic |
| 0xc100-0xc103 | output window | horizontal start and end, vertical start and end (inferred from the names of `dgDGOOutputLetterbox` that centres the picture in a 720-wide raster) | firmware |
| 0xc104 | `DGO1_601_FBC_CTRL` | frame-buffer control: bits 4-0 = b << 1, bit 6 = "format flag is zero", bit 7 set by the letterbox routine, blank field in bits 11-8 (read-modify-write by blanking and the gamma load) | firmware |
| 0xc200-0xc213 | `DGO1_601_CSC_SEL` CM11 to CM33, KEY | colour-space converter matrix and key, ten 13-bit values as byte pairs (8 bits each) | `DoDGRqstDataFormat` |
| 0xc214, 0xc215, 0xc216 | CSC CONTROL1-3 | 8, 8 and 1 bits | `DoDGRqstDataFormat` |
| 0xc400 | genlock-chip serial port | write: shift in a 47-bit image one bit per write (50-tick sleep each); read: bit 0 returns one status bit per read | firmware writes, diagnostic reads |
| 0xc401 | genlock-chip strobe | final write after the image | `dgWriteDgoTMC22071a` |
| 0xc600 | frame-buffer readback port | the diagnostic reads the board's two frame-buffer halves through it | `dgo_fb_test` |
| 0xc800 + n, 0xc900 + n | VOC 0xc6 (master), VOC 0xc7 (slave) | the standard VOC register file ([VOC registers](README.md#voc-registers)); 0x31 and 0x32 are 32-bit read/write | VOC probe, `dgEnableChannelGenlock`, load format |
| 0xe800 + n | both VOCs | writes go to both; the diagnostic writes 0xe831, reads 0xc831 and 0xc931 | `dgo_regs` |
| 0xcf00 | `DGO1_601_STATUS_SEL` | read-only status, below | `dgo_status` |
| 0xf000-0xf3ff | colour look-up table | 1024 words, loaded in mode 3 (below); blanking writes zeros | `arm_x_loadgamma`, `dgBlankChannel` |

**`DGO1_601_CTRL_SEL` (0xc006), established from `dgo_status`'s decode and the firmware's writes.** Bits 1-0 and 3-2: the EDH processor address of link A and link B. Bit 4: pixel-clock select of the genlock chip, 1 = internal (its PLL locks to the incoming video), 0 = external 27 MHz crystal. Bit 5: colour-space-converter data port disabled when 1. Bits 8-7: mode, 0 = low-latency (the VOCs drive the converter directly), 1 = frame-buffer mode (the VOCs write the board's frame buffer in encoder mode), 3 = colour look-up table mode, 2 = illegal (the diagnostic prints "not in any know mode"). Bits 10-9: how the two low bits of the 10-bit output are formed, 0 zero, 2 true 10 bits, 3 duplicate of the top bits (1 unnamed). The firmware's default after loading a GVO format (`DoDGRqstDataFormat`, b = 1): bit 4 = 0, bit 7 = 1, bits 2 and 10 = 1, bits 0, 1, 3, 5, 8, 9 = 0, so 0x484: frame-buffer mode, external crystal clock, link B address 1, true 10-bit output.

**`DGO1_601_STATUS_SEL` (0xcf00), established branches, inferred names.** The diagnostic reads it until two reads agree in bits 4-0 (up to 100 reads; else "inconsistent read values"), then reports: bit 0 set = no TRS codes detected on the links, clear = present; bit 2 = link A serializer PLL locked; bit 3 = link B serializer PLL locked; bits 1 and 4 are in the stable-read mask but not printed (**unknown**). A model that returns bit 0 = 0, bits 2 and 3 = 1 reports a healthy output.

**Genlock-chip status (the board's TMC22071 reference decoder, serial read of 0xc400).** The diagnostic reads 59 times and keeps bit 0 each time; the first bit read is the last field. Fields it names: locked or not locked (the lock bit, 1 = not locked), colour burst present, blanking level (8 bits), sync-tip value (4 bits), clamp, burst output, CVBS bus, PLL or free-running oscillator, AGC, coarse horizontal phase (8 bits), sub-pixel phase (4 bits), gain 1.0 or 1.5, source (2 bits), format (3 bits: NTSC at 12.27 or 13.5 MHz, PAL at 13.5, 14.75 or 15.0 MHz) and reset. **Established** that the lock bit and the burst bit are single bits of that stream; the exact stream index of each was read from `dgo_genlock_status` and is **inferred** to be bit 56 for lock (1 = not locked) and bit 47 for burst (1 = present).

## 4. Pixel path and genlock

- **Channel and window (established, [combination-files.md](combination-files.md)).** The GVO is combination slot 11 (HD GVO is slot 14), physical id 0xc6 with VOC 0xc7 as its pair. Its record reads a rectangle of the managed area ((0, 0), 720x486 in `1280x1024_30f`), loaded as the `CCIR601_525_DGO` format through display requests 22 (LoadFormat) and 20 (Resize) like any channel, then data format request 88.
- **Data path (established modes, inferred wiring).** In frame-buffer mode, the firmware's setting, the GVO's two VOCs fetch the window from the main frame buffer and write it into the option board's own frame buffer; the output side reads that buffer at the 601 timing through the output multiplexer, the look-up table, the colour-space converter (a GF9105 by the diagnostic's name) and two EDH-processing serial links A and B (dual link; a serializer and PLL per link). The diagnostic's frame-buffer test writes a pattern, reads both halves back through 0xc600 and checks EDH CRCs. In low-latency mode the VOCs drive the converter directly; no shipped software selects it (the firmware sets frame-buffer mode, b = 1). **Inferred** from the mode names and the test strings; the board's frame-buffer organisation is **unknown** (a netlist or datasheet for 030-1184 would settle it).
- **Data format (established).** Display request 88 selects the pixel format: converter control 0xc214 = 0x31 for formats 2 and 3, else 0x10; 0xc215 = 0xa7 for format 3, else 0xa3; 0xc216 = 0; the ten matrix values from one of two tables (a studio-range RGB-to-luma/colour-difference matrix scaled by 1024 for formats 0-2). The X module's checker refuses a GVO data format with alpha when the source pixel format has none ("GVO Data Format has alpha, but source Pixel Format does not have alpha"). The 10-bit RGB or RGBA source and the 4:2:2 output are published ([option boards](README.md#video-option-boards)).
- **Letterbox (established).** `dgDGOOutputLetterbox` centres the output of channel 0xc6 in a 720-wide raster by writing 0xc100-0xc103 and setting bit 7 of 0xc104; offsets depend on bit 20 of the record's control word (the data-format flag).
- **Look-up table (established).** For the external gamma form of the gamma load the firmware clears bits 11-8 of 0xc104, sets bits 8-7 of 0xc006 (mode 3), writes the 1024 words to 0xf000 + i, then restores 0xc006; blanking the GVO channel writes 1024 zeros there.
- **Genlock to the external CCIR601_525 reference (established writes).** The combination's `syncSource` 1 and `syncFormat` `CCIR601_525` cause the firmware (`dgEnableChannelGenlock`, for ids 0xc6, 0xc7 and 0xe6 unless the channel is the record's master) to set bit 4 of 0xc006 equal to the genlock enable, which selects the genlock chip's internal PLL clock locked to the incoming reference. The programming of the genlock chip itself is the 47-bit image of `dgWriteDgoTMC22071a`, built in the data-format request (word 0: bit 0, bit 1 or bit 3 from the flag, bits 24-17 = 0x7b, bit 30; word 1: bit 2, bit 12, bits 11-8 = 3). In the genlock path that touches the VOCs (0xc801, 0xc806 read; 0xe801, 0xe806 write) the firmware does this only when bits 8-7 of 0xc006 are zero, so in frame-buffer mode only bit 4 of 0xc006 changes. The reference input is the board's genlock connector ([channels and boards](README.md#channels-and-boards-owners-guides-ir4-addendum)). The X module's checker enforces: GVO must have an external sync source if its source channel is none; the GVO source channel must be none when another interlaced channel's source channel is none or another channel's frame rate is lower than the GVO field rate.
- **Timing relation (inferred).** The window is read at the GVO channel's own format timing (the `.vfo` CCIR601 timing), written into the board's frame buffer, and read out at the genlocked 601 timing; swap rates must agree (published rule, 2 percent). The frame buffer decouples the two clocks; its depth is **unknown**.

## 5. Readback: what software expects

- **Firmware at run time (established).** It reads only: the VOC probe (0xc831 and 0xc931 read back what was written, so the registers must store 32 bits), 0xc006 and 0xc104 (read-modify-write, so they must hold written bits), 0xc801 and 0xc806 (VOC register read-modify-write in low-latency mode), and the VOC registers 0x06 and 0x44 bit 0 that fill display request 19's reply (flags for channel 0xc6). Its reads of 0xcd00 belong to the DVP option. It never reads 0xc400, 0xcf00 or 0xc600, so it never reports lock or errors to the host.
- **X server, kernel, Inferno (established by absence in the firmware and kernel tables; inferred for Inferno).** Nothing shipped here reads the GVO lock state, field counters or error bits at run time; the server's lock handler reads only video chip 1's status (display-bus 0x300), not the option chips ([events page](../../platforms/ir/xsgi-events-and-manager-messages.md#genlock-and-the-screen-lock-event)). The server learns the board from request 18 (option mask) and 19 (channel 0xc6's configuration, a 0x4c-byte reply). Inferno's trace needs only the combination load and the channel enable; the evidence shows no dependency on lock.
- **Diagnostic expectations (established, software expectations).** After `dgo_reset`, 0xc000 reads back the value written (1, then 0); after a logic load the register tests of section 3 read back what was written; status shows PLLs locked and TRS present with a live output; after a reset the genlock chip reads not locked, and after programming the PAL (or NTSC) reference with a signal present it reads locked (`dgo_genlock_test`). The field counters the coordinator asked about were not found: no register or message names one on this board (**unknown**).

## What stays open, and what would settle it

| Open | Settled by |
|---|---|
| Logic device family and what `dgo.mcs` implements; the board's frame-buffer size and layout | a datasheet, netlist or photograph of part 030-1184 (the netlists held are `dg4_2voc_hdgvo`, the HD GVO form, not this board) |
| Final request after the last byte of the logic download; whether 0x8a02 bit 7 can ever stay clear in normal use | the tail of the loader at 0x13d1a9c and a trace of a real download |
| Names and meaning of 0xcf00 bits 1 and 4, 0xc006 bits 5-6 and the middle value of bits 10-9; stream indices of the genlock status bits | a second reading of `dgo_status` and `dgo_genlock_status` against their message texts, or a capture |
| Whether `hinv` prints a GVO line | a published `hinv` of a GVO pipe |
| Which checker rules apply when no GVO option is present (the model loads slot 11 anyway) | the combination checker's option rules read in full |
| Hardware lock timing and error reporting | measurements; no shipped software reads them |

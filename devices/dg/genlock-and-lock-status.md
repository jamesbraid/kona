# Genlock and lock status on the DG5 and the GVO

Everything shipped software does with an external timing reference on an InfiniteReality2 display generator (DG5-2, with or without the GVO option board): what it writes, what it reads back, which status bits exist, and what a passing field diagnostic expects. First configuration only (one IP27 Onyx2 pipe, IRIX 6.5.30m). The GVO board itself is in [gvo-option.md](gvo-option.md); the swap-ready line is in [swap-ready-and-swap-barrier.md](swap-ready-and-swap-barrier.md).

Grades: **established** (read in full from the cited routine), **inferred** (reasoned, with the reason), **unknown** (with what would settle it). Binary facts are cited by routine and image address: `arm1.u` is the ARM firmware (image base 0x0c000000, entries in [arm1_functions.md](../../software/ucode/arm1_functions.md)); `irsaudit` is `usr/diags/IR/bin/irsaudit` (N32, addresses as linked); `konal.so` is `usr/lib/X11/dyDDX/konal.so` (sha256 `37c26ff4e3cdd6616389e21ca3698b18c642b3e8815d37900001329754b5f156`); kernel objects are `usr/cpu/sysgen/IP27boot/kona.a` members and `rrm.o`. A Library search of `techpubs`, `irix-mirrors` and `origami-docs` for the extension requests found no document describing them. No `ide` image holds a genlock test: `ide` does not appear in the diagnostic's test list or help text, and `usr/stand/ide` is out of scope for this repository (it names no InfiniteReality symbol, [AGENTS.md](../../AGENTS.md)).

## Summary

| Question | Answer | Grade |
|---|---|---|
| Does any software read a genlock lock bit at run time? | No. The X server, kernel and firmware only write the genlock set-up and react to one event, the VOC interrupt (HH_INTR_STATUS bit 9), without reading why it came | established (absence over the routines below) |
| Where are lock bits read? | Only by `irsaudit`: the GVO genlock-chip serial status (one bit means "not locked") through bus 0xc400, and the GVO status word 0xcf00 (serializer PLLs, TRS codes) | established |
| What does the base DG5 report about lock? | Nothing is read. The VOC status register has external-sync-detect and external-sync-loss interrupt bits that no shipped code reads or clears | established (absence), bit names from [VOC registers](../voc/registers.md) |
| What must a model do to pass? | See the last section | established as expectations |

## 1. What the run-time software writes

- **X server (established, `konal.so`).** The video-control extension's "set screen input sync source" callback (slot +0x68 of the screen record, routine at 0x13c5b40) prints "Warning: using an undocumented setting to enable tri-level sync input" (string at 0x150d158, debug id 5017) for a first argument other than 1 or 2 (1 and 2 select the values 0 and 1, anything else the value 2), and then sends three requests to the firmware: display request 9 (`InputSync`) with payload 3, request 68 (`GenlockSwitching`) and request 26 (`EnableGenlock`), each with a flag that is 1 when the caller's third argument is -2 and 0 otherwise (0x13c5c34-0x13c5cd8). It then calls a helper at 0x13ce960 with that flag and the screen record's word +0x49c. The 0/1/2 value the routine computes for the first argument is overwritten with 3 in the same stack slot before request 9 is built, so request 9 always carries 3 (**inferred** from the instruction order, 0x13c5c2c-0x13c5c54; the routine was read once, branch by branch). The query callback at 0x145e840 passes the screen record and its word +0x3a8 to a helper that I did not read. The same module's combination loader sends the genlock parameters and the format's sync fields ([genlock parameters](README.md#genlock-parameters-command-25), [combination loader](README.md#loading-a-combination-channel)); the model's KONA video trace shows `InputSync` and genlock requests after `EnableChannel` ([combination-files.md](combination-files.md)).
- **Names with no readable body (established names, unknown bodies).** `konal.so`, `kona.so`, `konad.so` and `konas.so` carry local function names `konGenlockHandler`, `konHandleGenlockStatusChange`, `konSetScreenGenlock` and `GenlockNotify` (their `.text.<name>` section entries), but the dynamic symbol table gives no address, and none of the requests above is sent from a routine I could tie to them. **Unknown:** what a genlock status change does in the server. What would settle it: locate those four routines by disassembling the callers of the kernel message type 12 handler (the board-manager STREAMS read in `Xsgi`) and read them in full.
- **Firmware (established).** Request 9 read-modify-writes bits 21-20 of `frame_window_control` (display-bus word 0x8b, [fm registers](../fm/registers.md); `DoDGRqstInputSync` 0x0c011490); request 10 reads them back (0x0c0114f4). Request 68 copies bit 0 into bit 30 and request 84 into bit 27 of the display-state flag word at 0x0406cd1c, with no hardware write (0x0c006250, 0x0c006344); requests 69 and 85 reply with those flags (0x0c006270 pulses bus 0x343 bit 0 first, 0x0c006364). Request 26 blanks all channels, stops every requester, and per VOC calls `dgEnableChannelGenlock` (0x0c005538), which selects the VOC clock source, reprograms the clock, sets register 6 bits 12-9 from the reset ratio, sets bit 0 of register 0x30 (and bit 4 when genlock is switched off) and, on channel 1, clears and re-sets bit 0 of register 0x43 around a 50-tick pause. `dgLoadChannelGenlockParams` (0x0c004ec0) writes the 16 parameter words: VOC register 6 bits 12-9 and 2-1, register 0x81 bit 0 (the lock multiplier is bits 11-2, `dgIsChannelGenlockable` 0x0c005494 reads it), 0x82-0x84 and the frame-detection words at 0x30-0x32. It also sets VOC control bits 5-4 (external-sync detect and loss interrupt enables) and clears bit 6.
- **Kernel (established).** HH_INTR_STATUS bit 9 (`VOC`) is in the running enable mask 0xf7c. `kona_intr_hip2.o`'s handler runs `kona_voc_intr` (`kona_genlock.o` +0x0), which calls `rrmGenlockNotify(connection, -1)`; that defers through `streams_timeout` to `rrmGenlockNotifySTREAM`, which sends the board manager (the X server) a two-word STREAMS message of type 12 with words (0, -1) via `GfxIntrMessage` ([kernel.md](../../software/kernel/kernel.md)). The handler reads no register. It writes the served bit back to HH_INTR_STATUS and 0xbadc0ffe to HH_INTR_ACK like every cause. **Established:** that is the whole kernel involvement; nothing reads VOC status.
- **What raises bit 9 (inferred).** The VOC enables set by the firmware are external-sync detect and loss, so bit 9 is the OR of the VOCs' interrupt lines. VOC status bits 21 (`int_ext_sync_detect`) and 20 (`int_ext_sync_loss`) are the latched causes. No shipped code clears them, so whether the line is level or edge, and how a latched cause is cleared, is **unknown**. What would settle it: a read of a VOC status register after an external reference is applied and removed (capture proposal below).

## 2. What setmon and ircombine read and write

- **setmon (established).** `saXSGIvcSetScreenInputSyncSource` (0x10033100) and `saXSGIvcQueryScreenInputSyncSource` (0x10033c30) call callback slots +0x68 and the query slot of the extension state; they take a channel and a sync-source choice and return what the server stored. `setmon -n` loads a combination, which carries `syncSource` and the external sync format name ([combination-files.md](combination-files.md)). Neither tool reads a hardware status bit: every read goes through the X extension to the server's stored values ([setup-tool-functions.md](../../software/userland/setup-tool-functions.md)).
- **ircombine (established).** Writes the combination file (**inferred** from the file contents and the form handlers `external__5Form2` and `horizontalSync__5Form1` that store into the same fields): global `syncSource` (0 internal, 1 external), `syncFormatName`, `syncFormatValid`, `syncFormatFrameRate`, `syncFormatDateStamp` and per-channel `HSync`, `SyncComponent`, `SyncSource` (decoded in [combination-files.md](combination-files.md) and [dg.md](../../software/ucode/dg.md)). Its checker needs an external sync source when a GVO channel's source channel is none, and an HD GVO output must have its own sync format; frame rates must be compatible (`vfmtSyncFormatFrameRatesCompatible`, an exported function of the module).
- **xsetmon (established by names).** Its server-information form has `doInputSyncSourceNotifyHandler`, a handler for an input-sync-source notify event from the extension ([setup-tools.md](../../software/userland/setup-tools.md)). **Unknown:** when the server sends it, and what it carries. What would settle it: the sender of that event in `Xsgi` (the video-control extension's event code).

## 3. The timing reference on the DG5 itself

- **External sync into the VOCs (inferred from names).** The VOC chip has `pfd_control` (frame-detection control), `sync_detect_control` and `genlock_*` registers ([VOC registers](../voc/registers.md)). A DG5-2 with no option carries its genlock input on the VOC chain; the netlists name the pins `voc_ext_csync` and `voc_cdr_ext_csync` (strings in `irsaudit`, table at 0x10183238 and 0x101837f8). **Inferred.**
- **External PLL select (established as a diagnostic access).** `vdLoadExternalSync` (0x1013119c) opens a sync-format file, parses it, and shifts values into the JTAG element `DG.PLL_MUX0` (`tlPassthruWrite` at 0x10131314, data words 1, 2, 5; `vdStopExternalSync` 0x101315c0 writes 6 or 7). That is the diagnostic's way to present an external reference: through the scan chain, not the display bus. Its caller is a function-pointer call I did not resolve (**unknown**; the video tests that use it would be named by the call site).
- **Internal versus external clock select (established).** `vdSetVocInternalClock` (0x10134908) reads and writes display-bus 0x8e (master clock select, [request 43](README.md#display-requests)) and writes 0x4; `dg_clock_restore` (0x10036b08) restores 0x281 and 0x207 with the message "Inverted internal clock select on later boards" (bit 0 of 0x281 = 1) against 0x407 on old boards. A model must keep 0x281 and 0x8e writable and readable.
- **What loss of lock does (unknown).** No shipped software reacts to loss of lock other than the VOC interrupt notice of section 1. What the VOC does to its own timing on loss is not stated anywhere read here.

## 4. The GVO genlock input and chip (confirmed against the diagnostics)

[gvo-option.md](gvo-option.md) says no shipped software reads GVO lock at run time. **Confirmed against `irsaudit`:** the lock-related diagnostic routines are exactly `dgo_status` (0x10118f6c), `dgo_genlock_status` (0x101199f4), `dgo_genlock_test` (0x1011ac80), `dgo_genlock` (0x101193e4), `dgo_genlock_reset` (0x1011a280), `dgo_genlock_NTSC` (0x10119fac), `dgo_genlock_PAL` (0x1011a088), `dgo_write_tcm22071` (0x1011a164), `dgo_csc_status` (0x10119824) and the test entries `TEST_gvo_genlock` (0x1011bb5c, group `gvogenlock`, "GVO Genlock Part tests") and `TEST_gvo_status` (0x1011b8b4, group `gvostatus`, "GVO board, genlock and csc statuses"). No other function reads bus 0xc400 or 0xcf00 (`dg_access.tsv` lists only the firmware's writes to 0xc400/0xc401). The firmware, kernel and X server never read either.

- **Genlock-chip programming (established).** The chip is called TMC22071 in the diagnostic's messages. A 47-bit image is held one bit per word in `dgo_genlock_buf_out` (0x10345438, 47 words). Bits 46 down to 1 are each written to bus 0xc400 followed by one `dgo_wait(1)` (a write of 0 to 0xc008), then bit 0 to 0xc401 and another wait (`dgo_write_tcm22071`, 0x1011a164-0x1011a27c). The PAL image has bits {0, 3, 30, 34, 44} set and the NTSC image {0, 1, 30, 34, 44}; all other bits are 0 (`dgo_genlock_PAL` stores 1 at word offsets 0, 12, 120, 136, 176; `dgo_genlock_NTSC` at 0, 4, 120, 136, 176). The firmware builds a different image for its own use (bits 24-17 = 0x7b and others, [gvo-option.md](gvo-option.md)). `dgo_genlock_reset` (0x1011a280) prints "Resetting DGO Genlock chip", then calls `dgo_write_tcm22071` twice, with element 0 of the buffer set to 0 and then to 1 and the other elements as the last image left them.
- **Status read (established).** `dgo_genlock_status` reads bus 0xc400 59 times into `dgo_genlock_buf_in` (0x103454f8, 59 words), keeping bit 0 of each read; the first read lands in element 58, the last in element 0. The element tests are: element 56 = 1 prints "- NOT locked", otherwise "- locked!"; element 47 = 0 prints "- NOT color burst detected", otherwise "- color burst present"; element 46 = 1 prints "GRSONLY = 1". Other elements give blanking level (elements 55-48), sync-tip value (43-40), clamp, burst output, CVBS bus, oscillator mode (PLL or free-running), AGC, coarse and sub-pixel horizontal phase, gain (1.0 or 1.5), source (2 bits), format (3 bits: NTSC at 12.27 or 13.5 MHz, PAL at 13.5, 14.75 or 15.0 MHz) and reset. **Not resolved:** which element carries each of those last fields (the tests were read as a group; only the three above were matched to a message by instruction).
- **Lock reading order (established).** The lock bit is the third bit read (element 56), and 1 means not locked, 0 locked. `dgo_genlock_test` reads it the same way.
- **The test (established).** `dgo_genlock_test` (0x1011ac80): `dgo_reset` (0xc000 pulse), read 0xc006 and write it with bit 4 set (internal PLL clock select), `dgo_wait(1)`, trace "- PAL mode", `dgo_genlock_PAL`, `dgo_write_tcm22071`, then the 59-bit status read. **Pass:** element 56 = 0, "GOOD: TCM22071 was found locked in PAL mode"; element 56 = 1 gives "ERROR: Expected TCM22071 to be locked in PAL mode" and counts 1. It then `dgo_reset`s again, reads the status again, and expects element 56 = 1: "GOOD: TCM22071 was NOT found locked after reset"; element 56 = 0 gives "ERROR: Did NOT expect TCM22071 to be locked after reset". The function returns the error count (0 passes). There is no wait between programming and the first read other than the per-bit `dgo_wait(1)` writes (59 + 47 + 2 register writes), so a model must report "locked" immediately after the PAL image is shifted in, and "not locked" immediately after a reset.
- **GVO status word 0xcf00 (established).** `dgo_status` (0x10118f6c): reads 0xc006 and decodes mode (bits 8-7), LSB mode (bits 10-9), PLL select (bit 4), CSC port (bit 5) and the two link EDH addresses; reads 0xcf00 once, then re-reads it until two reads agree in bits 4-0 (up to 101 attempts) and prints: bit 0 = 1 "no TRS codes detected" (link A and B), bit 2 "link A serializer PLL locked", bit 3 "link B serializer PLL locked". **Unknown:** the meaning of bits 1 and 4, which only enter the agree mask. The routine prints and returns nothing the test treats as a failure except "inconsistent read values" (a read that never stabilises).
- **What signal the test expects (unknown).** The test says nothing about a cable. With nothing on the genlock input the TMC22071 cannot lock to a reference, so either the test expects the pipe's own output looped to the input, or the chip's "locked" bit means something other than input lock. No message, option text or `ide`-style help names a cabling requirement (contrast `TEST_ddo3_autoconfig_loopback`, which prints "CAUTION: DPLEX LVDS connectors must be cabled in loopback manner"). What would settle it: a capture of this test's status stream on a pipe with and without a reference (proposal below).

## What a model must do to pass the diagnostics

1. **GVO register file.** Accept the reset sequence of [gvo-option.md](gvo-option.md) (0xc000 readback), 0xc006 read-modify-write holding all 11 bits, and the 0xc400 serial port: 47 writes then 0xc401, with reads of 0xc400 returning a 59-bit stream whose third bit is the lock flag (0 locked).
2. **Lock behaviour.** After `dgo_reset` the lock bit reads 1. After the 47-bit PAL (or NTSC) image is written with 0xc006 bit 4 set, the lock bit reads 0 on the next status read. The next `dgo_reset` returns it to 1. The burst bit (element 47) is 1 only while the model reports an input; with none, "NOT color burst detected" is not a failure.
3. **Status word.** 0xcf00 returns the same value on two successive reads, with bits 2 and 3 set (PLLs locked) and bit 0 clear (TRS present) after a frame-buffer-mode setup; any stable value passes the diagnostic, because the routine only prints.
4. **Base DG5.** Nothing reads lock. The diagnostics that touch the sync path need 0x281, 0x8e, 0x207 and 0x4 writable, VOC status and control registers storing what the diagnostic writes, and, for `vdCheckDgInterrupts` (0x10130d90), a video interrupt (HH_INTR_STATUS bit 3) and a VOC interrupt (bit 9) to be deliverable when enabled ([Interrupts](README.md#interrupts)): the function returns 1 for a video interrupt seen and 2 for a VOC interrupt seen and prints them; **unknown** whether a caller treats a missing bit as failure.
5. **The run-time path.** A bit 9 interrupt is only ever turned into a type-12 STREAMS message; a model that never raises it breaks nothing shipped.

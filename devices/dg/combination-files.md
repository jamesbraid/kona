# Combination and format files as the GVO combinations use them

What a `.cmb` combination and a `.vfo` video format contain, how the X server's KONA module reads them and loads them onto channels, and what the Discreet Inferno load of `1280x1024_30f` does on a plain DG5-2. Facts are labelled **established** (read in full from the cited file or routine), **observed** (what a model run showed; model behaviour, not hardware evidence), **inferred** or **unknown**, and every unknown says what would settle it. The SGI data files were decoded and are not committed; every value below is a field value, decoded in our own words.

Sources: the 101 `.cmb` and 135 `.vfo` files of an installed Onyx2 (IRIX 6.5.21f, `/usr/gfx/ucode/KONA/dg4/{cmb,vfo}`, the Inferno 4.7.2 guest; the file set is the 6.5.30m media's 26 combinations and 74 formats plus the GVO and HD GVO ones), the model run in the evidence store (`inferno-dg52-20261112/combination-20261120`, including the video trace), and `konal.so` 6.5.30m (sha256 `37c26ff4e3cdd6616389e21ca3698b18c642b3e8815d37900001329754b5f156`) read with `objdump`. The container is in [display-file-format.md](../../software/video/display-file-format.md); the per-field meanings for the 26 media combinations are in [dg.md](../../software/ucode/dg.md#combination-files-cmb); the channel loader is [Loading a combination channel](README.md#loading-a-combination-channel). This page adds what the larger set and the loader's outer loops show. How the server gates format against combination loads is [Loading a format: per channel or as a combination](README.md#loading-a-format-per-channel-or-as-a-combination).

## 1. File structure, and what the larger set adds

**Established.** All 236 files (101 + 135) open with the container of display-file-format.md (magic `sdb `, format version 0.1, XDR words, a symbol table at the end) and decode with the field types listed there; no file needs a type the reader lacks. A `.cmb` carries `MajorVersion` 1 and `MinorVersion` 0 in all 101.

- **Header.** Container header, then the 20 global fields: `MajorVersion`, `MinorVersion`, `name`, `dateStamp`, `textport`, `managedSize`, `allocatedSize`, `pixelDepth`, `syncSource`, the four `syncFormat*` fields (`Name`, `Valid`, `FrameRate`, `DateStamp`), `syncComponent`, `fastlistChunksize`, `PSDhysteresis`, `minRMs`, `usingEncoderOutput`, `globalGamma` (three floats) and `usingGlobalGamma`. Same list as dg.md; no file has more.
- **Per-channel records.** A channel is the 38 fields named `ch<N><Field>` (`Blanking` to `VPhase` in dg.md's table), plus `VbobSyncSource` where present (137 of the 200 channel blocks). `<N>` is the combination slot, not a position: slots 0-7 are the monitor channels, 8 the encoder, and the option boards take 9 (Sirius), 10 (DVP), 11 (GVO), 12 (DPLEX), 13 (TVO) and 14 (HD GVO) ([slot numbers](README.md#slot-numbers-of-the-option-channels)). A file lists only the slots it uses; a missing slot has no fields. The reader marks a channel record present when it finds one (`+712`, [channel record](README.md#loading-a-combination-channel)).
- **Format reference.** `ch<N>FormatName` is a `.vfo` file name with its extension. `ch<N>FormatDateStamp` and `ch<N>FrameRate` copy the format's date and frame rate (**established** as values: the frame rate equals the `.vfo`'s `FramesPerSecond` in every channel decoded here). The format itself is read from the `.vfo` at load time (`vfmtReadKonaVideoFormat`, called from the loader's outer loops).
- **Input and output.** `InputOrigin` is the corner of the managed area the channel reads, `InputSize` the rectangle size, `OutputSize` the size the channel puts out (equal to the input size when the channel is not scaled), `MinSize` and `MaxSize` the limits the combiner allows. `SourceChannel` names the slot whose pixels the channel copies; it equals the channel's own slot unless the channel is dependent.
- **Sync.** `SyncSource` per channel and `syncSource`, `syncFormat*` global. **Inferred** (values, `gfxinfo` and the GVO files): the global `syncSource` is 0 for the internal timing and 1 for an external reference named by `syncFormatName`. It is 1 in 50 of the 101 files, all of them with a valid `syncFormatName`, and 0 in the other 51, which have none. The combination's external-sync handling reaches the display generator as the genlock parameters ([command 25](README.md#genlock-parameters-command-25)).
- **Which combinations exist.** By slot set: slot 0 alone in 25 files, slots 0 and 1 in 25, slot 1 alone in 6, slots 0 and 14 in 19, 0 and 11 in 10, 1 and 11 in 4, 1 and 14 in 4, and 8 files with three to eight monitor channels or an encoder. The 26 combinations of the 6.5.30m media are all among the 101; 37 files carry an option slot (11 or 14) and the `_CHAN1` and `_chan1` variants of those put the desktop on monitor 1 (slot 1) instead of monitor 0.
- **The two option slots.** In every slot-14 (HD GVO) and slot-11 (GVO) combination the option channel is its own source. A slot-11 channel always reads the top-left corner (0, 0) at its own size, 720x486 for the 525-line format and 720x576 for the 625-line one, with gamma 1.0 and `SetGamma` true in all 14 files. A slot-14 channel has gamma 1.7 and `SetGamma` false and its origin depends on the desktop: for example (280, 113) in a 1280x1024 desktop, (600, 201) in 1920x1200 for 720x486, (320, 80) for 1280x720 in 1920x1200, (0, 21) for 1920x1080 in 1920x1200, and (0, 0) in the 1600x1200, 1920x1080 and 2048x1120 desktops. Why those origins were chosen is not stated.

## 3. Is channel 0's 720x486 a crop or scaled?

**A crop. Established from the file; observed to match.** The `CCIR601_525_DGO` channel of `1280x1024_30f` (slot 11, not slot 0) has input origin (0, 0), input size 720x486 and output size 720x486: it reads the top-left 720x486 pixels of the 1280x1024 managed area one to one. Equal input and output sizes mean no resampling (the loader marks a combination resampled only when an enabled output is smaller than its input in either axis; [combination limits](README.md#combination-limits-infinitereality-video-format-combiner-users-guide-007-3279-003)). The trace's `Resize` of 0x2d0 by 0x1e6 is that 720x486 input rectangle. **Observed** (model, `head0-after-load.png`): head 0 shows a 720x486 window onto the top-left of the desktop, cut at the same place as the full screen, which is a crop and not a scaled copy. The managed area stays 1280x1024 (the combination's managed size equals the session's, so the loader's promotion step changes nothing).

What would change it: a different combination file. The `1280x1024+720x486_30f_hdgvo` slot-14 channel reads a different 720x486 rectangle, at (280, 113), still 1:1.

## 4. What happens to channel 1?

**Not loaded and not named, so it keeps its old format and is not listed afterwards. The part about the old format is inferred; the cause of the missing list entry is inferred.**

- **Established** (the file): `1280x1024_30f.cmb` has no slot-1 record. The loader's per-slot loops walk the 15 slots and skip every slot whose record is absent or disabled, so channel 1 gets no `LoadFormat` and no new input rectangle from this combination.
- **Established** (`konal.so` 0x1485d0c-0x1485f3c for the format loop; 0x14864c4-0x148667c for the enable passes): after the format loops the callback makes two passes over every physical channel the screen has (its channel count, 2 on a DG5-2), whether or not the combination mentions it, and sends the channel-enable attribute for each (one channel, recorded at +0x4c of the module's private record, is skipped; what it is **unknown**). The display-generator side: `LoadFormat` disables the channel it loads and never enables it ([dg_requests.md](../../software/ucode/dg_requests.md), requests 22-24), so every loaded channel needs the enable at the end. **Observed** (trace): `DisableChannel` 0 and 1, the two loads, then `EnableChannel` 1 and 0.
- **Inferred:** channel 1 is switched off for the duration of the load and switched on again at the end with the format it already had (the boot combination's `640x486_30i`, blanked, per the model's `gfxinfo` before the load). Nothing in the loader reloads it.
- **Inferred:** `gfxinfo` prints no channel 1 because it lists the channels of the loaded combination, and this combination has none for slot 1; the server's channel-info handler (`ProcSGIvcQueryChannelInfo`, [Unknown above](README.md#the-screen-record-and-the-option-channels-konalso-builds)) was not read. The header's "Display has 2 channels" is the board's channel count, which the load does not change.
- **Unknown:** whether the physical channel 1 keeps scanning and what it shows. What would settle it: the enable attribute's flag word for each pass (its middle word is 0 in the second pass and the third word is read from a channel-record field that was not identified), or a `gfxinfo`/video capture of a real two-channel pipe after loading a one-monitor combination.

## 5. Are two `LoadFormat`s on channel 0 within one combination load the expected sequence?

**Yes, on a board without a GVO channel: one load per combination slot, and the GVO slot lands on channel 0. Established for the loop; inferred for the slot-to-channel table.**

- **Established** (`konal.so` combination callback 0x1483e00): after validation, the callback loops over slots 0-14 in ascending order and calls the channel loader (the routine at 0x1465500, whose first send is the cursor-priority command) once for every enabled slot whose `SourceChannel` is itself. A slot that copies another slot is handled in a second loop. So the load sequence is one `LoadFormat` per enabled independent slot, in slot order, each followed by its own `Resize` ([the step list](README.md#loading-a-combination-channel)). For `1280x1024_30f` that is slot 0 (the 29.97 Hz desktop format, then `Resize` 1280x1024) and then slot 11 (`CCIR601_525_DGO`, then `Resize` 720x486). This is the trace's sequence; it is not "desktop format, then channel format".
- **Established** (`konal.so` 0x1474d9c and 0x1476864): the channel loader turns a slot into a physical channel through a 15-word table in the private record (+0x440 + 4 x slot) and then through a list of physical channel ids (+0xc + 4 x index). The screen-record builder fills table entry c with c for each display channel it creates (0x1474d9c), and for a GVO option channel fills entry 11 with that channel's index (0x1476864, the channel with physical id 0xc6).
- **Inferred:** on a DG5-2 with no GVO option no code stores entry 11, so it keeps its initial value; the record is obtained from a count-and-size allocator call (0x147478c-0x14747f4, `calloc`-style), whose zero fill was not read. With entry 11 zero, slot 11 resolves to channel index 0, the same channel as slot 0. The second `LoadFormat` therefore replaces the desktop format on channel 0, which is what the trace and `gfxinfo` show (**observed**: channel 0 ends as `CCIR601_525_DGO`, 720x486, external sync). The earlier README's "channel 0, because a board with no GVO option has no channel id for the DGO slot" is this mechanism.
- **Not an error path in the shipped code, by the read:** nothing in the callback checks that slot 11 has a channel behind it. Whether the earlier combination checker refuses a slot-11 channel on a pipe whose option mask is 0 was not read (the model loaded it without complaint, **observed**). What would settle it: the checker's option rules for slot 11, or a real plain DG5-2's reaction to this combination.
- **Consequence for a model:** a plain DG5-2 loading `1280x1024_30f` ends with channel 0 on the 720x486 format at 29.97 Hz and a 720x486 window onto the managed area; the 1280x1024 desktop format on channel 0 exists only between the two loads. With a GVO option board the same file would leave slot 0 on its desktop format on channel 0 and the 720x486 format on the GVO channel.

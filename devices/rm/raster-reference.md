# Raster arithmetic reference: one row per stage

Scope: what the shipped software, the board's own firmware and the published sources fix about the arithmetic of the InfiniteReality2 raster path (IRIX 6.5.30m, one pipe): geometry engine output, the pixel generator, texture, the image engines and the display link. The narrower questions that came first (CRC route, snap, tie rule, guard band, clip, depth clear word) are argued in [raster-rules.md](raster-rules.md); this page extends them to every stage and repeats their conclusions as rows. No hardware was used. No IRIX source was opened and no restricted library hit was seen; only committed notes, the published documents in [references/documents/](../../references/documents/README.md) and the committed disassembly of `arm1.u` were read.

## Grades

- **established**: read in full from the board's own program (`arm1.u`, `ge.u`) or stated by a first-party published source about the shipped generation.
- **software expectation**: what a shipped host program or diagnostic sends or expects. It fixes the contract the software uses, not what the chip does.
- **inferred**: a reasoned reading, or a statement about a neighbouring generation. The reasoning is in the row.
- **unknown**: no source read states it. The last column says what would settle it.

The chip-side arithmetic (pixel generator, texture generator, texture filter, image processor) has no program, so those rows can only be bounded.

## Ways to settle a row

| Code | Route | What it can reach |
|---|---|---|
| **D** | The diagnostic's expected words (`ge_inst.s` adder, multiplier and seed tests) | Geometry-engine arithmetic only. |
| **G** | Run the shipped geometry microcode on chosen inputs (needs the operand semantics and seed tables listed in [raster-rules.md](raster-rules.md#5-near-and-far-clip-and-colour-and-depth-rounding)) | What the engine sends, never what the chips do with it. |
| **V** | The raster-bus vector files and their gold signatures (`aaspoke`, `fog1`, `linesRus`, `msalpha`, `samplemask`, `projtex`, `tex2d_detail`; gold values in `irsaudit.*.gold`) | Any chip rule, but only after the signature polynomial is known ([raster-rules.md](raster-rules.md#1-the-crc-route)). The stage a vector exercises is read from its name, which is an inference. |
| **C** | A capture of pixel output or a published chip description not yet held | Anything. Listed last because no capture exists. |

## The depth buffer and the QEMU manual page

The manual page `docs/system/mips/sgi/hardware/kona.rst` on `sgi-origami` (revision 654862dafebd) says, in its raster-memory section (lines 1119-1120 of that file), that the model's board memory holds "a 24-bit depth buffer", and introduces the layout with "No capture gives the pipe's framebuffer organisation, so board memory is the model's own layout, an *approximation*." The page never says fixed point; the model's Mesa provider (`hw/misc/sgi-kona-mesa-provider.c`) declares the depth plane as 24-bit normalised unsigned and masks words to 24 bits. The claim is therefore a labelled model choice, not a hardware statement.

Against the sources:

- **Unsupported as hardware.** No published or shipped source gives a 24-bit fixed-point depth. The format of a stored sample is a floating or compressed one (D1, D2), or a plain 32-bit integer in one configuration (D4). A fixed-point 24-bit format is not among the hardware choices read.
- **Where a 24 appears in the sources, and for which stage.** (1) The depth size field of `IMP_SZ1` has a 24 code (D3), which the firmware sets with the compress bit on, so it is 24 bits of the compressed floating word, not fixed point; this is the storage stage, inferred. (2) The display board's pixel formats include "24-bit Z" for virtual-set masking (Video Format Combiner User's Guide, PDF pp.30-31, 38-39, in [dg README](../dg/README.md)): a video-output format of depth, not the stored format. (3) The Onyx2 specification page lists "24-bit floating-point Z" (`sgidepot-onyx2-tech-specs.html`), consistent with a floating word and a rounded-up figure of the 23-bit format in TR1 and TR2. (4) The firmware rounds the host's requested depth width up to a multiple of 8 (a 23-bit visual becomes width 24 in the state block), so "24" is also the width byte, not the format.
- **Interpolation versus store versus read-back.** The sources describe the stages separately: interpolation runs in the pixel generator at a width no source gives (D5); the store is the 23/16/15-bit floating or compressed word, or a 32-bit integer (D1-D4); read-back reaches the host as a value scaled to [0, 1] (engineers' answers, inferred) through image-processor read formats that include 15-, 16-, 31- and 32-bit depth words (D4). The clear path (D2) and the render path write the same word format only if compress selects it, which is inferred.
- **Switch.** A configuration switch exists: the size and compress fields of `IMP_SZ1`, written by the buffer-configuration handler from the visual's depth width and the sample count (D3). It is established that the firmware writes these; that the fields mean what their names say is inferred from the clear handler.

Suggested correction for review, as a statement of fact and not a design: the page's sentence is accurate if read as the model's own layout; it would be accurate about the board if it said that the board stores depth as a 23-bit floating word (or a 16- or 15-bit compressed one, or a 32-bit integer in one single-sample configuration) and that no source fixes how rendered depth is rounded into it.

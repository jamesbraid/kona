# Driving an InfiniteReality pipe without IRIX

What a driver that is not IRIX has to do to load the pipe's firmware, draw text, write images, keep the command FIFO from overflowing and map host memory for DMA. Each section answers one question that a Windows NT driver design put to this workspace, and states what the shipped software does, not what the hardware must do. The first configuration read is an IP27 Onyx2 with one InfiniteReality2 pipe on IRIX 6.5.30m; the IP35 kernel objects are named where they were compared. Labels are **established** (read in full), **inferred** (reasoning given) or **unknown** (routes tried, and what would settle it). No physical hardware was read.

Sources: the IRIX 6.5.30m `usr/gfx/gfxinit` loader, `kona.a` (IP27 and IP35 builds, and the 6.5-base build for the map RAM page codes), the generic textport driver, the X server modules and the IP27 `unix`, `usr/gfx/ucode/KONA/`, the IO6 PROM image (unpacked with the chips workspace's PROM tool; addresses are in its `io6prom` segment, loaded at `0xc000000011c00000`), the IRIX 6.5.7 source tree for the Hub's Crosstalk address form, and the pages linked below.

## 1. Loading the ARM firmware

The kernel does not load firmware: `KONAdownload` returns 0 and the generic download ioctl does nothing for this board (`kona_stubs.o`). The loader is `kona_loaducode` in `gfxinit` (`usr/gfx/gfxinit`, the same file as `gfxinfo`, 0x1000ca5c). Everything below is **established** from its disassembly unless marked.

**Order of operations in `gfxinit` for one pipe** (`main`, 0x10005888-0x100066b8): ioctl 113 (super-user mapping: the host-interface registers appear at window offset 0x800000, the loader reaches them at user-window offset 0x4000 + register offset), 103 attach, 110 map the whole pipe, then the family's probe hook, ioctl 106 (`KONAinitialize`), the family's load hook (`kona_init`, a shuffle of arguments into `kona_loaducode`), ioctl 107 (`KONAstart`), the post-start hook (`kona_diagnose`), 104 detach. `KONAinitialize` does the XG widget set-up and the `HH_RESET` pulse (1 then 0), enables only the parity interrupt and fills the map RAM ([xg.md](../../devices/xg/README.md#pipe-reset-konainitialize-and-the-credit-wait-path)).

**State the board must be in.** The loader writes no stall register and no `HH_RESET` bit 1. It relies on the state left by `KONAinitialize`: the pulse returns `HH_RESET` to 0, which clears the ARM start bit the kernel's textport sets (**inferred**, from that register's name and the kernel's 3-then-2 start sequence). The ARM then runs only when the loader's last step writes `HH_ARM_UNSTALL`. What holds the ARM between the pulse and that write is **unknown: no shipped software or published source depends on it**. A driver that copies the IRIX order (pulse, load, unstall) is safe by construction; one that loads over a running EEPROM program has no precedent. The EEPROM is not read, written or checked by the loader; the load replaces the ARM's RAM image and the EEPROM program does not run again until the ARM is restarted from it (below).

**The write path.** Per word: `HH_ARM_ADDRESS` (0x3e8) takes the ARM address once, then every word is a 32-bit store to `HH_ARM_DATA_INCR` (0x3f8), which advances the address by 4. Words are stored exactly as read from the file (the files are big-endian ARM images; a little-endian host has to swap each word, and what the XG's `SYS_END` control bit does to this path is **unknown**).

| Step | Registers (window offset, user-window offset in brackets) | Notes |
|---|---|---|
| 1 | read options (below), then `HH_ARM_CTRL` 0x308 = 1; `HH_ARM_ADDRESS` = 0x200050; `HH_ARM_DATA` 0x3f0 = 1 | host access on; ARM-side control register bit 0 (`ICU_CTRL_ARMACC`) set |
| 2 | the file sections listed in [hip.md](../../devices/hip/README.md#firmware-load-into-the-pipes-memories), each by address then data-increment stores, then the section directory | order arm1.u, geif.u, ged1b.u, ge11.u |
| 3 | `HH_TFIFO_HI` 0x3b0 = 5; `HH_ARM_ADDRESS` = 0x200050; `HH_ARM_DATA` = 0; `HH_ARM_CTRL` = 0; `HH_ARM_UNSTALL` 0x328 = 1 | the `HH_ARM_CTRL` = 0 write is not in [hip.md](../../devices/hip/README.md#firmware-load-into-the-pipes-memories); the ARM runs from here |
| 4 | ioctl 107, `KONAstart`: running interrupt mask 0xf7c, write-gather attach, then the `PIPE_SETUP` command | [kernel-functions.md](../../software/kernel/kernel-functions.md) |

The ten sections and their ARM addresses are in [hip.md](../../devices/hip/README.md#firmware-load-into-the-pipes-memories). What was missing there is the **section directory** (section 10, 56 words at ARM 0x40953d8, written after the files). **Established** (`kona_loaducode` helpers 0x1000bc24, 0x1000bda8, 0x1000c208, 0x1000c424; `arm1.u` `find_ucode` 0x0c001ab0): it is a 16-word header followed by room for ten 4-word records, the layout the ARM's `find_ucode` searches by tag. `find_ucode` takes a start index and a tag, walks the slots up to ten, skips a slot whose tag is 0 and returns the index of the first match or -1; it does not read the header's record count. The shipped files fill five slots.

| Directory word | Value |
|---|---|
| header +4 | the GE occupancy mask: 15 unless `KONA_OCCMASK` says otherwise. `init_ge_config` ANDs the detected engine mask with it and ignores it when the result is zero |
| header +8 | the number of records written (5 for the shipped files) |
| header +12 | a flags word: 0x82 unless `KONA_LEATHER` says otherwise. `init_ged` tests bit 5 (0x20) and sets or clears the byte at ARM 0xcf9 from it. Its other bits have no reader |
| other header words | 0 |
| record word 0 | tag: 0x4591 distributor program (`ged1b.u`, two records), 0x4592 slot table (`geif.u`, one record), 0x4593 engine microcode (`ge11.u`, two records) |
| record word 1 | ARM address of the bytes |
| record word 2 | a per-tag value: the file chunk's first word for 0x4591; 0 for 0x4592; that word divided by 3 for 0x4593 (the ARM adds 0x200000 to it to form an engine address) |
| record word 3 | length in bytes |

The two engine files are containers: a 44-byte header whose first halfword is the tag, whose word at +12 is the offset of the first chunk, then chunks of {word A, byte length B, B bytes}, ending at a chunk with B = 0. `ged1b.u` has chunks (A 0, 0xe8c bytes at file offset 0x76) and (A 0x1000, 0x840 bytes at 0xf0a); `ge11.u` has (A 0, 0x22ad0 bytes at 0x79) and (A 0x24000, 0x947dc bytes at 0x22b51). `geif.u` has no header: 2048 bytes, 1024 big-endian halfwords. `arm1.u` is an AIF image whose 128-byte header is not loaded ([arm1.md](../../software/ucode/arm1.md#container)). **Established** by parsing the files and by the loader's reads.

**Options.** `/etc/config/gfxinit.options` (read if present) sets `kona_occmask`, `kona_leather` and `kona_verifyucode`: the file is parsed line by line, `#` starts a comment, and a line gives one of these lower-case names and a value. The environment variables `KONA_OCCMASK`, `KONA_LEATHER` and `KONA_VERIFYUCODE` (upper case) are read after the file and override it; the loader prints which of the two supplied a value. With `KONA_VERIFYUCODE` nonzero the loader reads every word back from `HH_ARM_DATA_INCR` after writing a section and rewrites up to four times on a mismatch; the shipped default is off, which is why [hip.md](../../devices/hip/README.md#firmware-load-into-the-pipes-memories) saw no read-back. **Established.**

**Can a driver skip the engine files?** The ARM tolerates the absence, the engines do not work. **Established** (`arm1.u` `init_hip` 0x0c001d4c-0x0c001d78, `init_ged_ucode` 0x0c001e74-0x0c001e94, `init_ge` 0x0c003458-0x0c003478, `init_ge_board` 0x0c003d0c, end of `init` 0x0c0041fc): each of the three tag lookups prints "could not find ... expect bad behaviour" when the tag is missing. A missing engine microcode (`ge11.u`) or distributor program (`ged1b.u`) returns early and start-up goes on; a missing `geif.u` is worse, because `init_hip` then indexes record -1: the word it takes as the source address is header word 13 of the directory, which is 0, so it copies 512 words from ARM address 0 into the slot table. The start-up ends with one engine handshake whose result nothing tests. So: **`geif.u` and `ged1b.u` are required for any host-driven drawing; `ge11.u` is required for any token routed to the engines, which includes the X pixel path of section 3.** A load that omits `ge11.u` and `ged1b.u` leaves the ARM-run tokens working in principle (colour map, gamma, window IDs, cursor, display requests: [arm1_firmware.md](../../software/ucode/arm1_firmware.md)); that is **inferred**, not read as a run. The display path needs the video combination: `arm1.u` reads it from the EEPROM flash at 0x20000 (magic 0xfacefeed) and falls back to a built-in emergency format ([arm1_firmware.md](../../software/ucode/arm1_firmware.md#start-up)).

**The textport does not survive the load** (**established**): `tport.bin` handles token 0x001 as the textport entry, and `arm1.u` handles token 0x001 as `HP_BUFFER_CONFIG` ([icu_map.tsv](../../software/ucode/icu_map.tsv)). After the load a textport sequence reaches the buffer-configuration handler. Getting the textport back needs the ARM restarted from the EEPROM program, by the kernel's write of 3 then 2 to `HH_RESET` ([hip.md](../../devices/hip/README.md#reset-and-start-of-the-arm), **inferred** to boot from the EEPROM).

**What the NT design should do.** Copy the IRIX order exactly; load all four files in the order and layout above, with the directory written last; leave the EEPROM alone; treat a bug-check screen after the desktop load as needing either X tokens or an ARM restart from the EEPROM.

## 2. Textport behaviour

The wire format and the kernel's senders are in [textport.md](textport.md); the receiver is in [tport.md](../../software/ucode/tport.md#textport-command-handler).

**How the PROM drives the port** (**established**, `io6prom` segment, board function table at image offset 0xae860, address 0x11cae860, senders 0x11c27a70-0x11c28014; the IP35 PROM's console code was not read). Every command is written by plain 32-bit uncached stores to window offset 0xc10000, one store per word. Before each command the PROM polls `HH_GFIFO_LEVEL` (0x800208), masks it with 0x7fe and repeats while it is nonzero, at most about 5000 reads (the bound is 0x1388 and the counter steps once per read) with no delay between them; it then sends the command whether or not the FIFO drained. It does not attach hub flow control, kick 0xc00108, or poll for a reply: no sender waits on anything after a command. The commands it sends are the same words as the kernel's: 1,1,flag (blank); 1,2,colour; 1,3,index,r<<2,g<<2,b<<2; 1,4,x,y; 1,5 with the same low-edge minus one and clamp; 1,6,x,y; 1,8,xsize,ysize; 1,10 with the six header words and bitmap words packed as the kernel packs them. **The PROM also sends sub-command 7 (cursor move) with both coordinates rounded down to a multiple of 4** (0x11c27d88), a command no kernel routine sends. The board function table has no sender for sub-command 9 (alive) or 12 (configuration report). Which of these the PROM's character cell routine issues per character, and in what order, was not traced (the generic console layer that calls the board table was not followed): **unknown**.

**The kernel's cell sequence** (**established**, IP27 `unix` 0xc0000000000f3b20 and neighbours, the character drawing in `htp_write`): the cell is cleared first. It calls the board's colour function with the cell's background colour, then the box function over the whole cell, then the move function, then the colour function with the foreground colour, then draws glyph and any underline. So IRIX never relies on the glyph command for the background.

**Glyph background: transparent.** **Inferred**: `tport.bin`'s `tp_blit_bitmap` (0x0c00f224) expands each glyph bit into the top bit of a 16-bit pixel slot and sends the slots to the raster path under a write-enable set up first; a clear bit is a slot with no enable. That is a mask, not a two-colour fill. What the raster board does with a clear slot is not documented; the kernel's fill-then-draw order is consistent with transparency and does not prove it. **A driver should fill the cell with a box first, as IRIX does.**

**Colour index and depth.** **Established** (`tport.bin` 0x0c00f034, 0x0c00f04c): the colour-set command stores its index only when the index is below 0x1000, so the usable range is 0-4095; the palette command takes the same bound, ignores indices above it, and stores each of three components masked to 12 bits. The kernel sends 8-bit components shifted left by 2, so the stored values use 10 of the 12 bits. The textport keeps this palette in the ARM's RAM and sends 12-bit-per-component colour to the raster path when it draws; it is not the X server's XMAP colour map. **Inferred** from the packing in 0x0c00f224. The pixel depth of the frame buffer behind it is whatever the raster boards were configured with: no textport command sets it. **Unknown.**

**Why a display-only program can draw.** **Inferred**, not settled. `tport.bin` has no geometry path of its own, but its register write, box and bitmap routines use the same mechanism as `arm1.u`: operands stored to the engine ports (0x840, 0x474) followed by a handler address stored to 0x8c0. `arm1.u` takes that address from its slot table; `tport.bin` stores constants (0x3000, 0x3028, 0x3035, 0x300d, 0x2). A handler address is an engine program address, so the engines must hold code at those addresses when only the EEPROM program is running. `tport.bin` loads none (no engine download routine matches `arm1.u`'s, [tport.md](../../software/ucode/tport.md#what-the-image-contains)), but its start-up copies two blocks listed by a table at EEPROM address 0x7ff00, which `tport.bin` itself does not contain. **The best reading is that the EEPROM carries a small engine start-up program that `ireeprom` writes with it, and that this program is what draws.** What would settle it: a saved EEPROM from `ireeprom -r` (the file is {20-byte header, 128-byte block, image}); none is held. This matters for the NT design only in one respect: the textport depends on the EEPROM contents, not just on `tport.bin`.

## 3. X pixel grammar

The token list and payload counts are in [opengl.md](../../software/opengl/opengl.md#x-server-module-drawing-commands) and [GE.h](../../devices/ge/GE.h). On IP27 and IP35 hosts the X server modules are `konal.so` and `konad.so`; they send the same tokens with the token word stored at FIFO offset 0 before its payload ([kona-ddx.md](../../software/xsgi/kona-ddx.md)).

**The image write** (**established**, `kona.so` `konDrawImage` 0x552f40 and `konWriteFBSubBlock` 0x4f9af0, with the firmware `arm_x_pix_setup`, `arm_x_pix_write`, `arm_x_pix_finish`):

1. `X_LOADGC` (0x129, 13 words) and `X_PIX_SETUP` (0x136, 7 words), both built by `kon_loadPixmapGC` (0x501690).
2. `X_LOADPOS` (0x12a, 4 words) and `X_LOADCLIP` (0x12b, 5 words: 1, then one rectangle).
3. `X_PIX_WRITE` (0x139): **two header words, then the pixels.** The firmware reads the first payload word and the next into the engine set-up together with the width and height saved from `X_PIX_SETUP` words 4 and 5; `konDrawImage` fills the two with the x and y halfwords of the destination box (**inferred** from the two halfword loads that feed the stores at token offset 0x2720). The pixel words follow with no count.
4. `X_PIX_FINISH` (0x13a, one word, 0).

**Packing.** The host sends the image as an X ZPixmap: rows padded to 32-bit words, the first word carrying the source misalignment (the low two bits of the source address, times 8, is added to the row's bit count before rounding up), words copied unchanged and in order (**established**, `konDrawImage`'s size arithmetic and its copy loops of 32, 8, 4 and 1-3 words). The row bit count is `(source offset in bits) + bits-per-pixel x width`; 8-bit pixels are four to a word with the first pixel in the high byte, 32-bit pixels one to a word (**inferred**: big-endian X server on a big-endian host; no little-endian client exists). The depth does not change the token sequence; it changes the contents of the two set-up tokens. `kon_loadPixmapGC` takes a format code from its argument (low nibble 1, 2, 4 or 8 select 8-, 16- or 32-bit and the 12/10-bit RGB cases) and fills the 13 GC words and 7 setup words from six three-entry tables indexed by a small pixel-format number: `kon_pack8src` (0,1,1), `kon_pack16src` (1,1,1), `kon_pack32src` (2,2,2), `kon_pack8dest` (1,1,0), `kon_pack16dest` (1,1,1), `kon_pack32dest` (2,2,2), the main-shift tables `kon_mainL8shift` (8,0,8), `kon_mainL12shift` (4,0,12), `kon_mainRGB10shift` (2,0,-2), `kon_mainRGB12shift` (8,0,-8), `kon_overRGBshift` (1,0,15) and `kon_overCIAshift` (0,8,8), all read from `kona.so` `.data` at 0x586fc8-0x587078. **What each bit of the 13 GC words and 7 set-up words means is not decoded.** The field assembly in `kon_loadPixmapGC` is read to the point of the table lookups; the bit-by-bit meaning needs a trace of `X_PixSetupGE` and `XSetPacker` in `arm1.u`. Until that is done a driver can only reproduce the words IRIX sends for a given visual, not derive them: **unknown**. A pragmatic way for the NT design: record the 20 words IRIX sends for the 8-bit and the 32-bit visual (by reading `kon_loadPixmapGC` with known inputs) and replay them.

**Size limit.** Images are sent through the FIFO up to a limit and through the DMA-write request (driver request 10001) above it. **Established** (disassembly of `kona.so` `konDrawImage` 0x552f40 and `konWriteFBSubBlock` 0x4f9af0, and of the matching routines of `konal.so`, `konad.so` and `konas.so`, which carry the same request number at 0x503200 and 0x55eb54 in each): both functions compare the image's byte count (`konDrawImage`: the rows rounded up to whole words; `konWriteFBSubBlock`: width times height times four) against one threshold, 0x8000 in `kona.so` and 0x9000 in the other three builds. They skip the comparison, and so never use DMA, when the pixel-format word read from the screen's format record has 1 in bits 15:12 and nothing in bits 31:28. Earlier text in this workspace gave 4096 bytes for `konWriteFBSubBlock`; that figure is in neither build.

**Display tokens** (**established** payloads, [opengl.md](../../software/opengl/opengl.md#x-server-module-drawing-commands)): `X_LOADCMAP` 0x12e, 2 + n words (colour-map address, count n, n colour words; the firmware writes display-bus register 0x118 then 0x119); `X_LOADGAMMA` 0x12f, per colour (address, count 2, 12-bit value twice), or 0xdeadfeed, 1024, then 1024 packed 10:10:10 words for the external gamma RAM ([dg.md](../../devices/dg/README.md#colour-maps-and-gamma-tables)); `X_LOADXMAP_CONFIG` 0x133, one flag word written to XMAP register 9 (1 when a window needing a hardware window ID is created, 0 when destroyed, each followed by `WG_FLUSH_1` on IP19 hosts only). The window-ID (DID) tokens and the 24-bit colour-map paths are in [dg.md](../../devices/dg/README.md).

## 4. Flow control

Two independent mechanisms exist, and only one is required to avoid overflow.

**The credit layer is in the host's Hub, not in the pipe** (**established**, `gfx_flow.o`, [kernel.md](../../software/kernel/kernel.md#flow-control-layer)). For each CPU slice the Hub has a page register that names the FIFO page (stores to that page are counted), a credit counter, a bias, and an interrupt counter and comparator. The pipe returns credits on Crosstalk transaction number 17, selected by the `XG_GFX_DET` register (0x7c; 34 attaches, 1 detaches). The driver programs the Hub in a fixed order (bias 0, credit counter, page register with bit 40, the master Hub's `IIO_IGFX` register with widget, node, CPU and valid, then, after the caller's `XG_GFX_DET` write and a wait for credits to arrive, the bias). The totals are computed from the FIFO size the caller passes (`(size >> 3)` capped at 101 in the shipped mode, bias 8 or 68). The Hub then holds stores back by itself. The counter arithmetic and the unit of the 3-bit shift are **unknown** (the Hub does it). On IP35 the flow-control object is a different build (`IP35boot/gfxs.a(gfx_flow.o)`, 16 routines against 19: it has no `gfx_flow_set_cpu_attachment`, `gfx_flow_clear_cpu_attachment` or `gfx_flow_interface_alloc`). **Established** by reading `gfx_flow_init`, `gfx_flow_attach_me`, `gfx_flow_attach_me_finish` and `gfx_flow_credit_tnum_get` in both builds: the transaction number is still 17, the three per-slice registers it programs are at the same offsets (0x300 page, 0x308 credit counter, 0x310 bias, slice stride 0x28) and in the same order (bias 0, credit counter, page with bit 40, `IIO_IGFX`, then the bias after the credit wait). What differs is the node shift (33, not 32), the field the CPU slice is taken from, the packing of the `IIO_IGFX` word (an 8-bit node field at bit 5, one more bit at bit 4 and no valid bit, where the IP27 build puts a 9-bit node field at bit 4 and sets bit 20), the interrupt comparators, which the IP35 init writes with 20000 at offsets 0x320 and 0x348 of each of two register blocks 0x200000 apart (IP27: 10000, one block), and the absence of the IP27 test of a Hub register field that can switch transaction credits off. The credit totals and what the Bedrock's `IIO_IGFX` fields mean are **unknown**: no shipped software or published source depends on them beyond this object ([its entries](../../software/kernel/ip35/readings/gfxs.a-gfx_flow.o.md) are only call-level).

**Polling the fill level is enough for a single writer** (**established** as software behaviour, **inferred** as a guarantee). The IO6 PROM drives the textport with no credit layer: it waits until `HH_GFIFO_LEVEL & 0x7fe` reads zero, sends one complete command and does not wait afterwards (section 2). The kernel's textport senders do the same wait before and after each command in addition to attaching the credit layer. The FIFO's size is **unknown**. The workspace's 2048 words ([hip.md](../../devices/hip/README.md)) is **inferred** from the 11-bit level field of the first-generation host interface (mask 0xffe); the PROM and the kernel here read the second-generation field with mask 0x7fe, one bit narrower, which by the same reasoning gives 1024, while the kernel's own high-water setting of 0x700 reads as larger than that. Textport commands are at most about 110 words (the PROM builds a glyph in a 100-word buffer and a 6-word header), far under either figure, so a command sent into an empty FIFO cannot overflow. What breaks it:

- A command longer than the FIFO, such as an image, needs the poll between chunks, with each chunk smaller than the free space; the level read comes back after the earlier stores have arrived, so poll-then-burst is safe as long as burst size plus level stays under the FIFO's size; until that size is settled, take 1024 words (**inferred**, not demonstrated).
- A second writer (another CPU, a user mapping) on the same FIFO needs the Hub credit layer or its own mutual exclusion; the credit layer is what lets many user processes write without calling the kernel.
- An overflow raises `PIO_OV` in `HH_INTR_STATUS` (bit 10), and the kernel kills the pipe ("PIO overflow", reason 13); what the pipe does with the lost words is **unknown: no shipped software or published source depends on it**. A command left half-sent is a different case: [command-cut-short.md](command-cut-short.md).
- The kernel's hi-water handling uses `HH_GFIFO_HI` = 0x700, a 0x300 raw level as the wait threshold, and the `FIFO_LO` interrupt to wake the waiter ([hip.md](../../devices/hip/README.md#flow-control-the-fifo-interrupts)). A polled driver needs none of these.

**Interrupts.** The kernel connects three vectors (XG error, host interface, geometry engine). A driver that polls can leave the host-interface interrupt masked after `KONAinitialize` (which enables only parity), but then must poll `HH_INTR_STATUS` and `HH_ARM_MBOX` for DMA completion (section 5) and for ARM events: **inferred**, no shipped software runs polled.

## 5. DMA and the map RAM

**Entry width, page codes, reset contents.** The map RAM is 32-bit entries at window offset 0x100000, one per page of the pipe's DMA address space (16 KB in the 6.5.30m driver), 262144 entries when `XG_CONFIG.MAPRAM_SIZE` is 0 (the count is the field shifted left by 15, 0 meaning 8). An entry is the 28-bit frame number in 4 KB units (bits 27:0), `INVALID` (28), a 2-bit page-size code (30:29) and `ODD_PARITY` (31) (**established**, kpm's table; mask 0xffffffff for the whole entry). The attach test stores `0x10000000 | index`, reads it back and compares all 32 bits, but the pattern only uses bits 17:0 and 28, so it shows nothing about whether bits 27:18 or 31:29 store anything (**established**). `MAPRAM_ENA_PAR` in `XG_XT_CTRL` is set before the test and the driver never sets bit 31 on any entry it writes; whether the chip generates, checks or ignores that parity bit is **unknown**: no shipped software depends on it beyond leaving the enable set, so a driver should copy the IRIX attach writes, enable bit included.

**Page-size codes.** The IRIX 6.5-base driver uses all four: 0 is 4 KB, 1 is 16 KB, 2 is 64 KB and 3 is 1 MB. **Established** as the driver's expectation (6.5-base `kona.a`, `kona_mapram_hip2.o`, read in full): `kona_xg_psize_shift_to_index` (0x0-0x77) maps a page shift of 12, 14, 16 or 20 to 0, 1, 2 or 3 and logs an error and returns 0 for any other shift; its `kona_mapram_map` (0x11c-0x2a7) takes the shift as an argument, puts the code in bits 30:29 of every entry it writes and advances the frame number by one page per entry. What the chip does with the field was not read, so this is a software expectation, not hardware behaviour. The 6.5.30m driver fixed the shift: `kona_mapram_pagesizeshiftof` returns 14 (the 6.5-base one returns 12), `kona_mapram_map` writes `0x20000000 | ((physical >> 14) << 2)`, and the IP27 and IP35 builds are instruction-identical, so code 1 is the only code any valid 6.5.30m entry carries. The attach-time fill (`0x10000000 | index`) has code 0 in entries marked `INVALID`, which says nothing about what 0 means. **A driver written against the 6.5.30m behaviour should use code 1 and 16 KB pages only.** Routes also tried: `kpm` (field names, no values), `irsaudit` (no map RAM test), the X modules and `libGLcore` (they call ioctls), the IRIX 6.5.7 source tree (no KONA code), Linux and OpenBSD (identity only).

**Reset contents: unknown.** The driver writes every entry (index with `INVALID`) at `KONAinitialize` before use and never reads one before writing it.

**The 0x9000 attribute** (**established** names, **inferred** effect). `kona_idma` and `kona_start_selectfeed` send each address as two words, `A >> 12` and `(A & 0xfff) | 0x9000`. The firmware passes the second word's bits 15:12 into the input-DMA page-offset register (`HIP2_HA_IDMA_POFF`, 0x200014), whose fields are `PSIZE` (bits 13:12), `IOMEM` (14), `COHERENT` (15) and `GBR` (16). 0x9000 = `COHERENT` + `PSIZE` 1 ([arm1_firmware.md](../../software/ucode/arm1_firmware.md#control-and-status-registers)): the transfer is coherent and the page size is the one the map RAM entry carries (the unmapped form below sends the same 0x9000 for a 4 KB page, so `PSIZE` is not simply the map RAM's 16 KB code: its meaning is open). `IOMEM` and `GBR` are never set by any sender; what they select is unknown. A driver sends 0x9000 with every address. The kernel also has an unmapped form for one page: for a physical address of at most 4096 bytes, the diagnostic map request returns a high word of `(frame number x 4) | 0x10000000` and a low word of `(offset in a 4 KB page) | 0x9000` ([kernel.md](../../software/kernel/kernel.md#diagnostic-map-kona_diag_map)). That bit 28 of the high word marks a physical page rather than a map RAM address is **inferred** there; whether the pipe accepts that form from a driver that is not the diagnostics was not traced.

**The address form from IP27's Hub.** **Established** (IRIX 6.5.7 `irix/kern/sys/SN/xtalkaddrs.h`, 6.5.30m `IP27boot/kernel.o` `hub_dmatrans_addr` 0x22b08): the source header describes a widget's memory request as a Crosstalk address with bit 47 clear and the SN0 physical address in bits 39:0, with the node number in bits 39:32 in M mode (39:31 in N mode), and `hub_dmatrans_addr` returns the physical address it is given unchanged (the chips workspace's Bridge page records the same identity for the IP27 Bridge code). So the software gives a widget the physical address itself; that the Hub and crossbar forward it without translating it is **inferred** from that and from the absence of any translation register in the path. `kona_mapram_map` writes `0x20000000 | ((physical >> 14) << 2)` for each 16 KB piece of the physical pages `alenlist_get` returns, in 32-bit arithmetic: a 40-bit physical address fits the 28-bit frame field exactly (28 + 12 bits) and the node number is part of it (**inferred** from the field width and the identity translation; the XG forwarding the full frame as the Crosstalk address is not shown by any software). **Inferred:** the widget that receives the pipe's memory requests is named to the XG by `XG_XT_CTRL.DMA_DEST_ID` (kpm's name for bits 25:22), not by the address: the driver fills that field with the interrupt target number from `xtalk_intr_target_get` ([xg.md](../../devices/xg/README.md#reset-kona_reset_adaptor), step 4), and no address bit names a widget; what the XG does with the field was not read. An address above 2^40 would overwrite the control bits. On IP35 the node number starts at bit 33: the IP35 `kona.a` shifts the node id by 33 bits where the IP27 one shifts by 32, at every place it forms a node-block address (`kona_attach` and `kona_reset_adaptor` in `kona_edtinit_hip2.o`, three sites in `kona_tport.o`), and the entry arithmetic is the same in the IP35 `kona_mapram_hip2.o`, which matches the IP27 one instruction for instruction (**established**, compared). How wide the node field is, and so how many nodes the 40-bit frame field reaches, is not settled (the chips workspace's page on IP35 graphics widget DMA, `platforms/ip35/xio-graphics-dma.md`).

## What stays unknown

| Question | What would settle it |
|---|---|
| What holds the ARM between the reset pulse and the unstall | a run of the loader against an ARM model, or a kpm dump taken between the steps |
| What the pipe does with a command cut short, and which recovery is safe | answered as far as the shipped code goes in [command-cut-short.md](command-cut-short.md); what `FORCE` does in the host interface is open |

| The meaning of each bit of the 13 GC words and 7 set-up words for 8- and 32-bit pixmaps | tracing `X_PixSetupGE`, `XSetPacker` and the GC consumer in `ge.u` for the format codes in `kon_loadPixmapGC` |
| Map RAM parity rule, and what the chip does with the page-size code | a published XG description |
| The PROM's per-character command order | following the PROM's graphics console layer from its function table at 0xae860 |
| Byte order on a little-endian host | none shipped; a published XG description |

# What the pipe does when a host command is cut short

A command cut short by a bug check swallows the words that follow it, and only an exact zero pad or a forced privileged packet recovers it. This page says what the pipe does with a half-sent command, what the IRIX kernel does when it has to cut into a stream, and what a Windows NT driver can safely do. It answers one question from the NT design; the loader, textport and X grammar are in [non-irix-driver.md](non-irix-driver.md). Only InfiniteReality is covered; the VPro and IMPACT halves of the same question belong to their own workspaces.

Labels are **established** (read in full, with address), **inferred** (reasoning given) or **unknown** (routes tried, and what would settle it). Sources: `usr/gfx/ucode/KONA/arm1.u` (IRIX 6.5.30m, addresses are ARM addresses, see [arm1.s](../../software/ucode/arm1.s)); `kona.a` in `IP27boot` (`kona_context.o`, `kona_ddrn.o`, `kona_setup.o`, `kona_sched.o`); the `konal.so` and `kona.so` X modules; the 6.5.5 `sys/kona*.h` headers. No hardware was read and nothing here was run on a pipe.

## Short answer

- A command is a token word and its payload, with no length. A short command swallows the next words as payload. **Established** (section 1).
- Zero padding recovers a cut command **only if the pad count is exact**. One word too many, in the plain stream, is a token 0, whose handler drains 100 words and then spins on the input forever, so the ARM is lost until it is restarted. One word too few leaves the pipe still inside the command. **Established** (the handler), **inferred** (that nothing else rescues it).
- The firmware has a way to cut into a stream at any word: a privileged packet that starts with the host-interface "force" kick, and the context tokens that save, clear or abandon a half-received command. IRIX uses it at the two places read, a context swap and a destroyed rendering node, which is **inferred** to be how a client killed mid-command is cleared from the pipe. The firmware side is **established**; that the force kick is what lets the token in is **inferred**; what the force bit does inside the host interface is **unknown** (section 2).
- No pulse of `HH_RESET` is shown to clear a half-received command; IRIX never uses it that way. Treat it as unproven (section 3).
- The NT design should record the exact wire length of every command, pad to it, and not use the pad as a general resync. Section 4 gives the numbers.

## 1. How the pipe finds the end of a command

The IP27 and IP35 X modules (`konal.so`, `konad.so`) and the kernel send each command as a token word (0 to 0x1ff) followed by payload words in one plain stream; `kona.so` (the IP19 build) instead stores the first payload word at FIFO + 32 x token, so the token is in the store address ([opengl.md](../../software/opengl/opengl.md#x-server-module-drawing-commands)). The NT target is the plain stream. **Established.**

Three kinds of token end differently.

**Hardware-routed tokens** (206 of 512) carry a count in their token-map entry ([arm1.md](../../software/ucode/arm1.md#entry-format)). The count is **not always the number of words on the wire**: `X_LINE` (map 2) and `X_LINE6` (map 12) are sent as 1 and 7 words after the token (`kona.so` and `konal.so` for both; `konad.so` and `konas.so` show the same stores for `X_LINE`), the next word being a new command ([opengl.md](../../software/opengl/opengl.md#x-server-module-drawing-commands), the note on polylines). So what the host interface takes for such a token is the module's wire length, and the map count is not a safe pad. **Established** for the two lengths; **unknown** what the interface does with the field (no shipped software depends on it beyond the framing).

**ARM-run tokens** (306) have no count in the map. The handler reads its own payload with loads from the host-interface window and ends by reading the "last word" port (`r9 + 0x3c`); a handler that is waiting for a word simply blocks ([arm1_firmware.md](../../software/ucode/arm1_firmware.md#the-input-loop)). **Established.** `X_PIX_SETUP` reads 7 words, `X_PIX_COPY` 4, `X_PIX_READ` 2, `X_PIX_FINISH` 1 ([arm1_handlers.tsv](../../software/ucode/arm1_handlers.tsv)).

**`X_PIX_WRITE` (0x139)** is the one long ARM-run command. **Established** (`arm_x_pix_write` 0x0c034914, `CompPixGedReg` 0x0c034cfc): it reads two header words (the x and y of the destination), then, when bit 4 of the preceding `X_PIX_SETUP` word 0 is clear, programs the stream counter at `0x200058` with a word count it computed at set-up and waits for those words to pass (`waitForDH` 0x0c022354). The count is

    bytes_per_pixel x width + (bit_offset >> 3)   = row bytes
    padded_row = row bytes rounded up to a multiple of 4
    pixel_words = (height x padded_row - (padded_row - row bytes) + 3) >> 2

with bytes per pixel 1, 2, 4, 8 for set-up word 1 = 0, 1, 2, 3, and width, height and bit offset taken from set-up words 4, 5 and 6 (`CompGedReg` 0x0c034bf0 turns the module number into the byte size and passes it on). The formula is for those four pixel sizes. A set-up word 1 of 4 or 5, the bitmap sources the glyph routines use, goes to `CompBMGedReg` (0x0c034da4) instead, which stores `height x ((bit_offset + width + 31) >> 5)` as the count (**established**, read in full, rows padded to whole words and no trim of the last row). The command is therefore 2 + `pixel_words` words long. Whether the second header word is read and dropped or is also passed on through the counter changes what the engine sees but not the total length (the counter value encodes the same words either way). With the direct-write bit set the command is the two header words only. A cut inside the pixel data leaves the ARM in `waitForDH` with the counter part-way down; the host cannot read the counter.

**Bad tokens end the ARM.** Tokens 0x000 and 0x100 (`HP_DATA`, `HP_DATA_1`) are placeholders whose entries, `arm_data` and `arm_data_1`, are each a one-instruction branch to `arm_badcmd` (0x0c0017f4). So are the seven `X_UNUSED*` tokens and 45 unimplemented GL tokens: 54 of the 306 ARM-run tokens in all. **Established** (`arm_badcmd` 0x0c0017f4-0x0c001854): it prints the current and previous token, reads and prints 100 words, then loops forever reading and discarding the input port. Nothing later is dispatched. A zero word taken as a token is therefore fatal, and a leftover pad word of zero is exactly that.

## 2. What IRIX does to cut into a stream

**The kernel's packet.** Every privileged kernel packet is: write 0x30000 to the host-interface register at window offset `0xc00108`, send the token word, write 0x10000, send the payload words, write 0 ([kona_kern.h](../../software/kernel/include/kona_kern.h), [HIP.h](../../devices/hip/HIP.h)). The two bits are `PRIV` (bit 16) and `FORCE` (bit 17) of `HH_GINTR_INFO`; the firmware sees them as `ICU_STATUS_PRIV` and `ICU_STATUS_FORCE` in `0x200060` and the privileged handlers refuse to run unless `PRIV` is set. **Established.** Read again in the disassembly for this page: `KONAdestroyddrn` (`kona_ddrn.o`) writes 0x30000, the token 504 (`CONTEXT_MOPUP`), 0x10000, the word 259, and 0, and `KONApcxswap` (`kona_context.o`) writes 0x30000 before `CONTEXT_LOAD` 505 and `CONTEXT_DEACTIVATE` 508. Only `kona_checkpipe` for the board's manager uses 0x10000 alone, the case where the kernel is acting for the context that is already current and so is between commands. **Inferred:** `FORCE` marks "this token may arrive inside someone else's half-sent command", which is why it is set exactly when the kernel acts for a context other than the one writing. The firmware never reads the bit and no source says what it does in the host interface: **unknown**.

**What the firmware does when it is cut into.** **Established**, by reading these routines in `arm1.u`:

- The data-abort vector (entry 4, offset 0x10 of the vector block at 0x0c0002e8) points at the stub at 0x0c000074. It saves every register and the status word, copies the live part of the ARM stack (from the stack pointer rounded down to 32 bytes, up to 0x1000) into a save buffer, returns to user mode at 0x0c000100, sets the word `aborted` (0x04045e98) to 1 and re-enters the dispatch loop at 0x0c00006c. So an ARM handler that is blocked waiting for payload can be abandoned and resumed. The earlier text in [arm1_functions.md](../../software/ucode/arm1_functions.md) names this word as never read and `badaddr` as the data-abort path; both are wrong: `deactivate_hip` reads and clears `aborted` (0x0c021f28), and `badaddr` is the reserved vector (entry 5, 0x0c000234).
- `arm_context_deactivate` (0x0c022188) calls `deactivate_hip` (0x0c021df8), which saves the host interface's state into the context record: the pending word count (`0x20005c`), the pass-through counter (`0x200058`), the begin/end state, the low nine bits of the current and previous token numbers, the loop address and array count, and the token-map entries of those two tokens. It sets flag bits in the record for "words still owed" (0x10), "pass-through in progress" (0x20) and "ARM aborted" (bit 0), then resets the word count, the stream counter, the begin/end state and the array count (the loop address is left). `arm_context_activate` (0x0c0209dc) restores the same registers through `activate_hip` (0x0c020978) and, if the aborted flag is set, calls `restore` (0x0c000124), which puts the stack and registers back and returns into the abandoned handler so it carries on reading. Its own message says that a context with words owed and an aborted ARM "is impossible": a half-sent hardware-routed command and a half-sent ARM-run command are different cases.
- `arm_context_mopup` (0x0c02226c), the token sent when a rendering node is destroyed, does the clearing without the saving: pending word count to 0, stream counter to its idle value (0x10000000), begin/end state and array count to 0, the `aborted` word and its companion to 0, the word at r8 + 0xcfc to 0xdeaddead (so does `arm_context_deactivate`), then sends the event the kernel passed (0x103) back through `start_kcomm` and `finish_kcomm`. **Established.** A client killed in the middle of a command reaches this through the close path (`KONAdestroyddrn`).

**Inferred:** these routines are what makes a context switch safe at any word, and the data abort is raised by the interface when a forced token arrives while the ARM is blocked on a payload read. The reasoning: the abort vector is the only exception that resumes the dispatch loop, the saved state is exactly the parser state a mid-command switch needs, and the kernel switches contexts lazily, on the next client's first access (`rrmValidateMyPcx`, [kernel.md](../../software/kernel/kernel.md)), so the previous client can be anywhere in a command. No shipped code sets the abort itself, and nothing in the firmware reads `FORCE`, so the trigger is **unknown** as hardware behaviour. What would settle it: the host-interface chip's input logic, or an emulator that models the parser.

**Kernel-side cleanup.** `KONAsuspend` (`kona_sched.o`, +0x0) flushes the CPU's write-gather buffer and waits for returned credits before the thread leaves the pipe, so the words the client already wrote are in the FIFO ahead of whatever the kernel sends next. `rrmSuspend` only prints a notice and returns for a thread that was pre-empted while holding the pipe. None of the 25 tokens the kernel sends ([kernel.md](../../software/kernel/kernel.md#commands-the-driver-sends)) completes a client's command, and the kernel could not know what an arbitrary client owes, so it does not pad. **Established** (the two routines and the sender list); the reading is **inferred**.

**GED_NOP** (0x172) appears as a pad in kernel packets (a token and one zero word after the clip and memory tokens). Its map entry is a one-word hardware-routed command, so it is a harmless filler *at a command boundary*, not a resync.

## 3. A pipe reset short of restarting the ARM

`HH_RESET` (host offset 0x300) bit 0 is the host-interface reset; the kernel pulses it 1 then 0 at attach (`KONAinitialize`) and in the credit-recovery path `kona_flow_await_returned_credits`, and `init_graphics` (`kona_tport.o`) writes 3 then 2 to start the ARM from the EEPROM ([xg README](../../devices/xg/README.md#pipe-reset-konainitialize-and-the-credit-wait-path)). **Established** for the writes. After each pulse the kernel rewrites every register it relies on and the firmware is not restarted, so nothing shows that the pulse clears the parser, the FIFO or an ARM blocked in a handler. Overflow, parity and other pipe errors only call `kona_die` and mark the pipe dead. **Unknown** what a pulse does to a half-received command; do not use it as a resync. Restarting the ARM also reloads the token map and tables and so needs the EEPROM program; the textport answer in [non-irix-driver.md](non-irix-driver.md#1-loading-the-arm-firmware) explains why our emulators cannot do that.

There are no abort or resync tokens in the plain stream. The only token that makes the parser forget a half command is `CONTEXT_MOPUP`, and it can only be recognised as a token because of the force kick.

## 4. What the NT design should do

1. **Count the words.** The miniport keeps, per command in flight, the wire length (the words after the token word, as the IRIX module sends them) and the number sent. The bug-check reset routine pads with zero words to the wire length and no further. The lengths are in [opengl.md](../../software/opengl/opengl.md#x-server-module-drawing-commands): `X_LOADGC` 13, `X_LOADPOS` 4, `X_LOADCLIP` 5 (further rectangles are `X_BDATA4`, 4 each), `X_LOADSCISSOR` 4, `X_BOX` 2 and `X_BOX6` 12, `X_RECT` 2 and `X_RECT6` 12, `X_POINT` 1, 6 and 24, `X_SPANS` 3, 5 and 13, `X_LINE` 1 and `X_LINE6` 7 (not the map's 2 and 12), `X_LINE_R` 2 and `X_LINE6_R` 7, `X_PIX_SETUP` 7, `X_PIX_COPY` 4, `X_PIX_READ` 2, `X_PIX_FINISH` 1, `X_PIX_WRITE` 2 plus the pixel words of section 1. Zero payload is harmless for the loads and draws (a zero GC or box is replaced by the HAL's own loads); a zero-padded pixel write paints black into the box it was writing, which the STOP screen then covers.
2. **Do not pad by the token map's count, and do not pad past the end.** Both go wrong silently: the first over-pads `X_LINE`, the second turns the surplus zeros into token 0.
3. **The counting is only as good as the CPU's store order.** The other CPUs are frozen at the bug check, and a frozen CPU's write-gather buffer may or may not have reached the FIFO. The miniport should flush the buffer after each command (as `KONAsuspend` does with `gfx_flow_flush_my_wg`) so that a command is either all in the FIFO or all in the miniport's accounting as owed. A command written as one burst inside the gather window may also not be split, but no source says so: **unknown**.
4. **Fallback, not default: a privileged mop-up packet.** Write 0x30000 to `0xc00108`, the token 0x1f8, 0x10000, one payload word (the kernel sends 0x103), 0. It is the IRIX way to abandon a half-parsed command and is **inferred** to work from inside one; nothing shipped sends it from a client's own context, and it also overwrites the word at r8 + 0xcfc with 0xdeaddead and sends an event to the host through the DMA area the pipe-setup packet named, so it needs the miniport's start-up to have sent that packet. If the owed-word accounting is lost this is the only recovery with a basis in shipped behaviour, but if the force bit does not do what is inferred the token is read as payload and the pipe is no worse than before.
5. **Do not rely on `HH_RESET`.**

Between commands there is nothing to do: a STOP that lands on a command boundary needs no recovery, and every X command is short except a pixel write, so the cut case is rare in practice.

## What stays unknown

| Question | What would settle it |
|---|---|
| What `FORCE` does inside the host interface, and whether the data abort comes from it | the host-interface chip's input logic, or a run of a context switch on a model of it |
| Whether a hardware-routed token's count in the map is what the interface waits for, given `X_LINE` and `X_LINE6` | the same |
| What an `HH_RESET` pulse does to a half-received command and a blocked ARM | the same; no shipped software depends on it |
| Whether a store to a token address (the IP19 framing) is accepted on an IP27 host and starts a command by address | no shipped IP27 module uses it; a model of the interface |
| Whether the CPU's write-gather buffer can split one command's words across a freeze | the R10000 gather rules and the Hub's write path, not read here |

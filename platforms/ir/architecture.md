# InfiniteReality (KONA) architecture overview

A map of the whole pipe, written from the chapters of this repository so that a reader can see how the blocks connect, which boundaries are the best documented and where the family sits among the other SGI graphics designs. It adds no new reading: every claim points to the chapter, header or binary address that holds the evidence, and carries that evidence's label.

Labels follow `AGENTS.md`: **established** (read in a binary or in a published document), **inferred** (a reasoned reading, with the reasoning in the cited chapter) and **unknown** (no shipped software or published source settles it). Configuration read: one IP27 Onyx2 with one InfiniteReality2 pipe, IRIX 6.5.30m. Binaries for InfiniteReality3 and InfiniteReality4 are not held, so statements about those rest on published documents and on the board names the tools print. Paths in the citations are under `docs/` unless they start with `software/ucode/` or name a root header.

## 1. What the pipe is made of

```
host crossbar (XIO)
   | Crosstown/Ktown cable: 800 MB/s each way, 1.6 GB/s per pipe (established, published)
   v
GE board:  XG (Xtalk widget) -- HIP (host interface) -- ARM CPU
                                  |        |  \__ video-controller bus (8-bit) --> DG board
                                  |        \_____ boundary-scan controller (all boards)
                                  v
                       distributor (1024-word program ged1b.u)
                                  v
                       geometry engines x1..4 (72-bit microcode: ge.u, ge11.u)
                                  v
                       BEF back-end chip (shadow of raster registers, output FIFO RAM)
                                  | raster bus: 64-bit data word + 2-bit mode, ready/valid flow control
                                  v
RM/TM boards (one, two or four per pipe):
   pg --pgtg scx/scy[11]--> tg ;  pg --80-bit--> tf p,q,r,s ;  tg --31+2 bit--> tf
   tg --2 x 73 bit--> tm x8 ;  tm --16 bit--> every tf (8 inputs each)
   tf --5 x 16 bit--> imp (x20 or x10) ;  imp --20 bit--> tf (return path, readback)
   imp: framebuffer memory;  imp --8 bit x2--> 160-wire video bus --> 4 XMAP inputs of 40 bits
DG board:  fm0 bridge -- VOC x2 (or x8), XMAP x4, DACs, gain DAC, encoder, option chips
```

Chip lists per board are **established** from the diagnostic netlists (`rm.md` "Chips on each board", `software/diags/netmap_chips.tsv`): the first-generation board (`rm6`, `rmtm7`) carries pg, tg, four tf, eight tm and twenty imp; `rm7` and `rm10` carry the framebuffer chips alone; `rm8` has ten `imp9`; `rm11` has ten `imp8dc` with pg, tg, four tf and eight `tm1cc`; `tm7` and `tm9` are the texture section alone. The GE boards (`ge12_*`, `ge14_*`) carry hip, ged, bef and up to eight engines. The chip-name expansions are unknown; the roles in the table below are **inferred** from register prefixes, bus widths and the firmware's start-up writes.

## 2. The host command path

**What the host writes.** The user command FIFO is a page at pipe-window offset 0xc10000 (mapped at user address 0x4000; `kernel.md` "What a process maps"). A command is a token word (0 to 0x1ff) followed by payload words. There is no length field: a routed token's map entry carries a word count, and an ARM-run token's handler knows its own length and signals the end by reading the last payload word through a special port (established, `hip.md` "The command stream as the ARM firmware reads it"). A 64-bit store delivers two words, the lower address first (the software's contract, `GE.h`). The X modules built for IP27 and IP35 hosts write the token word and then the payload at one address; the IP19 module puts the first payload word at an address derived from the token (established for the modules, inferred for which module an IP27 server loads; `software/ucode/arm1_firmware.md` "Refused tokens: begin/end, divert, bad command"). The kernel sends privileged commands (memory, context, event, DMA pool tokens) by kicking `HH_GINTR_INFO` through the alias at 0xc00108; those tokens check the privilege bit.

**DMA.** The kernel never programs a DMA engine by register. It maps host pages into the map RAM (page-size code 1, 16 KB), then sends `DO_IDMA` for host-to-pipe transfers or `START_SELECTFEED`/`FINISH_SELECTFEED` for readback, with the address pair `(A >> 12)` and `(A & 0xfff) | 0x9000`. The 0x9000 is the coherent attribute plus the page-size code (established names, inferred effect). Display lists use a DMA pool (`DMAPOOL_SETUP`) and list-DMA commands (`hip.md` "DMA").

**Routing.** 206 of the 512 tokens are routed in hardware and 306 run an ARM handler (`software/ucode/icu_map.tsv`, `ge-routed-tokens.md`, `ge-arm-tokens.md`). Of the routed ones, 54 run the engine handler at index (command number & 63) of a 64-entry table the ARM loads into the distributor (matrix, X-server, map-grid, deformation and texture-bind commands), and 152 (vertex attributes, begin/end, primitives) go through the distributor program. A routed map word is the distributor's 24-bit control word in one of three forms (121 geometry, 71 pass, 14 register or pixel); the geometry fields are attribute offset, entry number, vertex, float, unsigned and normalise flags, defaulted components, valid bytes of the last word and component size (established, `software/ucode/ged.md` "The token-map entry is the distributor's control word"). Of the ARM-run tokens, 54 point at a bad-command handler a working driver never reaches, and the rest keep state, build pixel and texture paths, serve queries, drive the display and manage contexts (`software/ucode/arm1_firmware.md` "The 306 ARM-run tokens by kind"). The ARM can turn routed matrix tokens into ARM tokens and back at run time.

**What the engines do and what leaves the GE board.** The ARM reaches the engines by storing operands to decoded ports of the host-interface window and finally a handler address (taken from `geif.u`, 452 handlers) to port 0x8c0 (`software/ucode/arm1_firmware.md` "How a handler reaches the engines"). The engines then run `ge.u` code. Three kinds of word go onto the raster bus (`rm.md`):

- *Register writes.* The ARM sends engine command 128 (or 159 for the image-processor variant) with a select word, an address word `(0x110 + i) << 16 | register`, and the value. The select word is the bit mask of the shadow slot (bus index 7), the 89-word shadow records the value, and a bus word with the register index in bits 62-48 and a 48-bit value in bits 47-0 is produced (established for the sends, inferred for the chip's action; `rm.md` "The register-write word").
- *Vertex packets.* Mode 3 closes a vertex's first word (command nibble, x, y, high depth bits) and mode 2 its second (rest of depth, colour) (inferred; `rm.md` "Bus modes 2 and 3"). The vertex layout is established from the diagnostic's builder: a 4-bit command, x and y as unsigned 12.8 fixed point, 32-bit depth, four 13-bit colour fields (8191 is full scale). Commands: 2 single point, 0 a vertex that does not complete a triangle, 6 and 7 triangle-completing vertices (strip and fan rules, inferred), 0 then 4 or 14 for lines. The engines' triangle output stores one vertex at a time with no reciprocal, edge or slope arithmetic (`software/ucode/ge_compute.md`, the triangle output section). Texture-coordinate packets use codes 10 and 11.
- *Pixel and texel words.* The last engine stage of a pixel path (an output module) stores through tag addresses whose low bits carry the bus mode, using format codes 0x0 to 0xf and 0x12 to 0x17 that fix how one 64-bit word packs components (`rm.md` "Pixel and texel data words").

Primitive set-up (edge equations, slopes) therefore happens in the pixel generator, not in the engines (inferred; the SIGGRAPH 1997 paper, published, says the geometry-to-raster bus carries only screen-space vertices and that the fragment generator assembles strips and fans and computes slopes).

## 3. Raster boards

**Register set.** Registers are named by a 15-bit index with up to 48-bit values (established from the kpm table, `RM.h`): `PG_` 0x800-0x880, `TG_` 0xc00-0xc06, `TM_` 0x1000-0x13d5, `TFP_` 0x1401-0x153f, `TFT_` 0x1800-0x1858, `IMP_` 0x1c00-0x1c3f, `TML_` 0x5000-0x53ff, and combined names (`PGTG_`, `TGTM_`, `TGTMTFT`, `PGTFPIMP_`, `TGTML_`, `COMMON_`) at 0x3be0-0x3ff8 and 0x7fc0-0x7fc5. Each prefix names a chip type (inferred, backed by the firmware's start-up routines writing their own prefixes); a combined index reaches every chip its letters name. All four tf chips answer both `TFP_` (fog, texture environment, alpha; fed by pg) and `TFT_` (lookup tables, filters; fed by tg) (inferred from the netlists, the filter's self-test RAM list and the diagnostic's pixel-to-filter map). Broadcast to several RM boards and the per-chip decode of combined indexes are unknown.

**State grouped by stage.** The 89-word shadow in the BEF chip lists the state a context switch must restore, in order: host-interface pack mode and output-DMA line length and stride (words 0-2), pixel and texture generator scissor, depth rectangle, display rectangle, sizes and enables (3-20), multisample locations (21-22), `PG_` general, special, bloat, depth offset, mask, window offset, sample mask, stipple (23-35), `IMP_` configuration, operation, multisample, clip, sizes, depth clear, bank addresses, blend, write masks (36-46), the host pixel format (47), texture load and draw registers (48-74), and `TFP_` alpha, texture, environment, fog, formats (75-88). Start-up values: `software/ucode/befshadow.tsv` (established). The ARM's address word for a write is `0x110 + i` in its high half for all 64 constants in the image (established).

**Primitive set-up.** Positions reach the pixel generator on a 1/256-pixel grid (unsigned 12.8). The multisample location register gives each sample 3-bit x and y within the pixel; the firmware loads (0,0), (2,1), (6,6), (7,3) and the diagnostic (0,0), (1,3), (3,1), (2,6) (established). The published technical report states 8 x 8 sub-pixel accuracy with one, four or eight samples per pixel. Edge slope formats, tie rules and iterator widths are unknown (`rm.md` "Set-up arithmetic: what the software fixes").

**Pixel ownership and memory.** The diagnostic maps a pixel id to one of four filters by (id / 2) mod 4 (`irsaudit` 0x100cf0ac, called from 0x100cecdc; established function, inferred meaning). Which imp owns a pixel, how a pixel id derives from screen position and the number of RM boards, and the framebuffer and texture memory address maps are unknown. What is known: the framebuffer is 80 MB per first-generation RM (twenty imp, each four 1 MB cores; published), and the bank bases for colour, mask, stencil, depth and accumulation are 6-bit fields of `IMP_ADDR` (established); texture memory is split into two equal banks holding even and odd levels (published rule, `TM_DRAW_TEXMAP_3DM_*` inferred), texels are 16 or 32 bits, a 4K-entry 12-bit area is reserved for texture colour tables, and clip-map regions are at most 32K x 32K (15-bit centre fields, log2 size packers at `arm1.u` 0x0c036688 and 0x0c036810; established).

**What software can observe.** The raster chips have no DMA, interrupt or error pin (established negative from the netlists, `rm.md` "Moving data in and out of the raster boards", "Interrupts"), and the saved context image has no raster-board record (`rm.md` "Context save and restore"). Pixels and texels come back to the host only as the packed image the host interface writes under the pack mode, line length and stride in shadow words 0-2, selected by `IMP_OP` bits 14-17 (colour index, red, green, blue, alpha, stencil, depth planes and packed RGBA8, RGB10A2, LA16, Z32, RGBA12) or by `TFP_TEXRB` and `TM_RDBK_*` for texture memory. The diagnostics compare chip CRC signatures, not unpacked words. The internal reply bytes on the 16-bit readback bus are unknown. Framebuffer and texture memory contents are moved by the kernel's memory commands, not by the context switch (inferred).

## 4. Display

The video output controller (VOC) fetches its channel's window in tiles of **160 x 8 pixels**, counted in groupxels of four. A line is asked for as up to three request words (START, repeated MIDDLE, END) holding tile count, groupxel count, a valid bit and a repeat count; each field gets a first tile address (tile row x tiles per row + x / 160); the pan is (x mod 160) / 4 with x mod 4 in the top bits (established, `dg.md` "The video requester"; the tile size agrees with the published combiner guide). The framebuffer chips feed four XMAP chips over 160 wires, 40 per XMAP; requests return on two nets. The bit order on the wires is unknown. The wire-to-chip assignment is established (`rm.md` "Display and scanout from the raster boards"), but the netlist does not say which pixel bit rides which wire; what would settle it is a probe of one XMAP's pixel inputs while a window of a known pixel value is scanned out (hardware proposal first).

The VOC contains a sequencer loaded from the `.vfo` state tables (line types with edge masks and 14 output signals with edge slots; `dg.md` "VOC registers", `display-formats.md`). Formats carry 10 or 12 bits per component, optionally with alpha (12 only for RGB). The XMAP is reached through bus addresses 0x100-0x11f: cursor channel, glyph base, position and enables (0-3), the copy-buffer strobe (4, written 1 after every group of writes), and indirect ports 0x118-0x11f for colour map and cursor data (0x119), gamma (0x11b), display-id table (0x11c) and channel setup (0x11d), closed by writes to 0x11e and 0x11f (established; the closing roles are inferred). Colour maps are 32K or 128K entries; gamma has an XMAP form and a 10:10:10 external form (`dg.md` "Colour maps and gamma tables"). The hardware cursor is 39 slots of 260 words in the XMAP's colour-map RAM (inferred location, established layout: 64 rows of four words, two 64-bit planes, value = A << 1 | B, four 10:10:10 colours in words 256-259; `dg.md` "Cursor memory"). The kernel keeps 32 channel rectangles for cursor ownership, smaller priority value wins (established).

Interrupts: `HH_INTR_STATUS` bit 3 (video: retrace sequence, cursor update, swap completion) and bit 9 (VOC: genlock); the status bits and their offset are in `devices/hip/registers.toml` (`HH_INTR_STATUS`, bit 3 and bit 9 included; the register is at the offset `HIP.h` gives, not at any address in this chapter); the retrace sequence number is read from `HH_SEQID`; the master VOC's status bit 7 toggles each frame (established; the exact condition and timing of bit 3 is unknown; `dg.md` "Interrupts"). Channels are two (DG5-2) or eight (with the VIO5H daughterboard); a combination holds up to 15 channel slots with per-slot DAC rate limits; the emergency combination is a single 1280x1024 at 60 Hz format from `arm1.u` 0x040402c8 (`dg.md` "Combination limits").

The kernel textport uses a second ARM image, `tport.bin` (the EEPROM boot program in `ireeprom` format, magic 0xbadc0ffe, revision 0x83): it has the same 93 display requests and a textport token 0x001 whose sub-commands 1 to 10, 12 to 15 and 20 blank, set colour, define palette entries, move the text position, draw a box or point, move the cursor, initialise the console for a size, draw a glyph, report the board and show the start screen (established, `software/ucode/tport.md` "Textport command handler"). It draws with raster-bus vertex commands (a box is commands 0, 0, 6, 7). The names of the sub-commands are unknown.

## 5. Synchronisation and ordering

- **ARM mailbox** (`HH_ARM_MBOX`, status bit 4): 0 carries a text character stream (the host writes 0x10 to the status register to let the firmware send the next), 0x100 input DMA done, 0x102 swap-in complete, 0x103 context-activate done. **Engine event record** (status bit 5, own interrupt vector): a page of host memory named by the `PIPE_SETUP` token holds a code and three arguments; the kernel poisons word 0 after reading. Codes: 0x100 select-feedback done (slot, remaining bytes, status; overflow flag 0x800), 0x101 context deactivate done, 0x102 swap-out done, 0x103 mop-up done, 0x104 suspend (a count and a list), 0x105 pipe check. Each code except 0x101 is a payload word of the command that asks for it, so the event is posted when the ARM reaches that command in stream order (established, `hip.md` "Geometry-engine events", `ge.md` "Engine events"). Code 0's sender is unknown.
- **Swap** is a stream sequence, not a register write: `VALIDATE_BANK`, `DISPMODE` (drawable word, index, mode byte), `RETRACE_SEQID` with a number, then a wait for the video interrupt and `HH_SEQID` at or above that number. Swap groups use `SWAP_CNTRL` (writes the swap strobe, display-bus address 0x80); the last group member in mode 2 sends `HP_TBUS_1` with 0x478478 twice; multi-pipe networks use `DPLEX_SWAP` (established, `dg.md` "Buffer swap and retrace wait").
- **Readback ordering**: `START_SELECTFEED` programs the output DMA, the GL commands produce the data, `FINISH_SELECTFEED` posts event 0x100 with the remaining byte count (established).
- **Watchdog**: every half second the kernel reads `HH_TBUS_STATUS` bit 2 (`TBUS_ACTIVE`) and writes it back; with neither raster-bus nor ARM activity it reports "Pipe hung" and kills the pipe. `TBUS_DRAW` (bit 0) is written 1 at each video interrupt and `TBUS_STALL` (bit 3) at death; what sets them is unknown (`kernel.md` "`HH_TBUS_STATUS`").
- **Flow control**: the kernel waits when `HH_GFIFO_LEVEL` exceeds 0x300 words (set point 0x700) and uses the FIFO-low interrupt; credits return through Xtalk (`XG_GFX_DET`). FIFO, PIO and input-DMA overflow, parity and XG errors are fatal to the pipe (death reasons 10, 13, 14, 22, 12).
- **Context switch**: the kernel sends `CONTEXT_DEACTIVATE`, `CONTEXT_LOAD`, `CONTEXT_ACTIVATE`, `CONTEXT_MOPUP`; the image in a 64 KB host buffer has a 0x52-word header, 3-word records (tag, length, an unread third word), engine records, ARM-side sections and the distributor's 255 registers, ending each record with 0xedededed. A half-received command survives because the previous-token register and in-begin flag are saved and the activate handler is re-installed at that token's map entry (established, `ge.md` "Context save and restore"; engine record order inferred). The kernel treats the image as opaque.
- **Recovery**: 16 death reasons; a reset pulses `HH_RESET` (1 then 0) after `kona_reset_adaptor`, re-initialises flow control and re-runs map-RAM initialisation unless in the credit-wait path, which expects the map RAM to survive (`xg.md`).

## 6. The X server path and the GL path

Both use the same FIFO, token map and per-context rules. The X module (`kona.so`, `konal.so`, `konad.so`, `konas.so`) sends state tokens (`X_LOADPOS` 4 words, `X_LOADGC` 13 words naming foreground, background, write masks, configuration, raster op, address, blend and three format words, `X_LOADCLIP`, `X_LOADSCISSOR`), drawing tokens in 1, 6 or 24-item forms (`X_POINT*`, `X_RECT*`, `X_BOX*`, `X_SPANS*`, `X_SEGMENT`, `X_LINE*` with relative and background-colour variants), pixel tokens (`X_PIX_SETUP`, `X_PIX_WRITE`, `X_PIX_FINISH`, `X_PIX_COPY`, `X_PIX_READ`), stipple tokens, and display tokens (`X_LOADCMAP`, `X_LOADGAMMA`, `X_LOADCURSOR`, `X_LOADCURSORCOLOR`, `X_LOADXMAP_DID`, `X_LOADXMAP_CONFIG`). Each is documented word by word in `opengl.md` "X server module: drawing commands". `X_INIT` is never sent.

The X drawing tokens are hardware-routed, not ARM-run (`software/ucode/arm1_firmware.md` "The 306 ARM-run tokens by kind"), and the engine program carries modules for X entry, set-up, load and clip-draw plus an X pixel-output module (`software/ucode/ge.md`, `rm.md` "Pixel and texel data words"). So X rendering runs on the engines and ends in raster-bus vertex and pixel words, the same destination as GL. The ARM-run X handlers (colour map, gamma, cursor, display ids) write the display bus through the engine's display-bus handlers. libGLcore sends from the dispatch table at `__glkonim_dispatchState` (472 words); vertex attributes are routed tokens, images are `DRAWPIXELS` (8 header words), `DRAWTEXELS` (20) and `BITMAP`, whose inline length the firmware computes from the unpack state (`ge.md` "Pixel images"), and display lists and vertex arrays work by DMA and by rewriting map entries.

Its host is the IP27 board set; the pipe is named `KONAL` and an IP27 server loads `konal.so`.

## 8. What each software stage touches

- **Start and `hinv` identification.** The kernel starts a pipe that does not answer with `HH_INTR_INFO` 0 and `HH_RESET` 3, a read-back, then 2 (`init_graphics`), and reads the firmware state word by taking host access to ARM memory (`get_eeprom_state`: `HH_ARM_CTRL`, address and data ports 0x3e8 and 0x3f0, ARM address 0x87ff00). The kernel at attach reads the widget id (XG 0x04), map-RAM size (0x64), writes and reads the map RAM, reads display-bus addresses 0x8800 and 0xb00, reads serial pages through the one-wire port (XG 0x9c) and receives the configuration record from the ARM (a count of 0x1de followed by 478 words). No PROM image is held; the start sequence the kernel uses is in `hip.md`.
- **Textport.** Token 0x001 sub-commands (section 4) through the FIFO, drained and flow-controlled by the kernel, plus a stored or emergency video format loaded by the display requests.
- **X desktop.** The tokens of section 6, the display requests (`LoadFormat` 383 words, channel enable, cursor, gamma, blanking, video initialisation), `DISPMODE`, `RETRACE_SEQID`, the video interrupt, `GE_INTR` events 0x100 and 0x105, DMA readback for large reads, clip and buffer validation, context switches between server and clients, and the watchdog bit.
- **OpenGL.** Everything above plus the GL token families, texture download and bind tokens, pixel paths, display lists with DMA, vertex arrays, queries by readback (`RDATA_SETUP`), select and feedback, and the raster registers of section 3.

## 9. Open questions that shape any reconstruction

Set-up arithmetic and the strip or fan bit of vertex words; packet boundaries of bus modes 2 and 3 and the meaning of tag bits 16-17; pixel to image-processor mapping and memory address maps (no software depends on them); register and memory contents of the raster chips after reset; host-interface internals (split of a 64-bit store, the divert path, reset value of the low-water mark); engine details if the microcode were interpreted (unit-2 codes 0x2f and 0x3f, input-FIFO operation, register-write latency, the distributor's engine selection rule); IR2E, IR3 and IR4 chip lists and registers; display `hwd_mode` bits 2-4, clock chip PLL codes, wire bit order, cursor channels above 7; names of the textport sub-commands. The routes already tried are in `open-questions.md`, in the sections "Geometry engine program", "Raster and texture boards (RM, TM)", "Display generator (DG)", "Host interface (HIP)" and "ARM firmware".

## 10. Where the design sits among SGI graphics families

This section compares this repository with the IMPACT workspace (gr4, https://github.com/techomancer/gr4) and the VPro workspace (odsy). Comparison claims are inferred from the cited chapters; the underlying facts carry their own labels in those repositories.

| Boundary | IMPACT (MGRAS) | InfiniteReality (KONA) | VPro (BUZZ) | Grade |
|---|---|---|---|---|
| Host interface | HQ3/HQ4: microcoded sequencer, three FIFOs, a host address generator for 2D DMA, a 32-entry graphics TLB for virtual DMA, master of the display control bus, and a direct raster-register window at 0x7C000 (+0x7D000 executes) (the 32-entry TLB with 4 KB pages is established in gr4's decode header; the window offsets are read there from its address-map header only, inferred here; neither was re-read in this repository) | HIP: hardware token router with a 512-entry map, plus an ARM CPU; map RAM in the Xtalk widget instead of a TLB; video-controller bus to the display board; raster bus reachable only through tokens | the graphics chip is itself the widget; command FIFO is the first 16 tiles of board memory (128 KB), command words carry a register-block id and count | inferred |
| Geometry | one or two GE11 engines with 72-bit microcode; **the engine does triangle set-up** and streams edge and slope registers to the raster engine | GE11-family engines (same 72-bit word, same diagnostic program: `software/ucode/ge_isa.md`; same register offsets 0x40000-0x40038 in `GE.h`), plus distributor and ARM firmware; **the engine emits vertices** | one chip with downloaded transform microcode; window positions truncated to 1/256 pixel | inferred |
| Raster | RE4 walks edges from slope registers; PP1 applies per-fragment tests; state in RE4/PP1/TE1 register groups | pg, tg, tf, imp: fixed function, 15-bit register index space, state shadowed per context | one ASIC; rules recovered by matching stored simulator frames | inferred |
| Texture | TE1 plus Rambus texture RAM (1 or 4 MB), loaded as pixel blocks through the raster engine's transfer unit | tg, eight tm, four tf; two banks by level parity; loaded by texel words and `TGTML_TEXLD_*` registers | texture state blocks; texture shares board SDRAM with the framebuffer | inferred |
| Framebuffer ownership | pixel (x, y): raster engine y mod n, pixel processor x mod 2, rotating memory chip, 192 x 16 tile per raster engine (inferred: gr4 labels these formulas a working model, not read from a binary, and says a trace of memory writes for single pixels would settle them; this column was not re-read here) | imp chips with private SDRAM; ownership not read; filters own pixels by (id / 2) mod 4; display tile 160 x 8 | one board memory in 16 x 16 tiles | inferred |
| Display | VC3 timing SRAM and cursor, two CMAP colour tables, XMAP inside PP1 (no gamma), DAC with gamma | VOC sequencer fed by `.vfo` tables, external XMAP with colour map, three gamma RAMs, cursor memory and display-id table | PB&J behind a display FIFO; swap and retrace registers per slot | inferred |
| Context switch | HQ3 microcode saves into engine external RAM slots, a 63-word image by PIO; raster state not saved | ARM saves host-interface, ARM and engine records into a 64 KB host buffer; raster state not in the image | doorbell with a 7-bit slot, board writes a record to host memory, kernel replays shadow words | inferred |
| Sync | HQ3 flags and interrupts | mailbox, event record, retrace sequence number, swap groups | five interrupt sources, per-slot swap registers | inferred |
| X and GL | X server writes raster registers directly and keeps its own shadow; GL goes through the engine | X tokens use the same FIFO and run on the engines | X module writes the same command words as GL | inferred |

What the families share is structural: an Xtalk credit-return protocol (transaction number 17 in both this repository's `xg.md` and odsy's `buzz.md` section 1), a per-context command parser that keeps a half-received command across switches, a shadow-and-replay or save-to-host context mechanism, and an XMAP, colour map, cursor and display-id composition at scan-out. What is specific to each: token tables and payloads, raster register maps and bus words, texture formats, set-up arithmetic (vertices in on KONA, slopes in on IMPACT), memory-management commands, context images and display timing programs.

Two facts for the sibling repositories: the GE11 register offsets and the 72-bit word are common to this repository and gr4 (931 words of the diagnostic program are identical in both, `software/ucode/ge_isa.md`); odsy's recovered raster rules rest on stored simulator frames with matching checksums, a kind of reference this family lacks (its diagnostics store chip CRC signatures for scan-chain tests, `rm.md` "The diagnostic data files").

# How the ARM firmware (arm1.u) is built and what each token handler does

Structure of `usr/gfx/ucode/KONA/arm1.u` (IRIX 6.5.30m): start-up, the loop that takes host commands from the host-interface chip, the way a handler reaches the geometry engines and the host, and the 306 tokens the firmware runs itself. [arm1.md](arm1.md) covers the file container and the token map; this page reads the code behind it. [arm1_functions.md](arm1_functions.md) explains the remaining named functions and data symbol by symbol, grouped by family.

Facts are labelled **established** (read from the firmware at the address given), **inferred** (with the reasoning) or **unknown**. Addresses are ARM addresses: code and read-only data from 0x0c000000, initialised data from 0x04040260. [arm1.s](arm1.s) is the listing. [retools/tools/kona/arm1_handlers.py](../retools/tools/kona/arm1_handlers.py) writes [arm1_handlers.tsv](arm1_handlers.tsv) (one row per ARM-run token), [dg_dispatch.tsv](dg_dispatch.tsv), [ged_bound_table.tsv](ged_bound_table.tsv) and [hw_route.tsv](hw_route.tsv). It scans each function straight through and follows no branches, so a handler that reaches an engine handler through a callee lists the callee and not the handler.

## What the ARM sees

Two base registers are set at entry and never change: **r8 = 0** (the ARM's own RAM, addressed as r8 + offset) and **r9 = 0x00200200** (the host-interface window). **Established** (`start` 0x0c00002c and every vector entry load them).

**Established** (offsets used by the code) and **inferred** (what they hold):

| ARM address | Use |
|---|---|
| r8 + 0x00-0x3f | exception vectors; `init_arm` (0x0c001aec) copies the 16 words at `vector_start` here |
| r8 + 0x48-0x147 | `gepc[0..127]` packed two 16-bit handler addresses to a word ([arm1.md](arm1.md)) |
| r8 + 0x258-0x75c | shadow of GL state the handlers keep (cull-face value at 0x258, matrix mode at 0x73c, cull-enable byte at 0x75c) |
| r8 + 0x860 | sticky GL error: two bytes read big-endian; `set_error` writes only when it is zero, so the first error stays until `arm_geterror` clears it |
| r8 + 0xc98-0xca4 | read-back setup written by RDATA_SETUP (address pair, length) |
| r8 + 0xd00-0xfff | stack, filled with 0xdeadbeef at start-up as a canary (`init_arm`) |
| 0x00400000 + 4 x token | the token map ([arm1.md](arm1.md)) |
| 0x00200000-0x002000ff | host-interface control and status registers (below) |
| r9 + 0x000, 0x03c, 0x040 | payload ports: read-only |
| r9 + 0x200 | next-handler fetch |
| r9 + 0x400-0x9ff | engine ports: write-only |

### Control and status registers

Offsets are r9-relative negatives of the form r9 - 0x1b0; the table gives the absolute ARM address. Register and field names come from `kpm`'s table of the ARM-side registers (IRIX 6.5.30m `/usr/gfx/KONA/bin/kpm`, 227 records of 60 bytes from vaddr 0x100b72c8, the same record layout as its host-interface table; extracted to [arm1_registers.tsv](arm1_registers.tsv)). The IR diagnostic `irsaudit` uses the same names for the registers it tests ([docs/hip.md](../docs/hip.md#arm-side-register-names)). What a field does is the firmware's use of it unless labelled. `kpm` itself reads these registers through `HH_ARM_ADDRESS` and `HH_ARM_DATA` into its post-mortem dump (`hipInspectionPostJtag` 0x10013cdc) and interprets a few of them in `show_overview_section` (0x1000dc90) and `analyze_hip` (0x100173a0); those uses are cited where they add something.

The firmware's reset code that clears every 0x20th byte of a 4 KB window at 0xa00000 is therefore a clear of the cache tags.

## Start-up

**Established** (`start`, `init_arm`, `init`):

1. The reset code (0x0c000000) writes zero to every 0x20th byte of a 4 KB window at 0x00a00000 (**inferred:** a clear of cache tags, from the 32-byte stride), then enters `start` (0x0c00002c), which sets r8, r9 and the stack, calls `init` (0x0c004108) and falls into the input loop.
2. `init` reads the simulator bit, prints a banner ("Welcome to ARMLand", the build version and "InfiniteReality/Reality Software, IRIX 6.5 release"), clears three bookkeeping words in the data block if not simulated, and records the end of the zero-initialised data as the free-memory base.
3. `init_jtag` finds the boards on the scan chain (`init_kona_jtag_chain`, `init_config`: geometry, raster and display boards, their chip ids and serial numbers).
4. `init_ge_board` (0x0c003d0c) runs `init_ge_config`, `init_ge_jtag`, **`init_arm`** (vectors, canary, the saved-context areas), **`init_hip`** (token map, below), **`init_ged`** (distributor program, tables and the handler table), **`init_ge`** (finds the geometry-engine microcode with `find_ucode`, loads it, and starts the engine-side initialisation handlers `mgeb_GlobalInitialize` and `mgesi_SetGeId`) and `init_bef` (`init_befshadow`; the "bef" chip is on the scan chain, where `bef_set_ge` and `bef_set_numges` select the current engine and a 16- or 32-bit input).
5. Unless simulated, `dgFetal` runs (the display-generator state built from scratch, below); then `init_rm_board` (`init_pg`, `init_tf`, `init_tg`, `init_tm`, `init_imp`: the raster-board chips, each set up through scan-chain registers and engine-forwarded register writes) and `init_dg_board` (`dgAutoInit`, blanking all channels first).
6. Three 16-bit values assembled from the bytes at r8 + 0x40-0x45 go to the data block (+0x84-0x8c), `mem_init` sets up the swap-memory records and `check_pipe_sync(1)` waits for the engines' mailbox handshake (`geMbox valid & correct` in its messages).

**Established** (`dgFetal` 0x0c009628, `arm1.u` 6.5.30m). `dgFetal` pushes a zero word and calls `DoDGRqstFetal` with a pointer to it, the same handler the host reaches as display request 17. `DoDGRqstFetal` never reads its argument (it overwrites the first argument register before any load), so the wrapper is simply that request run from inside the firmware: it rebuilds the display generator's state record and puts the XMAP, every present video output chip, the video and gain DACs, the encoder and the option boards into their default state (`dgMake*Fetal`, [docs/dg.md](../docs/dg.md)). It has two callers: `init` at start-up, and `DoDGRqstAutoInit` (call at +0x4724) when the video combination held in the flash PROM fails its check (the word 0xfacefeed and a length under 0x8000 read with `eeprom_read` from 0x20000) or fails to load. That path prints "flashprom combo image failed to load, loading EBF...", runs `dgFetal`, then loads the built-in emergency format named by `pEmergencyBackupFormat`.

`init_hip` (0x0c001c60) builds the token map and fills `gepc` from `geif.u` ([arm1.md](arm1.md)). Two details **established** here that [arm1.md](arm1.md) did not state: tokens the list does not reach get the `arm_badcmd` entry only in the hardware copy at 0x00400000, not in `icu_map`; and `init_hip` finally stores `arm_bgnend` at 0x20006c and `arm_divert` at 0x200054.

## The input loop

**Established.** After `init` returns, `start` runs the loop at 0x0c00006c: `mov lr, r4; ldr pc, [r9, #0x200]`. Every handler returns with `mov pc, lr` (or ends `ldr pc, [r9, #0x200]` itself), so each command is: read r9 + 0x200, jump to it. **Inferred:** a read of that register returns the handler address of the next host token, taken from the 0x00400000 table and stalling the ARM until a command is available; the ARM never reads a token number to dispatch. The data is the 28-bit address shifted left by 4 that `init_hip` stored; the low four bits are the entry's flags and are dropped by the hardware.

**Established.** A handler pulls its payload words with reads of the payload ports: r9 + 0 (next word), r9 + 0x3c (the last word of the command) and r9 + 0x40. **Established** uses of + 0x40: the last word a handler reads before it hands the rest of its payload to the pass-through counter or to DMA (`arm_copylist_ldma` reads its count there, `arm_do_idma` its fifth header word, `load_*_ge` the first data word, `arm_x_loadcursor` the cursor address). **Inferred:** + 0x40 reads the next word without consuming it: `arm_x_loadcursor` peeks the address there, then starts the pass-through counter for 261 words, the address plus the 260-word block, so the peeked word is moved again by the hardware ([docs/opengl.md](../docs/opengl.md#cursor-the-select-cursor-kona-driver-request-10005-x_loadcursor-x_loadcursorcolor)). `arm_arm_nop` (0x0c022d70) shows the shape: read a count, read count - 1 words from r9 + 0, then the final word from r9 + 0x3c, and compare it with the expected value. Every ARM-run handler with a payload ends with the r9 + 0x3c read (the `final` column of [arm1_handlers.tsv](arm1_handlers.tsv)). **Inferred:** the read at + 0x3c tells the hardware the command is over; ARM entries in the token map carry no word count, so the handler alone knows how long its command is. A handler that does not read (`arm_kernel_private`, `arm_texload_setup`) just returns; whether the hardware discards the payload then is **unknown**.

### Refused tokens: begin/end, divert, bad command

- **Kind bits.** Bits 1-2 of an entry are 0 for 392 tokens, 1 for 12, 2 for one and 3 for 107. **Established** from the map: kind 1 is the eleven `BEGIN_*` tokens and `BEGIN_SUBDIV_PATCH`, kind 2 is `END` alone, and kind 3 covers the vertex attributes (colour, index, normal, texture coordinate, vertex, material, evaluator and packed-vertex tokens), `EDGEFLAG`, `SETERROR`, `SKIP2/4/5`, `DEFORM`, `SETCOLORNORMAL`, the list-execution and vertex-array-loop tokens, `POINTPARAMETERF/FV`, and `DO_IDMA`, `GED_VERIF_DUMP`, `CONTEXT_MOPUP`, `CONTEXT_ACTIVATE` and `CONTEXT_DEACTIVATE`. **Inferred:** kind 3 marks commands that may arrive between a begin and its end. The reasoning: the vertex data, edge flag and list calls are the commands the GL specification allows inside a `glBegin`/`glEnd` pair, the context-switch tokens must be allowed anywhere because the kernel can switch contexts mid-primitive, and `arm_bgnend` raises the GL "invalid operation" error.
- **`arm_bgnend`** (0x0c0018e4; vector at 0x20006c). **Established:** it records an invalid-operation error with `set_invalid_operation`, reads the current token number from 0x200078, looks up the number of payload words in the 512-word table `hipwc` (0x0c000ff4), and reads and discards that many words (32 for the two double-precision matrix tokens 0xd4 and 0xd6, whose entry is 0; for token 3, `BEGIN_RECT`, the count is the first payload word). Any other token with a zero entry is reported as "begin/end ERROR" and the firmware spins. It then sets 0x200068 to 1 when the token's kind is 0 or 1 and to 0 when it is 2. **Inferred:** the hardware jumps here when a kind-0 token arrives between a begin and an end, and 0x200068 is the in-begin flag (it is part of the saved context).
- **`arm_divert`** (0x0c001a34; vector at 0x200054) prints "divert not handled!" and spins. kpm names the trigger: bit 1 of `HA_ICU_CTRL` is `ICU_CTRL_DHDIVERT`, and bit 0 of a token-map entry, set on every hardware-routed entry, is `ICU_MAP_DH` ([arm1.md](arm1.md#entry-format)). **Inferred** from the names: with `DHDIVERT` set the host interface sends routed ("DH") tokens to `HA_ICU_DIVERT_PC` instead of the distributor, so the ARM can see them. No shipped program sets the bit (the firmware writes only 0 and 1 to `HA_ICU_CTRL`, irsaudit only 0 and 1), so the divert path never runs. What a divert does to the token and its payload is **unknown: no shipped software or published source depends on it**; routes tried: 6.5.30m `arm1.u`, the diagnostic build `usr/diags/IR/ucode/arm1.u` (the same spinning handler), irsaudit, kpm's register table and dump code, and the 6.5.5 `sys/kona*.h` headers. An emulator may treat `DHDIVERT` as having no effect.
- **`arm_badcmd`** (0x0c0017f4) prints the current and previous token numbers, then reads 100 words of payload printing each ("future data follows") and spins on the port. 54 of the 306 ARM-run tokens point at it, directly or through a one-instruction branch: the 7 `X_UNUSED*` tokens and 47 GL entry points the firmware does not implement (`TEXIMAGE1D`, `TEXSUBIMAGE*`, `GENTEXTURES*`, `GETFLOATV`, `GETINTEGERV`, the `GET*IV` forms and others in [arm1_handlers.tsv](arm1_handlers.tsv), group `unsupported`). **Established** (host side, `libGLcore` N32 and `kona.so`, 6.5.30m): the drivers send none of these tokens as a command except `WG_FLUSH_1` (0x1ff), below. `__glkonim_PixelStorei` sends `PIXELSTOREI` (0x33) and `__glkonim_PixelTransferf` sends `PIXELTRANSFERF` (0x30), so their unsupported siblings `PIXELSTOREF` (0x32) and `PIXELTRANSFERI` (0x31) are reached by converting the argument on the host; the `__glkonim_Get*` entry points store no token constant before calling into shared code, which answers from the driver's state or sends one of the supported query tokens; texture images go down as `DRAWTEXELS` ([docs/opengl.md](../docs/opengl.md)); and the X module stores none of the seven `X_UNUSED*` tokens (scan of every token-address store in `kona.so`, [docs/opengl.md](../docs/opengl.md#x-server-module-drawing-commands)). The exception is `WG_FLUSH_1`: `kona.so` stores 0xdeadbeef at its address (FIFO offset 0x3fe0) after every cursor load, X-map configuration and read-back, yet `arm_wg_flush_1` (0x0c026644) is a single branch to `arm_badcmd`. `HP_DATA` (0) and `HP_DATA_1` (0x100) are placeholders at the bottom of each half of the window. Any other token whose entry is `arm_badcmd` reaching the ARM is a host bug, and the firmware's response (print, drain 100 words, spin) is a debugging aid.
- **Who sends the write-gather flush tokens.** **Established** (6.5.30m, the binaries below): every store of `WG_FLUSH_0` (0xff) or `WG_FLUSH_1` (0x1ff) sits on a path for an IP19 host, and the IP27 and IP35 paths flush with a discarded read. **Inferred** (the module choice in the third item): on IP27 and IP35 hosts the pipe never sees either token, and `arm_badcmd` is never reached through them. The evidence, by binary:
  - `setmon` `KonFlush` (0x10032ef0) switches on a board-type word: for type 19 it calls `KonCmd` with token 511 and 0xdeadbeef; for types 25 and 27 it loads the word at window offset 0x4200 and discards it.
  - `gfxinfo` `wg_flush` (0x1000ec4c; `setmon` has the same routine) stores 0xdeadbeef at the pipe pointer + 0x1fe0, token 0xff, only when `get_ven_iptype` returns 19. For any host other than IP19, IP21 and IP25 it returns without an access: `get_ven_type` (0x1000fb2c) walks `getinvent` and maps only the CPU-board inventory types 11, 13 and 15, to 19, 21 and 25.
  - The IP27 kernel names the pipe `KONAL`: `kona_alloc_bdata` (`kona_edtinit.o`) copies six bytes from its `.rodata` + 0x70 into the board record at P+204, the start of the `GFX_GETBOARDINFO` reply ([docs/kernel.md](../docs/kernel.md)). The IP35 `kona.a` has `KONAD` in the same place, after the same two neighbouring strings. `Xsgi` lower-cases a board name in `ddxGetBoardName` (0x1012a250, one `tolower` call per byte) and `ddxMakeDynamicModulePath` (0x10080080) builds `%s/%s.so` under `/usr/lib/X11/dyDDX`. **Inferred:** an IP27 server therefore loads `konal.so` and an IP35 server `konad.so`; the name argument `ddxOpenScreens` passes at 0x1012ce30 was not traced back to `ddxGetBoardName`.
  - `konal.so`, `konad.so` and `konas.so` write each X command as a token word and then its payload, all at FIFO offset 0. At each of the eleven places where `kona.so` stores `WG_FLUSH_1` (`konCreateWindow`, `konDestroyWindow`, `konReadImage`, two in `konReadFBBlock`, `kon_loadGC`, `kon_initGCCaches`, `kon_allocCachedStipple`, `konValidateGC`, `konStereoPolyRectangle` and the cursor helper 0x526140) they load one word through the pointer at +16 of the screen private record and discard it (`konal.so` `konCreateWindow` 0x147d1ac-0x147d1b4). None of the three stores at offset 0x1fe0 or 0x3fe0.
  - `libGLcore.so` in all six builds (IP27KONA, IP27KONA32, IP27KONA64 and the three IP35 ones) has no store at 0x1fe0 or 0x3fe0 of the FIFO; the stores and address sums with those displacements are all inside `__glim_SubdivPatchSGIX`, into a work record. No `kona.a` object of either kernel has one.

  **Inferred:** the flush store is the IP19 host's way of pushing out writes the host has gathered, which is why `kona.so` also uses the address-encoded framing of `setmon`'s type-19 path. Whether an uncached read does that job on IP25, IP27 and IP35 hosts is **unknown**. What the host interface does with a flush token that does reach it is **unknown: no shipped software or published source depends on it**. The 6.5.30m kernel archives drive the pipe from IP27 and IP35 hosts only (`usr/cpu/sysgen/IP27boot`, `IP35boot`), and on those nothing sends the token. Routes tried: the map words (0xc0265fc0 and 0xc0266440 in [icu_map.tsv](icu_map.tsv), plain ARM entries with no discard bit), `init_hip`, kpm's host-interface register table (the only write-gather field is `HIP1_GINTR_WGORDER`, bit 18 of 0x108, which no shipped program sets), the 6.5.5 `sys/kona*.h` headers, `arm_badcmd`, the kernel, every X module and `libGLcore` build, `setmon` and `gfxinfo`.

## How a handler reaches the engines

**Established** (`tbus_regwrite`, `arm_cullface`, `arm_geterror`, `load_*_ge` and about 5000 stores to the window). Every send to the engines is a short run of stores to the engine ports, ending with a store to r9 + 0x8c0. The last store is a **handler address**, taken from `gepc` (directly, or from the packed copy at r8 + 0x48); the engines start that handler when it arrives. [ge_isa.md](ge_isa.md) shows the handlers end by jumping to address 0, where the engine waits for the next command word.

| Port (r9 +) | Stores in the image | Use |
|---|---|---|
| 0x400 | 1239 | descriptor word, always followed by data: see below |
| 0x420-0x43c | 85 | engine select, stored (data ignored, r8 = 0) just before the words it routes. In kpm's address layout for `HA_GED_CTRL` these are `GED_CTRL_SEL` values 8, 10, 12, 13, 14 and 15 with `GED_CTRL_TAG` 0. **Established** by function name and use: 0x430 (select 12) = one engine (`load_singlecast_ge`, `deact_section`, `diag_tbus_1`), 0x438 (14) = all engines (`load_broadcast_ge` and 28 others), 0x434 (13) = the next engine in turn (`diag_ged_nextge`; also every bulk pass-through send: `arm_passthrough`, `arm_bitmap_dlist`, the X colour-map, gamma and cursor loads, `mem_swapout_*arm`). **Established** pairing (`activate_gefifo` 0x0c020888): one test chooses 0x430 or 0x438 for the first command it replays and, with the same result, 0x420 or 0x428 for the second command to the same engines. So select bit 1 is one engine against all engines in both pairs (8/10, 12/14), and 0x420 and 0x428 are 0x430 and 0x438 with select bit 2 clear. 0x428 alone is used by `arm_clipplane`, `arm_texenvi` and `do_pixelmap`, each before a broadcast state command, and 0x43c (15, all engines with bit 0 set) by `resolve_viewport` (after a 0x438 send, before a lone handler word), `arm_x_loadpos` (after `check_pipe_sync`), `arm_slop`, the reference-plane enable and disable and `activate_private`. **Inferred:** select bits 0-1 choose the engines (one, next, all) and bit 2 is a qualifier the firmware clears for a command that follows another to the same engines. What select bits 0 and 2 change beyond the choice of engines is **unknown: no shipped software or published source depends on it**; an emulator that routes 0x420 like 0x430, 0x428 and 0x43c like 0x438 matches every firmware use. Routes tried: every store in `arm1.u`, `activate_gefifo`, kpm's register table (names the field, not its values), irsaudit's `ged*` builders (they write the descriptor port only), the distributor program in [ged.md](ged.md) |
| 0x470, 0x474, 0x478, 0x47c, 0x4f0-0x4fc | 552 | operand words: the first word of an engine command (a register or table address, a mode value). Which port a handler uses is fixed per engine handler (`mgeb_CullFace` takes it at 0x478, `mgesi_TbusRegWrite` at 0x474, the flush at 0x4f4) |
| 0x840, 0x880 | 1640 | further operand words, in order (0x840 for data, 0x880 for the 0x2bad2dad filler `IncrGEDPtr` sends) |
| 0x8c0 | 1589 | the handler address; also single data words in a few places |
| 0x800, 0x980 | 6 | seen in `arm_polygonmode` and `arm_context_mopup`; **unknown** |

**Established** (kpm's `HA_GED_CTRL_ADDR` and `HA_GED_DATA_ADDR` layouts, [arm1_registers.tsv](arm1_registers.tsv)): the port address is decoded, not a register number. From r9 + 0x400 (ARM 0x200600, `HA_GED_CTRL`) address bits 2-5 are a select field and bits 6-8 a tag; from r9 + 0x800 (ARM 0x200a00, `HA_GED_DATA`) bits 6-8 are a tag. So 0x470-0x47c are selects 12-15 with tag 1, 0x4f0-0x4fc the same selects with tag 3, and the data ports 0x800, 0x840, 0x880, 0x8c0 and 0x980 are data tags 0, 1, 2, 3 and 6. The descriptor word itself fills `GCCTRL_0` (bit 5) and `GCCTRL_1_23` (bits 9-31): the 24-bit distributor control word of [ged.md](ged.md#the-token-map-entry-is-the-distributors-control-word), which is why every descriptor has bit 5 set. **Inferred:** the tag travels with each word into the engines' input channel (`hq_st[2]`, `hq_op[3]` of the engine netlist, [ge_isa.md](ge_isa.md)), with data tag 3 marking the handler address that starts a command, since 0x8c0 always carries one

Three shapes **established** from code:

- **Single command.** `arm_cullface`: read the value (r9 + 0x3c), keep it in RAM (r8 + 0x258), store it to port 0x478, then store the low half of the packed word at r8 + 0x4c (slot 3, `mgeb_CullFace`) to 0x8c0.
- **Register write through the engines.** `tbus_regwrite(reg, value)` (0x0c015298): reg to 0x474, value to 0x840, slot 107 to 0x8c0. The firmware reaches the raster-board registers (the numbers 0x400-0x477 it writes in `start_rdata`, `finish_rdata`, `check_pipe_sync`, `init_tf`, `init_tm`, `init_imp`) only this way. **Inferred:** the engine handler forwards the word to the raster boards' register bus (the "tbus"); the register map is [RM.h](../RM.h).
- **Bulk copy.** `load_broadcast_geEram` (0x0c020c04) selects all engines (0x438), forwards the first word, stores `(n-1) | 0xc000000` to 0x200058 and waits for it to drain, so the words go from the host FIFO to the engines' external memory in chunks of up to 0x200 with no ARM loop, then stores slot 131 to 0x8c0.

### Descriptor port (r9 + 0x400)

**Established.** The firmware writes a descriptor word at r9 + 0x400 and then data at r9 + 0x8c0 in the same sequence everywhere: all descriptors seen from the ARM have bit 5 set and, for the small structured group, bits 30 and 25-27 choose a target. The targets whose function is read in the code:

| Descriptor | Writer | Meaning |
|---|---|---|
| 0x48200020 | `init_ged_ucode` | write one word of the distributor program (1024 words; words naming a slot are first relocated, [arm1.md](arm1.md)). 0x48000020 with data 0 first |
| 0x42000020 / 0x42400020 + data 0 | `init_ged_ucode` | reset the write pointer of the table below |
| 0x42200020 | `init_ged_ucode` | 16 words (table A of `ged1b.u`) |
| 0x42600020 | `init_ged_ucode` | 512 words (table B of `ged1b.u`, one per 9-bit command number) |
| 0x46000020 + index | `init_ged`, `arm_matrixmode`, `xform_init`, `xform_restore` | set the index of the handler table |
| 0x46200020 + handler address | same | write an entry; the index advances ([ged_bound_table.tsv](ged_bound_table.tsv)) |
| 0x44000020 | `init_ged`, `init_ge`, `RestoreDistMode`, the pixel and X pixel paths, `activate_ged` | distributor register 0x220, the distribution mode, below |
| 0x44200020 | `init_ged`, `init_ge`, `arm_pipe_setup`, `activate_ged` | distributor register 0x221, set to 1 only around per-engine command loops, below |
| 0x44400020 | `init_ge`, `activate_setcurrentge`, `PixelRestore`, the pixel line set-up | distributor register 0x222, the engine occupancy mask, below |
| 0x58400800, then 0x2bad2dad at r9 + 0x880 | `IncrGEDPtr` | command 128 (`BshRegisterWrite`) with a filler word; the name says it advances a distributor pointer. **Inferred** |

**Established:** every other descriptor is a routed token-map entry written by the ARM itself. Command number 128 in pass form (bit 5 clear) runs `mgesi_BshRegisterWrite` and 159 runs `mgesi_IMPbshRegisterWrite`; that is how `init_pg`, `init_tg`, `init_tf`, `init_imp` and the pixel setup code write raster-board registers ([arm1.md](arm1.md#hardware-routed-tokens-from-command-number-to-engine-handler)). The descriptors 0x42..., 0x44..., 0x46... and 0x48... of the table above are of the same family with command numbers 0, 64 and 128 and set bit 25-27 target codes; they are register-form descriptors, whose bits 30:21 are the distributor register number (the command-number view of bits 23:21 is its low three bits), so nothing is chosen by a command number there.

### Distributor registers 0x220-0x222

The three descriptors 0x44000020, 0x44200020 and 0x44400020 carry distributor register numbers 0x220, 0x221 and 0x222 in bits 21-30 ([ged.md](ged.md#registers-the-host-writes) gives the encoding). What the firmware writes to each, from a search of every value stored at r9 + 0x400 in `arm1.u` 6.5.30m:

- **Register 0x222, occupancy mask. Established.** `init_ge` writes the board's engine mask (board-configuration word +0x5c) five times at +0x332c. `activate_setcurrentge` (+0x1ff54) first tests a one-engine mask against that word and prints "activate_setcurrentge() currentGE %d not a member of occmask 0x%x" when it is not a member, then writes the one-engine mask the same way. `PixelRestore` and the colour and luminance line set-ups (`SetupGE_ColorLine` +0x2cdd0) write a one-engine mask too. So the firmware's own message names the register as the occupancy mask, and narrowing it sends every following command to one engine.
- **Register 0x220, distribution mode. Established** values, **inferred** meaning. `init_ged` (+0x2520) computes a byte at r8 + 0xcf9: 1 when bit 0x20 of the configuration flags word (`pinfo` + 0xc) is clear and the board has four or fewer engines, otherwise 0. That byte is written to 0x220 at start-up and is put back by `RestoreDistMode` and by the end of the X pixel copy, read and finish handlers. `do_bitmap` (+0x2b490), the other pixel paths, `arm_gethistogram` and `arm_getminmax` write 0 first. The 6.5.5 header `sys/kona_if.h` gives configuration flag 0x20 a round-robin distribution name. **Inferred:** 0 is round-robin distribution, one command to each engine in turn, which the histogram and min-max queries need because they send exactly one collect command per engine; 1 is the distributor's default policy, and boards with more than four engines always run round-robin.
- **Register 0x221. Established** values, **inferred** meaning. `init_ged` and the start of `init_ge` write 0. `init_ge` writes 1 (+0x35d8) before it sends one set-up command per engine (handler slot 224, the operand carrying the engine number and count) and 0 afterwards (+0x36d8); `arm_pipe_setup` (+0x232f4) does the same around its per-engine loop of handler slot 374. `activate_ged` restores 0x220 and 0x221 from the context record. **Inferred:** 1 makes the distributor step to the next engine after every command, so that a loop of n commands reaches each of n engines exactly once. What else the register changes has no firmware user that would show it.

### Matrix tokens flip between hardware and ARM

**Established** (`matrix_vector` 0x0c018f44, `matrix_passthru` 0x0c018ef0, `arm_matrixmode` 0x0c01904c). The fifteen matrix tokens 0x0d1-0x0df (`FRUSTUM` to `TRANSLATEF`) are rewritten in the hardware map at run time. For the colour-matrix mode (0x1800, GL_COLOR) `matrix_vector` replaces their entries with the addresses of the ARM handlers `arm_frustum` ... `arm_translatef`, and the colour-matrix state lives in the ARM (`update_colormatrix`, `invalidate_colormatrix`); `matrix_passthru` copies the original routed entries back from the static list. Both set 0x200050 bit 0 around the edit. For the other modes the ARM instead rewrites the engine-side handler table through descriptors 0x46000020 and 0x46200020 (table above, [arm1.md](arm1.md)). `xform_restore` calls both routines when a context's matrix mode is restored. So the ARM can turn a hardware-routed token into an ARM-run token and back.

## How the ARM answers the host

**Established.**

- **Text.** `putchar` (0x0c019c98) sends each character through `send_host_intr` when not simulated. The host reads one word per interrupt and keeps its low byte ([docs/hip.md](../docs/hip.md)).
- **Events.** The value sent to the mailbox by `arm_do_idma` and `arm_mem_swapin` is a word of the command's own payload (the host passes 0x100 in DO_IDMA's flags word, [docs/hip.md](../docs/hip.md)); `arm_context_activate` sends a word from its context record. The firmware has no fixed event numbers of its own.
- **Read-back (the "rdata" path).** RDATA_SETUP (0x1f2) stores an address pair and length at r8 + 0xc98. `start_rdata` (0x0c0224d4) then programs raster-board registers 0x477, 0x440, 0x463, 0x464, 0x460, 0x461, 0x462 and 0x476 through `tbus_regwrite`, and `finish_rdata` undoes it. Between them, a query handler pushes its reply words to register 0x476 (`arm_getconfig` sends the count 0x1de, then 478 (0x1de) words from the board-configuration block at 0x04067edc, a loop bound built as 0xde + 0x100 at 0x0c0224a4; `SendDGRply` sends display-generator replies). **Inferred:** these registers are the output-DMA registers of the host-interface chip, reached over the same register bus, because the sequence loads an address, length and start and RDATA_SETUP's payload is the address pair and length the kernel sends for read-back ([docs/hip.md](../docs/hip.md)).
- **Engine events.** The engines report to the host through a kernel-communication record: `arm_ge_intr` (token 0x1dd) calls `start_kcomm` and `finish_kcomm`, which use the same read-back registers, with the record the kernel reads in `kona_ge_intr` ([docs/hip.md](../docs/hip.md)).
- **Errors.** `set_error` and the `set_invalid_*` helpers keep the first GL error; the host fetches it with GETERROR, answered by engine handler `mgebi_ErrQuery`.

## The 306 ARM-run tokens by kind

### Display-generator commands

**Established** (`arm_video_cmd`, 0x0c006398). Token 0x1a6 carries a command number (0-0x5c), then as many words as the entry of `DGDispatchTable` (0x040412c0, 8-byte entries of word count and handler) says, then one checksum word at r9 + 0x3c. The checksum is the sum of the command number and the payload words: on a mismatch the firmware prints "DG: Expected checksum %d, got %d" and drops the command. Otherwise it calls the handler with the payload buffer, and the handler replies with `SendDGRply` through the read-back path. [dg_dispatch.tsv](dg_dispatch.tsv) lists the 93 commands and their `DoDGRqst*` handlers (6338 payload words in total). These are the display generator's own requests: formats, genlock, cursor, DAC and encoder control, textport glyph loads, gamma maps, monitor identification over the I2C bus (`read_edid`) and FPGA loads (`DoDGRqstLoadXilinx`). **Established** by their length: roughly 280 `dg*` and `DoDGRqst*` functions, a quarter of the image. The firmware, not the kernel, owns display timing: [docs/dg.md](../docs/dg.md) records that the kernel has no code for video timing, and this is where it is.

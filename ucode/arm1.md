# ARM firmware (arm1.u) and the host-token map

What `usr/gfx/ucode/KONA/arm1.u` (IRIX 6.5.30m, linked as `ucode/KONA/arm1.u`) is, and what it says about how a host command token reaches the geometry engine. Facts are labelled **established** (read from the file or its code at the stated address), **inferred** (with the reasoning) or **unknown**.

[retools/tools/kona/arm1_disasm.py](../retools/tools/kona/arm1_disasm.py) writes the outputs this page cites: [arm1_symbols.tsv](arm1_symbols.tsv) (every symbol), [arm1.s](arm1.s) (the whole read-only image disassembled and labelled) and [icu_map.tsv](icu_map.tsv) (the 512-entry token map). [retools/tools/kona/ged_relocs.py](../retools/tools/kona/ged_relocs.py) writes [ged_relocs.tsv](ged_relocs.tsv).

## Container

**Established.** `arm1.u` is a big-endian ARM image in AIF layout. The 128-byte header holds three branch-or-no-op words, a data word (0x2c), an SWI, then RO size 0x40248, RW size 0x27c7c, debug size 0x9ae8, zero-init size 0x2d4fc, debug type 1, image base 0x0c000000, workspace 0, address-mode word 0x120 and data base 0x04040260. The header is not loaded: read-only address A is file offset 0x80 + (A - 0x0c000000), and read-write address A is file offset 0x80 + 0x40248 + (A - 0x04040260). Checked by the literal pools: every pointer a function loads from its pool lands on a symbol or a string under this mapping, and an offset of 0 does not.

**Established.** The last 0x9ae8 bytes are a low-level debug table: a symbol count (1682) at +32, then 1682 pairs of {flags << 24 | name offset, value}, then the names. The symbols name the firmware's functions (`init_hip`, `arm_cullface`, `arm_context_activate`, ...), its data (`icu_map`, `gepc`, `DGDispatchTable`) and the linker regions (`Image$$RO$$Base` 0x0c000000, `Image$$ZI$$Base` 0x04067edc).

## The second image: `arm1_kpm.u`

**Established** (`usr/gfx/ucode/KONA/arm1_kpm.u`, IRIX 6.5.30m, 7176 bytes). The same AIF layout as `arm1.u`: header words 0xe1a00000, 0xe1a00000, 0xeb00000c, 0x2c, 0xef000011, then read-only size 0x1a00, read-write size 0x188, debug size 0, zero-initialised size 0x126c, image base 0x0c000000, address-mode word 0x120 and data base 0x04001a00. There is no debug table, so no symbols. Its strings are a register dump for exceptions ("ARM: Unexpected Exception (fault) - %s" with the six vector names), the banner "Welcome to NIC ARMland - config is 0x%x" and the NIC messages ("%s Serial #: %02x %02x %02x %02x %02x %02x Family: %02x%s", " (BAD CRC)", "Not NIC queriable from %s.", "Failure trying to read NIC interface from %s").

**Established** (code, read with the `arm1_disasm.py` decoder): it sets r9 = 0x00200200 and enters the same input loop (`ldr pc, [r9, #0x200]` at 0x0c000070); its exception vectors at 0x0c000308-0x0c000324 save all registers and print them; its only host-interface registers are the mailbox pair 0x200090 and 0x200094 (the wait-then-store sequence of `send_host_intr`, at 0x0c000328), the counter 0x2000b0 (a wrap-safe delay at 0x0c000348) and the bit-bang port 0x2000c0-0x2000cc (from 0x0c0010c0). It writes no engine port, token map or DMA register.

**Established** (host side, `usr/gfx/KONA/bin/kpm`, IRIX 6.5.30m): the diagnostic names `/usr/gfx/ucode/KONA/arm1_kpm.u` beside "Starting NIC inspection", "Timeout reading NIC information", "NIC message too long" and the format "%s: NIC #: %02x%02x.%02x%02x.%02x%02x (family: %02x)%s", and names `arm1.u` separately. So `arm1_kpm.u` is a small replacement firmware that `kpm` loads into the ARM to read the boards' serial-number chips (NICs) over the bit-bang port and return what it finds through the mailbox as text; the production firmware's own `nic_*` and `knic_*` code does the same job at start-up. **Inferred:** it exists so `kpm` can identify boards on a pipe whose production firmware will not start.

## The token map (`icu_map`)

**Established** (`init_hip`, 0x0c001c60). At start-up the firmware builds a 512-entry table of 32-bit words, one per host token, from a static list at `vector_end` (0x0c000328). Walking the list, a word with bit 0 set is a complete entry; an even word is followed by a second word, and the entry is (first | second << 4). Each entry is stored twice: in `icu_map` (0x04068e54, zero-initialised RAM) and at ARM address 0x00400000 + 4 x token. Tokens the list does not reach get `arm_badcmd` << 4 in the hardware copy at 0x00400000 only; `icu_map` keeps zero there. `init_hip` also records the index of the entry whose handler is `arm_matrixmode`.

**Inferred:** 0x00400000 is a table in the host-interface chip that the hardware consults for each incoming token. The firmware's own messages name an "ICU" (`HA_ICU_CURR_CMD`, `HA_ICU_PREV_CMD`), and the table is called `icu_map`.

[icu_map.tsv](icu_map.tsv) lists all 512 entries with the kpm token names. 306 tokens run an ARM handler and 206 are routed by the hardware.

### Entry format

**Established** from the code that reads or builds entries:

| Bits | Meaning | Where |
|---|---|---|
| 0 | `ICU_MAP_DH` (kpm): 1 = routed by the hardware, no ARM handler. 0 = ARM handler | `init_hip` keeps odd words whole and builds even ones from a handler address |
| 1-2 | Kind: 0 for 392 tokens, 1 for the twelve begin tokens, 2 for `END`, 3 for 107 tokens (vertex data, list calls, context switches). Read as "legal between begin and end"; the begin/end error path is in [arm1_firmware.md](arm1_firmware.md) | `init_hip`, `arm_bgnend` 0x0c0018e4 |
| 3 | Chain: more entries follow in the same list | `varray_build_command` sets it on every entry it builds and `varray_set_cmd_table` clears it on the last |
| 4-31 (ARM entries) | Handler address bits 0-27 (the entry is the address shifted left by 4) | `init_hip` |
| 6-8 | Payload word count for a vertex attribute (from `wordCountTable`) | `varray_build_command` |
| 27-28 | From `lastWrdTable` | `varray_build_command` |
| 29-30 | From `byteCmpTable` | `varray_build_command` |

`varray_build_command` (0x0c0395fc) makes vertex-array entries by taking the attribute token's own entry, clearing bits 5-8 and 27-30, and putting in the count and the two table values above.

**Inferred** from the values in the hardware-routed entries:

- Bits 29-30 give the component type: every `...F` and `...I` token has 2 and every `...D` token has 3 (for example `HP_LOADMATRIXF` 0x58625401 and `HP_LOADMATRIXD` 0x78625001). The double forms send twice the words.
- Bits 15-23 are a 9-bit command number. Forms of one command share it (LOADMATRIXF and LOADMATRIXD 196, ROTATEF and ROTATED 202, X_POINT, X_POINT6 and X_POINT24 170), and the X-server commands get consecutive numbers in token order (X_POINT 170 to X_BGPOINT 178, then X_LOADGC 179 to X_LOADSCISSOR 182). What the number selects is under "Hardware-routed tokens" below.
- For routed commands the payload word count is bits 6-10 (0 meaning 32) on pass and register entries (bit 31 clear) and bits 6-8 on geometry entries (bit 31 set), kpm's `ICU_MAP_N_WC` and `ICU_MAP_G_WC`. It matches X_DATA1 to X_DATA10 (1-10), X_POINT6 (6), X_POINT24 (24), LOADMATRIXF (16), ROTATEF (4) and LOADMATRIXD (0, 32 words for 16 doubles). The three `HP_NORMAL3*` entries, once read as an exception (bits 6-10 = 11), are geometry entries: their 3-bit count is 3 for the `F`, `I`, `B` and `S` forms and 6 for `NORMAL3D`.

**Established** (kpm 6.5.30m, its ARM-side register table at vaddr 0x100b72c8, [arm1_registers.tsv](arm1_registers.tsv)): the map is `HA_ICU_MAP` and kpm names every bit. Common to all entries: bit 0 `DH`, bits 1-2 `BGNEND` (the kind above), bit 3 `NEXT` (the chain bit), bit 4 `DATAINV`. An ARM entry (`HA_ICU_MAP_A`) has the handler word address in bits 6-31 (`ICU_MAP_A_PC`) with bits 4-5 zero. A routed entry has bit 5 `CMDVAL`, a count, a distributor control field `GCCTRL` and bit 31 `GFX`, in two layouts: `HA_ICU_MAP_G` (count bits 6-8, control bits 9-30) and `HA_ICU_MAP_N` (count bits 6-10, control bits 11-30). That matches the three forms [ged.md](ged.md#the-token-map-entry-is-the-distributors-control-word) reads from the IR diagnostic's packers: `GFX` set is the geometry form, `GFX` clear the pass form, and `CMDVAL` the register/pixel form. So bits 9-14 and 24-26 are distributor control bits, decoded field by field there, and bit 31 picks the layout. `DH` set means "routed by the hardware" (irsaudit calls `HA_ICU_WC` the "ICU DH word count"). `DATAINV` is set on 51 routed entries: the eleven begin tokens, `END`, `SWAPTMESH`, `BEGIN_SUBDIV_PATCH`, the 32 vertex-array loop tokens, `FLUSH`, `GED_NOP` and `SKIP2`, `SKIP4`, `SKIP5`. All of them carry no data for the engines and count the token word itself (1, or 3 and 4 for `SKIP4` and `SKIP5`, which skip that many words in all). **Inferred:** `DATAINV` marks the counted words as not data, so the distributor takes the command without loading the vertex record.

## How a command reaches a geometry-engine handler

The slot table `geif.u` (1024 big-endian 16-bit words, [ge.md](ge.md)) is what the firmware uses for geometry-engine addresses.

**Established** (`init_hip`, 0x0c001d78-0x0c001dbc): the firmware copies 512 32-bit words of `geif.u` into `gepc` (0x04068654), so `gepc[k]` is word k, whose low half is the handler address of slot k. gfxinit loads the file for it ("LoadGeifFile: sdram addr"), and `find_ucode` locates it by the tag 0x4592; a simulator flag can point at 0x8000 instead. It then packs `gepc[0..127]` as halfword pairs into the state block at r8 + 0x48.

**Established** (ARM-handled tokens). A handler stores the payload in a host-interface register and then writes a geometry-engine handler address, taken from `gepc`, to the register at r9 + 0x8c0. Examples, each confirming a pairing [ge_name_matches.tsv](ge_name_matches.tsv) had only inferred from names:

- `arm_cullface` (token 0xb6): payload to r9 + 0x478, then the low half of r8 + 0x4c, which is `gepc[3]` = slot 3, `mgeb_CullFace`.
- `arm_frontface` (0xba): r8 + 0x64, `gepc[15]` = `mgeb_FrontFace`.
- `arm_matrixmode` (0xd0): r8 + 0xac, `gepc[51]` = `mgeb_MatrixMode`. For mode 0x1700 (model-view) it then writes, through a register written before each word (r9 + 0x400 = 0x46200020), the model-view variants: `gepc[44]` LoadIdentity_Modelview, `gepc[48]` LoadMatrix_Modelview, `gepc[151]` Frustum_Modelview, `gepc[53]` MultMatrix_Modelview, `gepc[56]` Ortho_Modelview, `gepc[67]` PopMatrix_Modelview, `gepc[71]` PushMatrix_Modelview, `gepc[75]` Rotate_Modelview, `gepc[78]` Scale_Modelview, `gepc[85]` Translate_Modelview.

**Inferred:** the geometry engine takes the handler address itself as the command, so for ARM-handled tokens the token-to-slot step is the ARM's choice of `gepc` index, written in its code, not a table. The matrix-mode case suggests that the per-mode matrix commands are rebound when the mode changes, which is why one host token (LOADMATRIXF) has four handlers.

**Established** (`init_ged_ucode`, 0x0c001e20). The distributor program `ged1b.u` is loaded as 1024 32-bit words. Before writing each word to the distributor (register 0x48200020 written first), the firmware tests it: top two bits 2, bits 27-29 zero and bits 16-22 one of 0x3e, 0x45, 0x46, 0x47, 0x48. Such a word holds a geometry-engine slot number in its low 16 bits, and the firmware replaces it with that slot's handler address (from r8 + 0x48 below slot 128, from `gepc` above; a slot above 0x1ff prints "bad index"). It then loads the distributor's tables: 16 words through 0x42200020 and 512 words through 0x42600020. [ged_relocs.tsv](ged_relocs.tsv) lists the 83 relocated words. They name 35 handlers, all primitive-assembly entries: `mgesi_Triangles`, `mgesi_TriangleStrip*`, `mgesi_QuadStrip*`, `mgesi_TfanPoly*`, `mgesi_LineStrip*`, `mgesi_Points`, `mgeb_Material`, `mgeb_RasterPos`, `mges_EvalCoord`, `mgesi_SubdivEntry` and `mgebi_NullCommand`.

This corrects an earlier reading: `ged1b.u`'s code segment is 931 32-bit words (0xe8c bytes), not 12-byte records, and its second segment (byte address 0x1000) is the 528-word table block the firmware loads after the program.

## Hardware-routed tokens: from command number to engine handler

The firmware loads three things that decide what a routed token does. All three are written through the descriptor port at r9 + 0x400 and the data port at r9 + 0x8c0 ([arm1_firmware.md](arm1_firmware.md) lists the port protocol).

**Established** (`init_ged_ucode` 0x0c001e20, `init_ged` 0x0c0024e8).

1. **The distributor program** (1024 words of `ged1b.u`, descriptor 0x48200020), with the 83 slot words relocated to handler addresses ([ged_relocs.tsv](ged_relocs.tsv)).
2. **Two tables from the second segment of `ged1b.u`:** 16 words (descriptor 0x42200020) and 512 words (descriptor 0x42600020). The 512 entries are small numbers (largest 0x3a1) that are word addresses inside the 1024-word distributor program: entry 129 is 0x254, entry 170 is 0x275, entry 196 is 0x4f.
3. **A table of engine handler addresses.** `init_ged` writes 43 entries into indexes 0 to 63 of a table: descriptor 0x46000020 with the index as data sets the index, 0x46200020 with a `gepc` handler address writes an entry and advances the index (`arm_matrixmode` sets index 3 once and writes ten entries in a row). [ged_bound_table.tsv](ged_bound_table.tsv) lists them: 0 `mgesi_BshRegisterWrite`, 1 `mgeb_Fogf`, 2 `mgeb_Fogi`, 3-12 the ten matrix operations (load identity, load matrix, frustum, multiply, ortho, pop, push, rotate, scale, translate) in the modelview variants, 14 `mges_NullCommand`, 15 `mgesi_TBUS_1`, 16 `mgebi_ReferencePlane`, 25-28 the map-grid and map-spec evaluators, 29-31 deformation and IMP register writes, 32-33 the 2D mip-map bind and texture scale/bias, 34 `mgesi_PushAttrLights`, 42-54 the X-server commands (`XPoint`, `XPointRel`, `XRect`, `XBox`, `XSpans`, `XSegment`, `XLine`, `XLineRel`, `XBgPoint`, `XLoadGC`, `XLoadPosition`, `XLoadClip`, `XLoadScissor`) and 60-63 `EnableUnpack`, `DisableUnpack`, `RestoreColor` and `RestoreNormal`.

**Established** (correlation, [hw_route.tsv](hw_route.tsv)). Take a routed token's command number n. The handler at index `n & 63` of that table has the token's own name for 48 of the 206 routed tokens (the matrix tokens, `TBUS_1`, `REFERENCE_PLANE`, the deformation tokens, `BIND_2D_MIPMAP_TEXTURE`, `FOGF`, and every X-server drawing and load token from `X_POINT` to `X_LOADSCISSOR`), and by role for six more: `MAPGRID1D` and `MAPGRID2D` (`EvalGrid1D` and `EvalGrid2D`), `X_POINT6_R`, `X_POINT24_R` and `X_LINE6_R` (the relative forms) and `LOAD_POST_TEX_SCALE_BIAS` (`TextureScaleBias`). That is 54 tokens. The X-server tokens are the best test: the drawing tokens 0x14c-0x161 take numbers 170-178 and the load tokens (0x129, 0x12a, 0x12b, 0x12d) take 179-182, which land on indexes 42-54, where `init_ged` wrote the X handlers in that order; the old name-matched slots (240, 242, 244-250, 360-363) are the ones stored there.

**Established** (the number is also a separate key into the distributor program). Tokens that share a program entry call different handlers: command 170 (`X_POINT`), 174 (`X_SPANS`) and 178 (`X_BGPOINT`) all start at distributor word 0x275, yet their indexes 42, 46 and 50 hold `XPoint`, `XSpans` and `XBgPoint`; entry 0x2a1 is shared by `LOADIDENTITY` (131), `ORTHO` (135), `TBUS_1` (143), `MAPSPEC1D` (155), `X_POINT_R` (171), `X_SEGMENT` (175) and `X_LOADGC` (179). So the handler does not come from the distributor program.

**Inferred**, from those three results together: the hardware takes the 9-bit command number from the token entry, starts the distributor program at table[16 + n] (the second 512-word table) and uses the low six bits as an index into the handler table, giving the engine the handler address as its command. The firmware's own sequencing supports it: the handler table is filled by the ARM from `gepc`, which is why no static array in `arm1.u` or `ged1b.u` holds a number-to-slot map (every earlier search for one failed), and why one token (`LOADMATRIXF`) can run different handlers: the ARM rebinds indexes 3-12 whenever the matrix mode changes, so the number stays fixed while the handler changes. What is not established is the hardware step itself; no firmware code reads or writes it, only the tables.

**Established** (the ARM injects routed commands itself). The descriptor words the firmware writes at r9 + 0x400 have the layout of a token-map entry: bits 15-23 are a command number, bits 27-30 the count and type fields, and bit 5 is set on the register form (bit 0 clear); the pass-form command writes 0x58404800, 0x58400000 and 0x58400800 have bit 5 clear. Decoding every descriptor constant in the firmware (about 230 distinct values, ~1000 stores) with the rule above gives, by command number:

| Command number | Index | Handler | Stores | Used by |
|---|---|---|---|---|
| 128 (pass form, bit 5 clear: descriptors 0x58404800, 0x58400000, 0x58400800) | 0 | `mgesi_BshRegisterWrite` | see the note below the table | raster-board register writes: pixel and raster setup, format registers, `activate_ged`, `init_ged_regs` |
| 0, 64, 192, 256, 320, 384, 448 and 128 in register form (bit 5 set) | none | distributor register writes: the register number is in descriptor bits 30:21 and these command numbers are only its low three bits shifted up | most of the 0x42..., 0x44..., 0x46..., 0x48..., 0x50... and 0x58... descriptors | `init_ged_ucode`, `init_ged_regs`, distributor table and program loads |
| 159 | 31 | `mgesi_IMPbshRegisterWrite` | 57 | pixel-path ends, `SetupRM` |
| 32, 96, 160, 224, 288, 352, 416, 480 | 32 | `mgebi_Bind2dMipmapTexture` | 87 | `deactivate_ged`, `deactivate_ged_ge` |
| 129 | 1 | `mgeb_Fogf` | 7 | `initFogState` |
| 143, 161, 162, 188, 189, 191, 206-208 | 15, 33, 34, 60-63, 14-16 | `TBUS_1`, `TextureScaleBias`, `PushAttrLights`, `EnableUnpack`, `DisableUnpack`, `RestoreNormal`, `NullCommand`, `ReferencePlane` | 1 each | `tbus_write_word`, `arm_pvertex_setup`, `arm_pvertex_cleanup`, `vertex`, `normal`, `color` |

So the ARM sends a hardware-routed command by writing an entry-shaped word and then the command's payload through the data ports; the same index-to-handler rule picks the handler. Only the pass form (descriptor bit 5 clear) with command number 128 reaches `BshRegisterWrite`. In the register form (bit 5 set) the word is not a token entry at all: bits 30:21 are a 10-bit distributor register number and the command-number view of bits 23:21 is just that number's low three bits, so the command numbers 0, 64, 192, ... 448 seen on those descriptors name eight different registers and select no handler or register space. Checked over the 58 distinct register-form descriptor words in the firmware: none has bits 23:21 different from register bits 2:0. The earlier count of 945 stores for command number 0, 64, ... 448 mixed the two forms. This also settles that bits 6-8 of the number are not part of the handler choice.

**Established** (the handler table serves only the pass form). Bit 31 of an entry (`GFX`, [Entry format](#entry-format)) splits the 206 routed tokens cleanly: all 54 tokens whose index names their own handler have bit 31 clear, and none of the 122 tokens with bit 31 set (the begin, colour, normal, vertex, material, evaluator-coordinate, packed-vertex and vertex-array-loop tokens) lands on its handler that way. The handler table is written in only four functions of `arm1.u` 6.5.30m (`init_ged` +0x25ac and `arm_matrixmode`, `xform_init` and `xform_restore` at fixed index 3), found by evaluating every descriptor value stored at r9 + 0x400 (232 distinct values), not by function. None writes indexes 13, 17-24, 35-41 or 55-59. The descriptors whose number falls on indexes 19-21 are geometry entries with bit 31 set: 0xd869e800 and its siblings (command 211 or 83) in `arm_rasterpos*` and `rasterpos_init`, 0xdc2a6800 (command 84) in `arm_getmaterialfv`, the colour-material routines, `getcurrent` and `material_push`, and 0xd80a4000 (command 20) in `arm_evalstrip1d` and `arm_evalstrip2d`. **Inferred:** these are injected vertex-form commands whose distributor program picks the handler, like the host's own vertex tokens, so they never consult handler-table indexes 19-21, which is why nothing loads them. The earlier reading that these commands used indexes 19-21 applied the pass-form rule to geometry entries.

**Where the rule does not hold.** For the other 152 routed tokens `n & 63` names an unrelated handler or none, so the handler table is not how they reach the engines: the vertex data tokens (colour, index, normal, texture coordinate, vertex, material, evaluator, packed vertex: numbers 1-18, 78, 129, 142-146, 159, 206, 272 and 448), the begin and end tokens (386-397), `SWAPTMESH`, the vertex-array loop tokens (all number 0), `FLUSH`, `GEPASSCMD`, `SKIP*`, `SETCOLORNORMAL`, `DEFORM` and `X_DATA1`-`X_DATA10`. **Inferred:** their programs pick the handler themselves: the begin and vertex programs contain the relocated slot words for `mgesi_Triangles`, `mgesi_TriangleStrip*`, `mgesi_QuadStrip*`, `mgesi_LineStrip` and the rest of the primitive handlers, and `X_DATA*` and `X_BDATA4` land on `BshRegisterWrite`, a register write, which fits their role. [The next section](#the-512-entry-table-as-eight-banks-the-152-vertex-primitive-and-beginend-tokens) maps each of them to its entry in the distributor program. [ged.md](ged.md) decodes that program's instruction set.

**Unknown.** Whether the handler table sits in the distributor or in the engines. The engine error register has a bit named `ELUT_ADR` ([GE.h](../GE.h)); a table indexed by six bits that is written beside the distributor program is **inferred** to be the distributor's, but nothing in the firmware names the chip.

## The 512-entry table as eight banks: the 152 vertex, primitive and begin/end tokens

Source data: [ged_banks.tsv](ged_banks.tsv) (all 512 table entries) and [ged_route.tsv](ged_route.tsv) (every routed token), written by [retools/tools/kona/ged_route.py](../retools/tools/kona/ged_route.py). Labels as above.

**Established.** `ged1b.u` carries an assembler line table (the section after the code): for each of the 931 program words the source file and line it came from. The thirteen source files are `dist.s` (the common stubs and the first words), `flush.s`, `material.s`, `trigger.s` and one file per primitive: `points.s`, `lineloop.s`, `linestrip.s`, `lines.s`, `tri.s`, `tstrip.s`, `tfanpoly.s`, `quad.s`, `qstrip.s` (build string "uasm 6.0 ... Thu Jul 20 17:33:26 2006"). The source text is not in the file. Looking each table entry up in the line table gives the module a command number starts in.

**Established.** Split by bits 6-8 of the command number n (the "qualifier"; k = n & 63), the 512-entry table is eight banks of 64 entries, and nearly every bank is one module:

| Bank | Entries start in | Handlers reachable from a bank's entries (relocated slot words, [ged_relocs.tsv](ged_relocs.tsv)) |
|---|---|---|
| 0 | `trigger.s`, `material.s`, `dist.s` stubs and the first line of every primitive file | `mgeb_Material`, `mges_NullCommand`, `mgebi_NullCommand`, `mgeb_RasterPos` and one entry per primitive start (below) |
| 1 | `lineloop.s` (36), `dist.s` | `mgesi_LineStrip` and its Copy/Save/Restore forms, `mges_EvalCoord` |
| 2 | `qstrip.s` (56) | `mgesi_QuadStrip`, `Save`, `Restore`, `RestoreSave` |
| 3 | `tstrip.s` (60) | `mgesi_TriangleStrip` and its `WithSwapOdd`, `Save`, `Restore` and `RestoreSave` forms (nine) |
| 4 | `tfanpoly.s` (44) | `mgesi_TfanPoly`, `Save`, `Restore`, `RestoreEdge`, `RestoreEnd`, `RestoreSave`, `End` |
| 5 | `linestrip.s` (20), `quad.s` (20) | `mgesi_LineStrip`, `mgesi_Quads` |
| 6 | `tri.s` (16), `lines.s` (12), `points.s` (8), `lineloop.s` (4) | `mgesi_Triangles`, `mgesi_Points`, `mgesi_LineStrip` and `SaveV0`/`SaveAndIgnoreV0`/`RestoreV0` |
| 7 | `quad.s` (20) | `mgesi_Quads` |

Within a bank each module defines the same set of attribute entry points at the same k, so each attribute (colour, normal, texture coordinate, vertex, material, evaluator) exists once per bank with that primitive's code. For k = 16 (colour) the entry is in `lineloop.s` line 53 (bank 1), `qstrip.s` 68 (2), `tstrip.s` 46 (3), `tfanpoly.s` 94 (4), `linestrip.s` 68 (5), `lines.s` 27 (6) and `quad.s` 42 (7); bank 0's is the common stub that ends in `mgebi_NullCommand`.

**Established (the vertex entry, k = 14).** In bank 1 it starts at `lineloop.s` line 193 and its span holds `mgesi_LineStrip`; bank 2 `qstrip.s:185`, `mgesi_QuadStrip`; bank 3 `tstrip.s:304`, `mgesi_TriangleStripWithSwapOdd`; bank 4 `tfanpoly.s:235`, `mgesi_TfanPolyEnd`; bank 5 `linestrip.s:35`; bank 6 `tri.s:45`, `mgesi_Triangles`; bank 7 `quad.s:54`, `mgesi_Quads`; bank 0 a stub that ends in `mges_NullCommand`. The vertex entry of a bank therefore starts the primitive assembly of that bank's primitive.

**Corrected** ([ged.md](ged.md)). The banks are not chosen by the token. For a geometry token, bits 6-8 of the command number are three separate flags: vertex, floating-point data and unsigned data. The IR diagnostic's control-word packer and the 121 geometry entries of the map establish this. The distributor picks a group of entries from its own primitive-class register through the 16-word table A, plus a vertex-state count, and the 512-entry table is laid out per primitive, not in eight banks. For all 177 vertex-state loads in the program, the loaded address equals B[8 x A[class] + 4n]. The begin stubs load that class and state, and that settles how a begin constant becomes a bank. The bank table above is still a correct index of where entries start, read with that layout. The distributor's instruction set is in [ged.md](ged.md). Still **unknown**: the exact rule for when the token's own k is used instead of the state ([ged.md](ged.md#how-an-entry-is-chosen)).

A token the ARM runs instead is a plain handler that picks a `gepc` slot in its own code ([above](#how-a-command-reaches-a-geometry-engine-handler)).

# Display tables: video formats, combinations, VOF sources and the option-board image

What the files under `ucode/KONA/dg4/`, `ucode/KONA/vof/` and `ucode/KONA/dgo1/` hold (IRIX 6.5.30m install). Facts are labelled **established** (read from the files, with the check that shows it), **inferred** (a reading, with the reasoning) or **unknown**. The container and name table of all 74 `.vfo` and 26 `.cmb` files parse with `retools/tools/kona/sdb_dump.py` and `retools/tools/kona/display_formats.py`, and `retools/tools/kona/sdb_dump.py --check` tests the relations below on the 74 `.vfo` files and passes. The stored values of every file are in [display-formats.md](../docs/display-formats.md), one row per file. First configuration only: the table values are for IR with the DG4 display generator.

No file here is read by the pipe's kernel driver. The X server module reads them: its `vfmt*` functions open a `.cmb` and the `.vfo` files it names, and pack each format into the 383-word `LoadFormat` display request, whose word layout, field by field, is in [docs/dg.md](../docs/dg.md#the-loadformat-request-383-words) together with the registers the firmware loads from it. `ircombine`, `setmon` and `sdbutil` (`usr/gfx/`, `usr/gfx/ucode/vfc/`) are the user tools around the same files.

## The container (`.vfo` and `.cmb`)

Both kinds use one big-endian container, specified with its reader functions in [display-file-format.md](../docs/display-file-format.md). It holds a header, the field values and a name table sorted by name, so a reader asks for fields by name. Every file here parses with `retools/tools/kona/display_formats.py`, which decodes each file into the rows of [display-formats.md](../docs/display-formats.md).

## Combination files (`.cmb`)

**Established** (26 files in `dg4/cmb/`). A combination describes what each video channel shows and which format file drives it. The file name is the layout: `1280x1024_60.cmb` is one channel, `2@1280x1024_60` two, `8@640x480_60` eight, `1280x1024+1920x1080_72` two different formats side by side, and `+NTSC` adds the encoder channel. In `1280x1024+4@640x480_60` the count is of the small channels after channel 0, and `7@800x600_60+NTSC` and `1280x907+5@640x453_60` have no channel 1 (their regular channels are 0 and 2 up, then encoder channel 8).

Global fields (20 of them, in file order): `MajorVersion` 1, `MinorVersion` 0, `name` (empty in every file), `dateStamp` 0, `textport` (1 only in `3@1280x1024_60`), `managedSize` and `allocatedSize` (width, height; the allocated size rounds up to whole tiles, below), `pixelDepth` 2 in every file, `syncSource` 0, `syncFormatName` empty, `syncFormatValid` 0, `syncFormatFrameRate` 0.0, `syncFormatDateStamp` 0, `syncComponent` 0, `fastlistChunksize` 1.0, `PSDhysteresis` 2, `minRMs` 0, `usingEncoderOutput` (1 in the three `+NTSC`/`+5@640x453` combinations that have a channel 8), `globalGamma` (1.7 three times) and `usingGlobalGamma` 0.

Per-channel block, 38 fields named `ch0...` to `ch7...` (and `ch8...` for the encoder). Common to all channels in all files: `Enable` 1, `Blanking` 0, `OutputAlpha` 0, `CursorPriority` 0, `PixelFormat` 0, `DataFormat` 0, `PlacementRes` (2, 1), `HalfLineInterp` 0, `HPhase` `VPhase` `SCHPhase` 0, `Gain` 1.0, `SetGamma` 0, `Gamma` 1.7 three times, `FilterSize` (5.0, 3.0), `FlickerFilter` 0, `Letterbox` 0, `SafeArea` 100.0, `SetupEnable` 1, `TriLevelSyncEnable` 0, `FIFOwatermark` 0, `MaxTilesPerRequest` 8, `MaxTilesPerLine` 8, `SyncMethod` 0. Fields that vary:

## Video format files (`.vfo`)

**Established** (74 files in `dg4/vfo/`, 170-203 fields each depending on the number of fields per frame). A `.vfo` is the compiled description of one video format for the display generator ("VOC for DG4" in `VofHardwareName`, file generator `dg4_def_version` `$Revision: 1.54 $` for 54 files and `1.1` for 20). `dg4/vfo/README` is a human-readable summary in the same terms (pixel clock, line, field and porch lengths) of the 54 formats compiled with revision 1.54; the 20 compiled with revision 1.1 are not in it. Its total and active lines and pixels, frame rate, fields, swaps and pixel clock agree with the stored fields of all 54 (checked).

### The video-output-format tables

**Established** (all 74 files, relations checked by `--check` and `ucode/KONA/vof/*.vof` for the meaning of the names). The display generator's timing is a small sequencer: a set of **signals**, each with up to a few **edge** slots, a set of **line types**, and a **state table** that runs the line types down the frame.

1. **Signals.** 14, in this order, from `EdgeSignalAssignmentValue` and from the `I` lines of the `.vof` sources, which list the same 14 in the same order: HSYNC, VSYNC, CSYNC, CBLANK, TRISYNC, FIELD_START, FIELD, FRAME_START, VIDEO_ACTIVE, LINE_START, STEREO_OUT, IMPREG_LD, XMAPREG_LD, VOF_VDRC_EN. `SignalInitialStateValid` (all 1) and `SignalInitialStateValue` give the level at the start of a line: **established** that the encoding is 1 low, 2 high (`TransitionDirectionLow` 1 and `TransitionDirectionHigh` 2 are stored in each file; `640x480_60` has 2 for HSYNC, VSYNC, CSYNC, TRISYNC and 1 for the rest, and `640x480_60.vof` has `I HSYNC 1`, `I CBLANK 0`: level + 1).
2. **Edge slots.** 50 slots, arrays `TransitionValid`, `TransitionValue`, `TransitionDirection`, `EdgeSignalAssignmentValid`, `EdgeSignalAssignmentValue`, each 50 entries. The slot count per signal is the same in all 74 files: 4, 4, 8, 6, 6, 2, 2, 2, 6, 2, 2, 2, 2, 2 in the signal order above, and the slots of one signal are consecutive. A valid slot is one transition: a position in video clocks (`TransitionValue`) and the level it goes to (`TransitionDirection`, 1 or 2). For 1280x1024_60 HSYNC has slot 0 (position 0, to low) and slot 1 (position 60, to high): 60 clocks = 120 pixels = `FormatInfo_H_Sync`; CBLANK goes high at 180 clocks (360 pixels = sync 120 + back porch 240) and low at 820 (1640 = 360 + 1280 active).
3. **Which lines an edge applies to.** `TransitionLineTypesUsing00000` to `...00049` (names built from the format string stored in `_TransitionLineTypesUsing_Name_`) are 50 arrays of 32 booleans, one per edge slot: bit n set means the edge happens on lines of type n. **Established** as data; the reading matches the `E signal clock level types` lines of the `.vof` sources (`E HSYNC 95 1 0,1,2,3`: the last column is a line-type list).
4. **Line types.** `LineTypeValid[32]` and `LineTypeLength[32]`: the length of each type in video clocks. 1280x1024_60 uses 11 types of 840 clocks each (1680 pixels / 2); other formats have different lengths on equalisation lines. Matches `L type length` in the `.vof` sources.
5. **State table.** `StateTableLineType[256]` and `StateTableRepetitions[256]`, with `StateTableValidStates` and `StateTableSize` (256): state i runs `StateTableLineType[i]` lines for `StateTableRepetitions[i]` lines. **Established:** the repetitions of the valid states sum to `TotalLinesPerFrame` in all 74 files, and the entries after the valid ones are zero. 1280x1024_60 has 13 states: line types 0-7 once each (8 lines), type 6 for 30 lines, type 8 for the 1024 active lines, then types 9, 6 and 10 once each (8 + 30 + 1024 + 3 = 1065). 640x480_60 has 13 states in which line type 6 runs for the 480 active lines, preceded by type 3 for 28 lines and followed by type 3 for 7. Matches `V repeat type` in the `.vof` sources.

The `.vof` text sources (below) show the same sequencer in the vertical-areas and line-length directives, so the mapping from `.vfo` arrays to `.vof` directives is one-to-one.

### Fields and swaps

**Established** as values, per field of the frame, arrays of `FieldsPerFrame` entries: `FieldLineCount`, `FieldLineOffset`, `FieldLineSkip`, `FieldSwap`, `FieldColor`, `FieldEye`. Non-interlaced one-field formats store 1 entry. `1920x1080_30i` has 2 fields of 540 lines, `FieldLineOffset` (0, 1) and `FieldLineSkip` (1, 1): field 1 starts one line down and takes every second line. The `.monitor` sources use the same idea (`field0 off = 0 inc = 2`, `field1 off = 1 inc = 2`), so skip = inc - 1 (**inferred** from this one pair). `1024x768_96s` (stereo) has 2 fields of 768 lines each, `FieldEye` (1, 2) and `FieldSwap` (1, 0): left eye then right eye, with a buffer swap after the first field only. `1280x1024_180qi` is field-sequential colour: 6 fields, `FieldColor` (1, 2, 4, 1, 2, 4) = red, green, blue as bit masks, 7 meaning all three; `FieldEye` 3 means both eyes. **Inferred:** `FieldEye` 1 left, 2 right, 3 both, and `FieldColor` a bit per primary, from the values in these three files. `SwapsPerFrame` equals the number of nonzero `FieldSwap` entries in the files read.

### Frame detection

**Established** as names and values, **inferred** as roles. The block named `PFD...` ("programmable frame detection", from `ProgrammableFrameDetection` 1) is a sequence the display generator uses to recognise a frame boundary on an incoming sync signal:

- `PFDSourceSignalName` is `CSYNC` (57 files) or `HSYNC` (17): the signal watched. **Established:** `HSYNC` exactly in the 17 files whose `SerratedCSyncOnHSync` is 1 (the other 57 have 0): `dg4.def` exports that field, builds a serrated sync on `HSYNC` when it is set and then names `HSYNC` as the source.
- `PFDTable` is 32 entries of 2 bits' worth of codes, with the names `PFDEQ` 0, `PFDLT` 1, `PFDGT` 2, `PFDTrigger` 3 stored in every file; 1280x1024_60 has (2, 1, 0 ..., 3). **Inferred:** the 32 entries are the 64-bit `VOC_PFD_SEQUENCE_LO/HI` register pair of the `.vof` sources (32 x 2 bits), each entry saying how a line's length compares with the previous (equal, shorter, longer) and 3 where the frame is declared. `PFDControlSize` is 32.
- `PFDClockSpeeds` (50, 25, 12.5 MHz), `PFDNumClockSpeeds` 3, `PFDClockSettings` (0, 1, 2) and `PFDClockSelect` (0, or 1 in 6 files): the measuring clock and its register code. `PFDComparatorPrecision`, `PFDRegularLines`, `PFDInvert`, `PFDValidTable`, `PFDVOFVerticalPhase`, `PFDVerticalPhaseBias`, `PFDMaximumClocks` (4096) and `PFDMinimumPrecision` (4e-8 in 64 files, 0 in 10): **inferred** to be the comparator width, the number of regular lines per frame, the invert flag, a validity flag, the vertical phase of the sequencer and limits, from the `VOC_PFD_CONTROL_COMP_PRECISION`, `_LINE_COUNT`, `_FLIP` and `VOC_VOF_VERT_PHASE` register names. `PFDVOFVerticalPhase` is close to, but not always, `TotalLinesPerFrame` minus the vertical back porch (1280x1024_60: 1065 - 35 = 1030, equal; 640x480_60: 525 - 34 = 491 with a 33-line back porch, one more); the exact rule is **unknown: no shipped software or published source depends on it** (the compiler that applies it is not shipped; the X module only copies the value; routes tried: the four `vfc/rules` files, which set no value for it, and the stored values of all 74 files against their line counts).

**Consumers, established** ([docs/dg.md](../docs/dg.md#genlock-parameters-command-25)): the frame-detection fields matter only for the combination's external sync format. The X module reads that `.vfo` and sends `PFDTable` (two packed words), `PFDInvert`, `PFDClockSelect` and `PFDComparatorPrecision` as words 7-11 of display command 25 (`DoDGRqstLoadGenlockParams`); `PFDVOFVerticalPhase` sets LoadFormat word 298 of each genlocked channel. `PFDRegularLines` and `PFDValidTable` are read and never sent: **unknown: no shipped software or published source depends on it** (routes tried: every load of those record offsets in `kona.so`, `setmon` and `ircombine`: all three carry the same format reader, `setmon`'s copy of the genlock builder loads the same six fields, and `ircombine` loads none).

## VOF sources (`vof/`)

**Established.** Three text files (`default.vof`, `vga.vof`, `640x480_60.vof`) and four `.monitor` files, hand-written inputs for an earlier or test version of the same compiler, with comments that define the directive set. They are not the sources of the shipped `.vfo` files (the 640x480_60 sync is 95 pixels in the `.vof` and 96 in the `.vfo`).

- `I signal level`: the initial level of each of the 14 signals (two more, SPARE1 and SPARE2, are marked defunct in two files and listed as live in `640x480_60.vof`).
- `E signal pixel level types`: an edge, placed in the next free edge block of that signal, with the list of line types it applies to.
- `L type length`: the length of a line type, in pixels in these files (800 for 640x480_60).
- `V repeat type`: a vertical area appended to the state table. 640x480_60 is `V 1 0`, `V 9 1`, `V 2 2`, `V 33 1`, `V 480 3`: one set-up line, 9 front-porch lines, 2 sync lines, 33 back-porch lines, 480 active lines.
- `R name value`: initial register values, names from a `voc1_regs.h` header that is not shipped. A fully commented-out list is the register map of the video output controller ("VOC"): `VOC_REVISION`; `VOC_CONTROL` (double-buffer enable and control, five interrupt enables: FIFO over, FIFO under, external sync loss, external frame, VDRC, host, and an output pixel mux); `VOC_IWSC_ORIGIN/SIZE/SCREEN` (input window: x and y origin and size, screen width); `VOC_VOF_CONTROL` (stop, one shot, reset source, clear state pointer, line/edge select) and `VOC_VOF_VERT_PHASE`; `VOC_PFD_CONTROL` (enable, flip, clock select, frame select, comparator precision, line count) and `VOC_PFD_SEQUENCE_LO/HI`; `VOC_VDRC_CONTROL` (enable, pixel size, dither, transfer size, transfer alpha), `VOC_VDRC_MAW`, `_FIRST_TILE_ADDRESS`, `_START_LINE`, `_MIDDLE_LINE`, `_END_LINE` (tile count, group-pixel count, request valid, repeat), `_PAN`, `_REQ` and `_REQ_PATTERN` (stereo and colour per slot, active lines, next cursor offset); `VOC_PLL_CONTROL` (ready, read and write execute, vertical wait, auto update), `VOC_PLL_ADDRESS/READBACK/DATA_REG`; `VOC_GEN_CONTROL`, `_HRATE_DIV`, `_H_MASK`, `_BP_CLAMP` (the horizontal mask and back-porch clamp, matching `HBackPorchClamp*` above); `VOC_FIFO_HIGH_WATER` (864 in two files; `default.vof` sets `VOC_FIFO_CONTROL_HIGH_WATER` to 640 instead), `VOC_FIFO_CONTROL`, `VOC_SAC_CONTROL`, `VOC_MUX_CONTROL_RATIO`, `VOC_SIZ_CONTROL` and the `VOC_SIZ_X_` and `_Y_` coefficient registers (a scaler: filter, slope, delta and four start coefficients per axis). The names are established; the list gives no address, width or bit position. **Established** since, from the firmware ([docs/dg.md](../docs/dg.md#voc-registers)): VOC register r of channel id is display-bus address 0x200 + 0x100 x id + r, the same space as `HH_VC_ADDRESS`. [DG.h](../DG.h) matches these names to the offsets the firmware writes.
- The comment "tiles are 160 x 8 pixels" and `VOC_VDRC_END_LINE_GROUPXEL_COUNT 160`, `VOC_VDRC_MAW 4` (640 pixels = 4 tiles) show the tile geometry; "groupxel" is the file's word for a unit of pixels in a tile line: four pixels, **established** from the firmware's requester and input-window code, which divides x by 4 and counts 40 groupxels per 160-pixel tile ([docs/dg.md](../docs/dg.md#the-video-requester)).

The `.monitor` files give the monitor's raster for a `.vof` (front and back porch, `hsync_max`, `vsync_max` = whole lines plus one hsync, pixels per line, lines per field, `num_fields` and one `fieldN off = a inc = b` per field). `1280x1024.monitor`: `pixels_per_line = 1680`, `lines_per_field = 1065`, `vsync_max = 5165` (= 3 lines + 125 pixels).

## Option-board image (`dgo1/dgo.mcs`)

**Established.** `dgo.mcs` is an Intel HEX file: one extended-segment record (segment 0), 2133 data records of 16 bytes and one of 10, an end record; every record checksum is correct and the data addresses run 0 to 0x8559 without gaps, giving 34138 bytes (273104 bits). `dgo` names the display-generator option board in the firmware (`dgWriteDgoTMC22071a`, `dgDGOOutputLetterbox`, `NIC_dgopt_type` in `arm1.s`: the board has a TMC22071A video encoder, **inferred** from the function name) and the `CCIR601_*_DGO.vfo` formats. **Inferred:** a programmable-logic configuration image (47 percent of the bytes are 0xff, the rest is dense). Read with the bits of every byte reversed (least significant bit first), the stream starts with eight 1 bits, the nibble 0010, a 24-bit value 0x042ac9 = 273097 and the nibble 1111. 273097 is 7 bits short of the file's 273104 bits, so the value is **inferred** to be a length count, and the layout (fill, preamble, length, fill) is that of a serial configuration stream for a programmable-logic device; which family, and what the image implements, is **unknown**. The ARM firmware's stored "flashprom combo image" and "Emergency Backup Format" messages (`ucode/tport.md`) are about combinations, not this file; **Established** (`kona.so` 6.5.30m strings): the X module names the directory `/usr/gfx/ucode/KONA/dgo1` and parses Intel HEX itself ("bad .mcs checksum at line %d (%s)!"), so the X server reads `dgo.mcs`; the firmware's logic-load requests are `DoDGRqstLoadXilinx` (6 words, bus 0x8900, "Illegal xilinx type %d") and `DoDGRqstLoadPabXilinx` (1328 words) ([docs/dg.md](../docs/dg.md#display-requests)). **Unknown: no shipped software or published source depends on it:** the device family and what the image implements.

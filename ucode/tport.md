# tport.bin: a second ARM image built from the display-generator code

What `usr/gfx/ucode/KONA/tport.bin` (IRIX 6.5.30m, 127889 bytes) is, from its container and strings. Facts are labelled **established** (read from the file), **inferred** (with the reasoning) or **unknown**. The file has not been disassembled; [scripts/arm1_disasm.py](../scripts/arm1_disasm.py) reads the same layout and would do it with a header offset.

## Container

**Established.** Five big-endian words precede an AIF-style header laid out as in [arm1.md](arm1.md): 0xbadc0ffe, 0x83, 0x44c00a35, 0 and 0. The header then has two no-op words, a branch-and-link (0xeb00000c), a data word (0xa4), an SWI 0x11, the read-only size 0x178e0 (96480), the read-write size 0x7a1c (31260), a debug size of 0, the zero-initialised size 0x52794 (337812), a debug type of 0 and the image base 0x0c000000, the same base as `arm1.u`. The header is the 0x80 bytes from file offset 0x14; read-only data start at offset 0x94, and 0x94 + 96480 + 31260 is 127888, one byte short of the file size. Unlike `arm1.u` there is no debug table, so the image has no symbols. The meaning of 0xbadc0ffe, 0x83 and 0x44c00a35 is **unknown**; **inferred:** a magic number, a version and a build stamp.

## Contents

**Established** (strings, 302 of them, 51 shared with `arm1.u`). It is ARM code for the display generator's requests: the same 93 request names `arm1.u` dispatches through `DGDispatchTable` ([dg_dispatch.tsv](dg_dispatch.tsv)): `VCWrite`, `VCRead`, `LoadFormat`, `EnableChannel`, `CursorPosition`, `InitTextport`, `LoadTextportGlyph`, `AutoInit`, `LoadEncoder` and the rest, with the command logging "DG: arm video cmd %s (%d) with %d words of data", the checksum messages ("DG: Checksum", "Reply checksum") and the reply path "SendDGRply". Its source files by assertion and message text are `video_request.c`, `video_util.c`, `video_clocks.c` and `eeprom.c`. It reports the board as "InfiniteReality2 Graphics" and counts engines and raster boards ("%d GEs, %d RMs"). It does not contain the host-interface, distributor or engine-loading strings of `arm1.u` (`pHipState`, `deactivate_ged` and the like): about 250 of its strings are not in `arm1.u`, most of them messages and assertions for video-request code.

**Established.** It carries an EEPROM writer and a loader for stored display configurations: "el: writing combo", "el: writing header", "el: writing ucode(0x%x)", "loading combination from EEPROM", "flashprom combo image failed to load, loading EBF...", "combo loaded from flashprom!", "loaded combination from Emergency Backup Format", and "auto executing %s" with "checking cmd %s" and "Error executing stored video command %d @0x%08x". `arm1.u` prints the same fallback message ("flashprom combo image failed to load, loading EBF...", in its own `eeprom_*` functions), so the two images share the EEPROM and combination code.

**Inferred.** A "combination" is a stored set of display-generator commands executed at start-up; the files under `dg4/cmb/` (26 files named by the channel layout, for example `1280x1024+NTSC_60.cmb`) are such sets and `dg4/vfo/` (75 files named by raster size and rate) the video formats they load. The reasoning rests on the names of the files and on the messages "loading combination" and "auto executing". The file formats are **unknown**.

**Unknown.** Whether `tport.bin` is the image the display generator's own processor runs, the standalone variant the textport (`InitTextport`, `LoadTextportGlyph`) needs when no engine is present, or a diagnostic build; where the pipe loads it from (no `find_ucode` tag naming it was found); and how its entry differs from `arm1.u`'s. The display tables themselves (`dg4/cmb`, `dg4/vfo`, `vof/`, `dgo1/dgo.mcs`) are not read.

# Setup and video-configuration tools: function reference

Sources: `usr/gfx/gfxinit` (also installed as `gfxinfo`), `usr/gfx/setmon`, `usr/bin/X11/xsetmon`, `usr/gfx/ircombine`, `usr/gfx/sgcombine`, `usr/gfx/dmconf`, `usr/gfx/ucode/vfc/sdbutil`, `usr/gfx/KONA/bin/ireeprom` and the diagnostic `usr/diags/IR/bin/hyper` (6.5.30m). Roles are **inferred** from names, strings and, for the register-facing helpers, the code cited. The graphical tools are built on SGI's ViewKit C++ class library: each form has a generated layout class (the name ending in `UI`) and a behaviour class derived from it, and the "EZ" classes are small wrappers for toolkit resource values. Names are given as the binaries spell them, with the C++ mangling.

### The InfiniteReality report of `gfxinfo`

**Established** (`gfxinit` 6.5.30m, the routine `kona_info` at 0x1000a218-0x1000a8f0 and the strings at 0x100215e8-0x10021758 and 0x10027c38-0x10027cc8). The report for a Kona pipe prints, in order: the board name, 'Display has N channels', 'N GEs (of M), occmask = 0x..', the back-end FIFO RAM and path width, the RM line with one count per slot, the per-slot texture memory, the pixel-depth class, the colour-map size and optionally the external-gamma suffix, then option lines (GPI, TVO, DPLEX, DVP, GVO, Sirius).

- **RM name by board set.** The first word of the configuration record picks it: set 0 RM6, set 2 RM8, set 5 RM10, set 6 RM11. Sets 1, 3 and 4 print RM7, or RM9 when every populated slot's three-byte name field reads RM9 and its flag bit 2 is clear. **Inferred** that the first word is the board-set number, from `vfmtActualHWToKonaTarget` reading it as `bdset`. The textport's names for the same sets are in [ucode/tport.md](../../ucode/tport.md).
- **Texture memory per slot.** Code 0 None, 1 16MB, 2 64MB, 3 128MB, 4 256MB, 5 512MB, 6 1024MB; an empty slot prints a dash, and slots are separated by a slash. The `GL_RENDERER` builder in `libGLcore` (`GetBoardInfo`, [opengl.md](../opengl/opengl.md#getboardinfo)) indexes the same ladder, 0, 16, 64, 128, 256, 512, 1024, with board-reply word +80, which is configuration offset +40, the first RM slot's texture word ([kernel.md](../kernel/kernel.md#the-configuration-record-and-its-identity-words); the reply's configuration record starts at +40).
- **Pixel depth.** 0 Small, 1 Medium, 2 Large, 3 Extra-Large; set 2 prints 3 as 'Extra-Small (Tiny)'. The single letters S, M, L and X that `GetBoardInfo` appends to the `GL_RENDERER` string index the same field (reply +180, configuration +140).
- **Colour map and gamma.** 32K for field value 0, 128K for 1, then a computed value for others; the suffix ', 64K external gamma' prints for external-gamma field 1.
- **Back-end FIFO.** '4MB external', '16MB external' or 'Internal', then '32bit path' or '16bit path'.
- **Board name.** Taken from the kernel's board record (ioctl 102). The IP27 kernel object `kona_edtinit.o` holds KONAL (+0x1260) and the IP35 `kona.a` holds KONAD (+0x17ff0). The tool carries the strings KONA, KONAT, KONAS, KONAL and KONAD; no shipped kernel produces KONA, KONAT or KONAS. **Established** (published output, 71 `gfxinfo` dumps): `KONA` (3 dumps) and `KONAS` (18) go with RM6 and `hinv` "InfiniteReality", `KONAL` (40) with IP27 hosts and `KONAD` (10) with IP35 hosts; the pairings are in the next list. `KONAT` is in no capture, and which hosts print plain `KONA` against `KONAS` is **unknown** (the `KONAS` posts that show a CPU line show IP25).
- **Board identity words, decoded (established, `arm1.u` 6.5.30m `init_config` 0x0c01d8a0-0x0c01dd24, `dg_board_id` 0x0c01d2d0).** The first word of the `brd:` line is the geometry board's scan-chain id (stored at configuration +256). The firmware takes from it the engine count (bits 17-16 as an index into the byte table 1, 2, 4, 8 at 0x0c01e098, stored at +4), the back-end FIFO memory code (bits 19-18, at +12) and the GPI flag (at +16): it is 1 only when bits 15-9 are all zero and bit 20 is clear, and 0 for any nonzero bits 15-9. The last word is the display board's id (stored at +836 and read at 0x0c01dd28-0x0c01dd7c): channel count is bits 18-16 plus one (at +20), the option-board type is bits 21-19 (at +24), bit 22 goes to the colour-map size field (+28) and bit 23 to the external-gamma field (+32), the two fields `gfxinfo` prints as the colour map and the gamma suffix, and bits 4-1 are stored at +72. The option type selects which serial-number page name is read: 3 TVO, 4 DPLEX, 5 DVP, 6 GVO on board sets other than 0, and 1 DVP or 2 PAB on board set 0 (strings at 0x0c01e02c-0x0c01e094). The published DPLEX sample decodes consistently: the geometry word `20160a06` has bits 17-16 equal to 2, so four engines ('4 GEs'), and the display word `f9211002` has bits 18-16 equal to 1 (two channels) and bits 21-19 equal to 4 (DPLEX). **Unknown, and not answerable from software held:** which board generation (GE12, GE14 or GE16; DG4 or DG5) a word names. The firmware never forms those names; the `GE14-4` and `DG5-2` forms of the verbose report come from the serial chips' part numbers, which no shipped binary lists, and what bits 4-1 of the display word and bits 8-0 of the geometry word mean is also unknown.
- **Not printed.** No GE revision and no DG revision appear for this pipe; the `brd:`, ` ge:`, `rm%d:` and ` dg:` lines of the verbose form print raw identity words. The `brd:`, ` ge:` and `rm%d:` words decode as the previous item says and [ir2e-ir3-products.md](../../evidence/findings/ir2e-ir3-products.md#123-board-identity-words-scan-chain-ids-printed-on-the-brd-line) grades (type, engine count and texture-code fields established); what stays **unknown** is the meaning of the geometry and raster words' low bits (8-0), of bits 4-1 of the display word and of the ` dg:` line's words ([dg.md](../../devices/dg/README.md#gfxinfo--v-sample-dplex-guide)). What would settle it: tabulate each word against the board part number and revision printed beside it in the published `gfxinfo -v` dumps and see which bits track the part or revision; a bit that never changes across boards of different parts is not a part code.
- **What published captures print** (**established**, published output; each line is evidence for the board shown, counts are dumps). The internal names `hinv` prints as "Graphics board: ..." (some posts capitalise Board), with the `gfxinfo` pair they go with:

  | `hinv` name (dumps) | `gfxinfo` board name | RM name | GEs | per-slot texture seen | host line |
  |---|---|---|---|---|---|
  | InfiniteReality (23) | KONA, KONAS | RM6 | 4 | 16MB, 64MB | IP19 (2), IP25 (6) |
  | Reality (6) | KONAL | RM8 | 2, occmask 0x03 | 16MB, 64MB | IP27 |
  | InfiniteReality2 (36) | KONAL | RM7 | 4 (one pipe 2) | 64MB | IP27 |
  | InfiniteReality2E (10) | KONAL, KONAD | RM9, RM7 once | 4 | 64MB | IP27, IP31, IP35 |
  | InfiniteReality3 (14) | KONAL, KONAD | RM10 | 4 | 256MB | IP27, IP31, IP35 |
  | InfiniteReality4 (4) | KONAD | RM11 | 4 | 1024MB | IP35 |

  The pixel-depth word and the channel count are the loaded combination's: RM6, RM7, RM9 and RM10 pipes show Small through Large or Extra-Large, RM8 pipes show only Extra-Small (Tiny), Small and Medium, and RM11 pipes show Extra-Large in all 7 dumps. The first-generation pipe's option line is "Sirius video option detected" (10), the others show GVO (14), TVO (8), GPI (7) or DPLEX (1). The `gfxinfo -v` identity records name the boards: GE12-4 (first generation), GE14-2 (Reality), GE14-4 (InfiniteReality2, seen in `hinv -m`), GE16-4 (2E, 3 and 4); RM6-16, RM8-16, RM9, and RM10 for IR4 pipes that print RM11; TM7-64 and TM9-1024; DG5-2 on Reality, 2E and IR4. The first-generation DG record prints "WARNING: No NIC page A found." and no board name. `hinv -m` locates the pipe at `/hw/module/N/slot/ioN/kona`. An unconfigured or corrupt record prints out-of-range numbers and empty text where a lookup misses ("Display has 0 channel", "Texture Memory: -/-/-/-", and one corrupt pipe with a count in the millions).
- **Microcode.** `kona_loaducode` (0x1000ca5c) loads `arm1.u`, `geif.u`, `ged1b.u` and `ge11.u` by name, in that order, with no board-set choice between them. **Established** by reading the four call sites.

### The hardware description and the channel limit (`ircombine`, 6.5.30)

**Established** (the stores of the `HardwareForm` callbacks, `ircombine` 6.5.30). The hardware form fills one record, reached through the word at +120 of the form, whose first words are: +0 the graphics board (0 for `doGfxOnyxIR`, 1 for `doGfxOnyx2IR`, 2 for `doGfxOnyx2R`, 3 for `doGfxOnyx2IR4`; 0x10055fe0 to 0x10056160), +4 the number of RM boards (1, 2 or 4 from `oneRM`, `twoRM` and `fourRM`, 0x10056550, 0x10056640 and 0x100563e0), +16 the number of video output channels (2 from `twoVOC`, 8 from `eightVOC`, 0x100566b0 and 0x10056360) and +24 the option board (0 none, 1 Sirius, 2 the TMDS video output, 3 the graphics video option, 4 the digital video projector and 5 the DPLEX; `siriusOption`, `doTmdsOptionButton`, `gvoOption`, `dvpOption`, `dplexOption`). No callback takes a pipe index. The menu offers two channels or eight and nothing else, which agrees with the two-VOC and eight-VOC display generators ([dg.md](../../devices/dg/README.md)).

**Established** (`vfmtUpdateFormatInfoInCombination` in `ircombine`, 0x10084ba0 to 0x100866cc). The routine walks 15 channel slots, each a 2736-byte record in the combination, counts the enabled ones, and reports "too many channels: specified hardware supports %d channels" (error 27, 0x1008668c to 0x100866c4) when the count exceeds the hardware record's channel word at +16 plus one if its option-board word at +24 is nonzero. So the limit follows the hardware description, not a fixed number. An eight-channel pipe with no option board accepts eight channels and refuses nine; with an option board the limit is nine. The combination has room for 15 channel slots at most, and the hardware menu stops at eight video channels. **Inferred:** the record read at 124(sp) there is the hardware description above; the routine receives it as an argument and the callers were not traced. Whether the shipped `8@` combination files exercise the limit is not read here; the `setmon` binary carries the same message text and a separate "22 channel option detected but not yet supported" refusal.

## `ireeprom`

**Established** (`usr/gfx/KONA/bin/ireeprom` 6.5.30m, option string `wrveiFp:f:hcd:s` at 0x100042b0, help text at 0x10004469-0x10004599): the pipe's EEPROM holds the pipe's firmware image (boot code and data, with a revision, timestamp, length and checksum that `-i` prints) and, separately, the stored video combination. The options are -w (write the EEPROM from a file in 'EEPROM boot-format'; a file whose revision is not newer than the stored one is refused unless -F), -r (read the EEPROM into a file), -e (erase it), -c (erase only the video combination), -v (compare the EEPROM with a file), -i (print its information), -F (force an older revision), -h, -p (pipe number) and -f (data file); -d and -s are in the option string but not in the help. `-w` writes firmware, not a combination. Writes go through the write-gather window (`KonWGWrite`, 0x10002a4c); `erase_combo` (0x10003430) prints 'Erasing KONA EEPROM video combination...' and sends two words, 492 and 6. **Established** (`arm1.u` `arm_eeprom_op` 0x0c01a0ec, read through its dispatch): the pipe's handler for token 492 subtracts one from the first payload word and jumps on the result, so the word 6 selects the branch at 0x0c01a124, which zeroes four words of the 128 KB scratch buffer and programs four bytes of it into the flash at 0x20000 (`eeprom_write`). Those four bytes are the combination header's magic word. At every start `DoDGRqstAutoInit` (0x0c004674) reads the first two words at 0x20000, accepts the stored combination only if the first is 0xfacefeed and the second is below 0x8000, and otherwise loads the built-in emergency backup format of 0x3fe words at 0x040402c8 with `dgLoadCombo`. That block holds a LoadFormat request (command 22 at block +224, the format block from +228) for `1280x1024_60.vfo`: name at +236, frame rate 60 times 65536 at +304, 1065 total lines and 1680 total pixels at +312 and +316, 1024 active lines and 1280 active pixels at +320 and +324. A wrong magic word or an oversized count (as after `ireeprom -c`) loads that block silently; only a stored combination whose header passes and which `dgLoadCombo` then refuses prints 'flashprom combo image failed to load, loading EBF...' and calls `dgFetal` (0x0c009628) before loading it (0x0c004708-0x0c004728). So `ireeprom -c` leaves the pipe starting on 1280x1024 at 60 Hz, as the posts say. A combination the display tools save to the pipe is written by operation 1, which puts the magic and the word count at 0x20000 and the payload after them (`eeprom_load` 0x0c01a230); the same start-up read finds it again on every start, so the stored combination is reloaded after each reset for as long as the flash holds it. **Inferred:** that the flash holds it across power-off, from the part's program command sequence in `eeprom_state` (0xaa, 0x55, then 0xa0 at the unlock addresses) being that of a non-volatile flash device; the firmware gives no other evidence.

## What the published manuals add

Labels follow [published-sources.md](../../references/documents/published-sources.md); page numbers are PDF page indexes of the stored copies ([references/documents/](../../references/documents/README.md)).

- **`ircombine` (established, published).** The combiner's windows, per-channel attributes, global attributes, target-hardware facility and encoder channel are described in the InfiniteReality Video Format Combiner User's Guide (007-3279-003); [dg.md](../../devices/dg/README.md#what-the-published-manuals-add) holds each limit it states. Its command lines: `/usr/gfx/ircombine -gui [-target display]`, `ircombine -source file F -dest active`, `setmon -n file` (download), `setmon -x file` (store in the EEPROM) and `setmon -g` (external genlock), samples in `/usr/gfx/ucode/KONA/dg4/cmb`, formats described in `/usr/gfx/ucode/KONA/dg4/vfo/README`, and graphics restarted by `(/usr/gfx/stopgfx ; /usr/gfx/startgfx) &` (PDF p. 22, 45; DPLEX guide PDF p. 16, 31). The XSGIvc server extension library answers queries about the running combination and `XSGIvcLoadVideoFormatCombination()` loads one (PDF p. 17, 22). The form classes listed above for `ircombine` (`HardwareForm` with `doGfxOnyxIR`, `doGfxOnyx2IR`, `doGfxOnyx2IR4`, `doGfxOnyx2R`) are the target-hardware choices of the manual's Target Hardware window (Onyx InfiniteReality, Onyx2 InfiniteReality, Onyx2 Reality; PDF p. 46); the IR4 entry is not in the 1998 manual, so it was added by a later release.
- **`gfxinfo` and `hyperpipeinfo` (established, published).** A printed `gfxinfo -v` and `hyperpipeinfo` for a two-pipe DPLEX system are annotated under [the display generator chapter](../../devices/dg/README.md#gfxinfo--v-sample-dplex-guide). `hyperpipeinfo` takes no arguments and prints one `network id` per pipe (-1 for a pipe outside any network).
- **`hyper` (established, published).** The DPLEX guide names `/usr/diags/IR/bin/hyper` as the example that configures the existing DPLEX network and runs a clock application on all pipes, multiplexed at the output pipe, with source in `/usr/share/src/hyperpipe/hyper` from the `gl_dev.sw.gldev` subset (007-3849-001 PDF p. 50). It uses the `GLX_SGIX_hyperpipe` calls named in [libgl.md](../opengl/libgl.md). The same guide says `irsaudit` makes only a limited check of a DPLEX board and cannot run from the DPLEX output monitor or the graphics console, and that the window system must be stopped first (PDF p. 46; the HD GVO guide says the same for TVO boards, PDF p. 26).
- **`sdbutil` and the video format compiler (established, published).** The compiler's manual (007-3402-003) documents the rules files that [ucode/dg.md](../../ucode/dg.md) reads from the `.def` files: a board description with required variables `VideoClockRatioNumerator`, `VideoClockRatioDenominator`, `SystemVideoClockRateMaximum`, `SystemVideoClockRateMinimum`, `DisplayArchitecture` (examples `MG_VC3`, `O2_GBE`, `IR`) and `VfoVersion`, and optional `DACRateMaximum`, `DACRateMinimum` and `OptionHardware` (examples `Presenter`, `DDO2`, `GVO`); signal assignments from chip signal to board signal; the special signals composite sync, active, tri-level sync and pixel-requesting; and transition rules over an edge database whose transitions are kept at the database's own resolution until extracted and then quantised to the clock (PDF p. 83-87). These are the field names that appear as `DisplayArchitecture`, `OptionHardware` and `PixelAccurateBlanking` rows of the combination files in [ucode/dg.md](../../ucode/dg.md) and agree with them.

- `vfcInitKonaCombinationChannel` (`usr/gfx/ircombine` 0x1007e130): **Established.** The 1128-byte initializer clears the channel's scalar fields, flags and work-order slots (including stores at 0x1007e154, 0x1007e1f0, 0x1007e230 and 0x1007e464), records the caller's channel arguments at offsets 0, 4, 8, 0xc and 0x10 of the temporary record (stores at 0x1007e284-0x1007e294 and 0x1007e374-0x1007e394), and creates the format records through `vfcGetKonaCombination` at 0x1007e2b8, 0x1007e330 and 0x1007e3b0.
